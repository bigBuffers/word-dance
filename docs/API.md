# word-Dance — REST API contract

Base path `/api` (media at `/media`, SPA at `/`). JSON in/out, `Content-Type: application/json; charset=utf-8`. This file is the frozen contract between the backend routers (`backend/wd/routers/*`, Pydantic models in `backend/wd/schemas.py`) and the frontend (`frontend/src/api/types.ts` — Section 9 is copied there verbatim). Any change requires updating `schemas.py`, `types.ts` and this file in one commit.

## 1. Conventions

* **Auth column**: `–` public · `U` logged-in user (401 otherwise) · `O` logged-in user with `onboarding_state='done'` (409 `onboarding_required` otherwise; `/api/onboarding/*`, `/api/auth/*`, `/api/account/*`, `/api/settings*`, `/api/screen/*`, `/api/stages`, `/api/vocab*`, `/api/lookup`, `/api/words/*`, `/api/bank*`, `/api/suggestions*` are `U` — browsing, screening and the bank work before onboarding; only 今日/学习/记录 require it, matching FRONTEND §2 and DESIGN §6.2) · `A` admin (403 otherwise) · `G` guardian (slice 1-B): an account with `account_kind='guardian'` acting in its **own** session (`sessions.actor_user_id IS NULL`) — a switched child session and every non-guardian get 403 `forbidden` · `G+gate`: `G` with the session's 家长门 stamp (`sessions.guardian_gate_at`, written by endpoints 102 / 105) not older than 10 minutes, else 403 `guardian_gate_required`.
* **Child accounts** (slice 1-B): a child account (`users.guardian_user_id IS NOT NULL`, `User.is_child`) gets 403 `guardian_required` on the account and identity endpoints whatever the session type — **6** `PUT /api/account`, **7** `POST /api/account/password`, **8** `DELETE /api/account`, **9** / **10** e-mail code / verify, **85–88** phone codes / bind / unbind / rebind, **89** profile, **104** switch, **108–111** claim / declare (`deps.require_not_child`); learning, settings (14–18), bank, export / import, words and screening stay open to children, and a child never satisfies `G` — its guardian does these things in 「我的孩子」 (94–103). The third-party bind / unbind endpoints of slice 2-A (112 with `kind:'bind'`, 117, 118 / 120 with `kind=bind`) are on the list too.
* **Third-party identities** (slice 2-A, §3.3): a WeChat mini-program openid, a QQ openid or an Apple `sub` is an `identities` row (`provider ∈ {wechat_mini, qq, apple}`, `subject` = the id) next to the phone identity of §3.1 — pseudonymous, never shown to anyone, never logged; `User.providers` lists the providers bound to the account and `ServerFlags.wechat_enabled` / `qq_enabled` / `apple_enabled` (also in `GET /api/health`) say which providers this instance offers (`WD_WECHAT_*` / `WD_QQ_*` / `WD_APPLE_*`, DEPLOY §4; all false = nothing changes for users). An account that has only such identities sets a password at `/welcome` step 0 (89) — WeChat / QQ / Apple are never a re-authentication factor, and an admin never signs in through them (403 `password_required`, the endpoint-81 rule).
* **Word visibility** (the single rule, applied by every route that reads `words`: 20, 21, 22, 23, 24, 25, 31, 33, 52, 53 and the screen/today joins): a word is visible to user `:me` iff `is_public = 1 OR created_by_user_id = :me OR EXISTS (SELECT 1 FROM user_words uw WHERE uw.user_id = :me AND uw.word_id = words.id)`; admins see every word. A word that is invisible yields 404 `word_not_found` (never 403) and is absent from lists. Two users who added the same unvalidated string share one `words` row and both see it; a third user does not (DESIGN §5.2).
* **Route order**: FastAPI matches routes in registration order. The lookup preview lives at `GET /api/lookup` (not under `/api/words/`) so it can never collide with `GET /api/words/{id_or_lemma}`; every static sibling path under a dynamic segment (e.g. `POST /api/words/batch-mark`) is registered before the dynamic route, and `{id_or_lemma}` never matches a path containing `/`.
* **Session**: cookie `wd_session` (`HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` + `Secure` on https). Sliding expiry once per day. A child's device session (endpoint 107, slice 1-B) is fixed at 90 days (`Max-Age=7776000`), and the slide never shortens a session: `expires_at = max(current expires_at, now + WD_SESSION_DAYS)`, the re-sent cookie carrying the seconds left until it. The WeChat bridge (§3.3, slice 2-A) adds a second, short-lived cookie: `wd_wxt` (`HttpOnly; SameSite=Lax; Path=/api/auth/wechat/ticket; Max-Age=180`, `Secure` like the session cookie) — the poll secret of a login / bind ticket (112), required by 113 / 114 (a poll without it is a 404 identical to an unknown ticket) and cleared when the ticket is consumed; it never identifies a user. The QQ / Apple flows (§3.3, 118–122) add a third one: `wd_oauth` (`HttpOnly; SameSite=Lax; Path=/api/auth; Max-Age=600`, `Secure` like the session cookie) — a random browser secret set by 118 / 120 on the 302 to the provider; its sha256 travels inside the signed `state` and then inside the one-time grant, and 122 requires it (a grant whose hash is not that of the cookie presented → 302 `/login?error=invalid_grant`, nothing else happens) and clears it. It ties the result of a flow to the browser that started it; it never identifies a user either.
* **CSRF**: every non-GET `/api/*` request must carry `X-WD-Request: 1`; if an `Origin` header is present it must equal **either** the request's own `Host`-derived origin (scheme from `X-Forwarded-Proto` when `WD_TRUST_PROXY=1`, else the connection) **or** the origin of `WD_PUBLIC_URL` when set (`http://localhost:5173` is also accepted when `WD_DEV=1`). Otherwise 403 `csrf_rejected`. No CORS. (Accepting the Host-derived origin keeps a LAN install reachable by IP *and* by hostname even though install.sh writes the LAN URL into `WD_PUBLIC_URL` for delivery links — DEPLOY §4.) One exception by path (`deps.CSRF_EXEMPT_PATHS`, slice 2-A): `POST /api/auth/apple/callback` (121) is Apple's `response_mode=form_post` landing from appleid.apple.com — no header, a foreign Origin — so the middleware skips the rule for exactly that path and the endpoint verifies its HMAC-signed `state` (10 minutes, `wd/oauth_state.py`) instead (§3.3); the state proves the server minted it, and the `wd_oauth` cookie checked at 122 proves the browser collecting the result is the one that started the flow.
* **Pagination**: `page` (1-based, default 1), `page_size` (default 50, max 100). Response `{"items":[…],"page":1,"page_size":50,"total":4722}`.
* **Idempotency**: all `GET`s are side-effect free (`GET /api/today` and 123 `GET /api/today/playlist` never build; 76 `GET /media/audio` only fills its clip cache — the same answer for the same text). Grades and screening verdicts carry `client_event_id` (UUID v4); a duplicate returns the original outcome with `duplicate:true`.
* **Throttling** (DESIGN §10, persistent `auth_throttle`): every authenticated non-GET `/api/*` request counts toward **300 mutations per minute per user** (`mutate:user:<id>`, checked by the `current_user` dependency before the route runs); the per-endpoint limits (login, register, verification codes, password re-checks, custom adds, …) are listed with their endpoints. The login IP limit (endpoint 3, `login:ip:<ip>` 20 per 10 min) counts **failures only**, and the lockout key is `login:user:<identifier>:<ip>` with the identifier in its canonical form — a phone as E.164, an e-mail NFKC lower-cased, a username lower-cased, so another spelling of the same number is the same bucket (`wd unlock <identifier>` clears it). Verification-code sends (endpoints 80, 82, 85, 90) are limited per target (`code_send:target:<E.164|email>` 1/min, 5/h, 10/day), per client IP (`code_send:ip:<ip>`, `WD_CODE_IP_HOURLY` per hour), for phones per 7-digit prefix (5/h) and by the site-wide SMS caps `WD_SMS_HOURLY_CAP` / `WD_SMS_DAILY_CAP` (503 `sms_budget_exhausted`, not 429; sends that would create an account stop at 70 % of the day cap); endpoint 9 keeps only its own `email_code:user:<id>` 3/h and no `code_send` keys. Code checks (10, 81, 83, 86, 88, 91) count 20/h per target (`code_check:target:<t>`) and 60/h per IP (`code_check:ip:<ip>`) — **failed checks only**, read before the code is looked at: a correct code never spends a window; captcha challenges (79) 60/h per IP. Over a limit → 429 `rate_limited` with `Retry-After` and `details.retry_after_s`; `GET`s are never throttled — except 76 `GET /media/audio`, whose cache **misses** count 60 per user and minute (hits are free), 79 `GET /api/auth/captcha`, and 113 `GET /api/auth/wechat/ticket/{ticket}` (the WeChat poll, `wx_poll:ip`, below). Learner-triggered content generation (a 不熟悉 mark on a word without content, and endpoint 30) also counts toward `WD_AI_USER_DAILY_WORDS` words per user per UTC day (`ai:user:<id>`, 80 by default, 0 = unlimited): beyond it the mark still lands but nothing is enqueued and endpoint 30 answers 429 (CLAUDE_INTEGRATION §7). Slice 1-B adds three keys: a child's login codes (endpoint 99) count 5 per hour per child (`child_code:user:<child id>`); child-device sign-ins (107) count **failures only**, 10 per hour per IP (`child_login:ip:<ip>`, the `login:ip` rule — a valid code never spends the window); and the 家长门 (102, 105) has no window but a lockout key `gate:user:<guardian id>` with the login cadence (10 failures → 15 min, doubling every 5 more up to 24 h, cleared by a success; 423 `account_locked` with `details.retry_after_s`) — keyed per guardian, not per IP, because the guesser sits on the guardian's own device. Slice 2-A adds the WeChat bridge's keys (the `wechat_bridge.py` constants): a browser's tickets `wx_ticket:ip:<ip>:m` 30/min and `wx_ticket:ip:<ip>:h` 300/h (112 — a classroom behind one NAT opening the sheet together, every 3-minute refresh a new ticket), its polls `wx_poll:ip:<ip>` 1200/min (113 alone — thirty sheets polling every 2 s; 114, the 小程序码 picture, is **not** throttled: one image per ticket, bounded by 112 and served from a process cache, and a 429 on the `<img>` would hide it for good), and the mini program's `wx_scan:ip:<ip>` 600/min (115) and `wx_confirm:ip:<ip>` 600/min (116) — **flood brakes only**: in release every mini-program request reaches the server through the mainland relay host (DEPLOY §7.1), whose single address is what `client_ip` sees, so these two windows are site-wide caps and must stay wide; the brute-force brakes are per WeChat user — `wx_scan:openid:<sha256 prefix>` 10/min after code2Session and `wx_confirm:openid:<sha256 prefix>` 20/min on the ticket row's openid, counted before the `mp_token` is checked (the keys carry a hash, never the openid). The QQ / Apple windows are listed with 118–121.
* **Timestamps** UTC ISO-8601 `YYYY-MM-DDTHH:MM:SSZ`; local dates `YYYY-MM-DD`.
* **Headers on every response**: `X-Request-Id` (uuid4, also in logs); `Cache-Control: no-store` on all `/api` JSON.
* **Error envelope** (all errors incl. Pydantic validation, which is converted from FastAPI's 422):

```json
{"error":{"code":"invalid_word","message":"只能包含英文字母、空格、连字符、撇号和缩写点","details":{"input":"abc123"}}}
```

| `payload_too_large` | 413 | request body larger than `WD_MAX_BODY_BYTES` (rejected from `Content-Length` before the body is read, or while streaming it; `details.max_bytes`) |
| `account_locked` | 423 | login lockout, or the 家长门 lockout of 102 / 105 (`gate:user:<guardian id>`, the same cadence) — `details.retry_after_s` |

| `ai_disabled` | 503 | admin AI action while `WD_AI_ENABLED=0` / paused |
| `audio_unavailable` | 503 | `GET /media/audio` (76) when no clip can be produced — `details.reason`: `off` (no provider: `WD_AUDIO_PROVIDER=off`, or `auto` on a host without `/usr/bin/say`; the client stops asking for the rest of its session), `busy` (no synthesis slot within 8 s, or too many requests already waiting for one; under `bailian` also a 429 / 5xx from 百炼 — retry in a minute), `failed` (the provider failed — for this text, or for every text when `say` resolves no English voice or `WD_AUDIO_SAY_VOICE` names a voice `say` does not know, or 百炼 refused: a wrong key, a voice the model lacks, arrears; for `accent=zh-CN` also: `say` has no Chinese voice, `WD_AUDIO_SAY_VOICE_ZH` names none, or the provider is `youdao` / `bailian`, which speak no Chinese yet; the log event `audio_unavailable` says which) or `missing` (`WD_AUDIO_PROVIDER=cache`: the read-only mirror of another host's `say` clips has no clip for this text — and none at all for `accent=zh-CN` — the client speaks it with the device's own voice if it has one) |
| `provider_error` | 502 | the third-party provider failed (slice 2-A, §3.3): code2Session or the 小程序码 (114 → the SPA shows the pairing code alone; 115), the QQ token / openid exchange (119), Apple's JWKS fetch (121) — the provider's own error code goes to the log, never to the client |
| `email_send_failed` | 503 | `POST /api/account/email/request-code` (9) and every e-mail code send (80, 82, 85, 90) when the mail provider refused or could not be reached (the code is voided; retry later) |
| `sms_budget_exhausted` | 503 | a phone code send while the site's hourly / daily SMS cap is reached, or a send that would create an account past 70 % of the day cap (`details.retry_after_s` = seconds to the next hour / the next `WD_TZ` day; which cap refused is logged, never returned) |
| `sms_send_failed` | 503 | the SMS provider failed for a reason other than a rate limit (a provider rate limit is 429 `rate_limited` with `Retry-After`); the code is voided |
| `internal_error` | 500 | unexpected; logged with request id |

**2 `POST /api/auth/register`** — body `{username: string, password: string, display_name?: string, email?: string, invite_code?: string}`. `username` 2–32 chars `^[A-Za-z0-9_一-龥]+$` and never a mainland mobile number (`1…` 11 digits, optionally prefixed `86` / `0086` → 400 `validation_error`, `details.fields.username` 「用户名不能是手机号」: such a name would shadow the number's own identity in endpoint 3); `password` 8–64 chars; `display_name` ≤ 32. → `201 {user: User, settings: Settings}` + cookie. The `user_settings` row is inserted in the same transaction as the user **with `next_push_at = clock.compute_next_push(now, 'Asia/Shanghai', '08:00')`** computed from the default settings — a freshly registered user is never left with `next_push_at NULL` (the scheduler selects users by `next_push_at <= …`, DESIGN §6.4); onboarding and `PUT /api/settings` recompute it. **Bootstrap rule**: inside one `BEGIN IMMEDIATE` the server checks `SELECT COUNT(*) FROM users`; when it is 0 the registration is accepted **regardless of `WD_REGISTRATION_MODE` and without an invite code**, and that user becomes `admin` (the first user ever is always admin). Errors: 400 `validation_error`/`weak_password`, 403 `registration_closed`/`invalid_invite`/`verification_required`, 409 `username_taken`/`email_taken`, 429 (5/h per IP, `register:ip:<ip>` — counted here only, never by the code sign-in).

**3 `POST /api/auth/login`** — `{username: string (≤ 254), password: string}` → `200 {user, settings}` + `Set-Cookie`. `username` is an **identifier**, resolved in this order: the exact username (`COLLATE NOCASE`); when it normalises to a mainland phone number (`^\+?86?1\d{10}$`), the live `identities(provider='phone')` row; when it contains `@`, the account whose `users.email` equals it (lower-cased) **and** is verified; anything else takes the dummy-hash path (401). 401 `invalid_credentials`, 403 `account_disabled`, 423 `account_locked`, 429. A new session is created (no fixation). `login:ip:<ip>` (20 per 10 min) counts **failures only** (checked before the password, counted on the failure path); the lockout key is `login:user:<identifier>:<ip>` with the identifier in its canonical form — the spellings the resolution above uses: a phone as E.164, an e-mail NFKC lower-cased, a username lower-cased, so 「138 0013 8000」 and `+8613800138000` share one bucket (10 failures → 15 min, doubling every 5 more up to 24 h, cleared by a success or `wd unlock <identifier>` in any spelling). Admin accounts sign in here only — a code login (81) answers them 403 `password_required`.

### 3.1 Sign-in by verification code (slice 1-A)

Design: docs/AUTH_SIGNUP_DESIGN.md §5.2; the account model (`identities`, `login_codes`, `users.password_set_at` / `age_band`) is migration 0018. Codes are 6 digits, valid **10 minutes**, 5 attempts, stored as `HMAC-SHA256(WD_SECRET_KEY, code:channel:target:purpose)`; a new code voids the older unused codes of the same (channel, target, purpose). Targets are normalised first: phones to E.164 (`1xxxxxxxxxx`, `861…`, `+861…` → `+86` + 11 digits, else 400 `invalid_phone`), e-mails NFKC / trimmed / lower-cased (the endpoint 2 rule, else 400 `validation_error`). Every send below obeys the §1 send throttles (429); a phone send also needs `WD_SMS_PROVIDER` (409 `sms_unconfigured`) and the site-wide caps (503 `sms_budget_exhausted`), an e-mail send a mail provider (409 `smtp_unconfigured`); a send's answer never reveals whether the target belongs to an account. Admin endpoints 92 / 93 are in §8.

**80 `POST /api/auth/code`** — `{channel: CodeChannel, target: string, purpose: 'login' | 'reset_password', consent?: boolean, captcha?: CaptchaToken}` → `202 CodeSendResponse {sent: true, expires_in_s: 600}` for known and unknown targets alike. Order: `purpose:'login'` requires `consent: true` (400 `consent_required`) → target normalisation → channel availability (409 `sms_unconfigured` / `smtp_unconfigured`) → captcha while `WD_CAPTCHA=on` and no session (400 `captcha_required` / `invalid_captcha`) → the §1 send throttles (429) → the SMS caps (503 `sms_budget_exhausted`; a `login` send to a target without an account stops at 70 % of the day cap) → issue + send (503 `sms_send_failed` / `email_send_failed` void the code; a provider rate limit is 429 `rate_limited` with `Retry-After`; a number the provider refuses as illegal is 400 `invalid_phone`). Existing account: `role='admin'` → 403 `password_required`; disabled → 403 `account_disabled`; a phone identity whose last code login (else its binding) is older than `WD_PHONE_STALE_DAYS` → `{user: null, settings: null, created: false, challenge: StaleChallenge}` and no cookie; otherwise `identities.last_login_at` / `users.last_login_at` are updated and a session issued. Slice 1-B: a guardian with ≥ 1 child keeps its phone — 409 `guardian_factors_required`, `details.missing: ['phone']` (the phone is mandatory while children exist; the verified code survives the refusal; 88 rebind is unaffected); a child account gets 403 `guardian_required` (its phone is bound and unbound by the guardian, 100 / 101).

**89 `POST /api/account/profile`** — `{display_name: string (1–32), account_kind?: AccountKind (default 'learner'), age_band: '14plus' | 'adult', username?: string, password?: string}` → `200 {user}`: the first-time setup of a code-created account, allowed only while `needs_profile` (409 `invalid_transition`, `details.reason:'profile_done'`); `username` follows the endpoint 2 rule (409 `username_taken`), `password` the password rules (400 `weak_password`; sets `has_password`); writes `account_kind`, `age_band`, `age_declared_at`, `age_declared_ip`. `u14` is refused (400 `validation_error`, 「未满 14 周岁的同学请由家长注册」 — child accounts are created by a guardian, endpoint 95). ### 3.2 Guardian and child accounts (slice 1-B)

Design: docs/AUTH_SIGNUP_DESIGN.md §5.1 「家长 + 孩子」, §5.2 「切换与边界」 / 「未成年人」 / 「存量账号」; migration 0019 (`family_codes`, `sessions.guardian_gate_at`, `users.profile_prompted_at`) on top of 0018's `users.account_kind` / `guardian_user_id` / `guardian_consent_at` / `guardian_pin_hash` and `sessions.actor_user_id`. A **guardian** is an account with `account_kind='guardian'` — chosen at `/welcome` step 0 (89), declared by the legacy prompt (110) or made one by a claim (109). It needs **two factors** before it may create, switch into or issue codes for children: a live phone identity AND a password or a verified e-mail (`family.guardian_ready`; otherwise 409 `guardian_factors_required` with `details.missing ⊆ ['phone', 'second_factor']` — and 6 / 87 refuse to remove a factor while children exist). A **child** is a `users` row with `guardian_user_id` (`User.is_child`), created by its guardian (95: `age_band 'u14'`, `age_declared_at` / `age_declared_ip` / `guardian_consent_at` stamped at creation — the guardian's consent is the creation itself) or claimed from an existing account (109). Children are learners in every other respect — learning, settings, the bank, export / import, words and screening answer them like anybody —, but the **restriction list** of §1 (6–10, 85–89, 108–111) answers a child 403 `guardian_required` whatever its session (a switch, a login code, a simple username + password), and a child never satisfies `G` — 104 and every `/api/guardian/*` endpoint answer it 403 `forbidden`: its guardian renames, re-passwords, signs out, sets free or deletes it through 94–101. Constants, not settings (`backend/wd/family.py`): a child's device session 90 days, the 家长门 stamp 10 minutes, at most 10 children per guardian, 8-digit child login codes and 6-digit claim codes valid 10 minutes (`family_codes` with `code_hash = HMAC-SHA256(WD_SECRET_KEY, code:kind:target)`; expired rows GC'd hourly, used rows kept a day), 5 wrong guesses burn a claim code. Codes and PINs never reach a log line or a `system_events` detail (ids only).

**The 家长门** (endpoints 102 / 105; `G+gate` = 95–101 and 103): the guardian proves it is not the child holding the tablet with **exactly one** of the 6-digit 家长 PIN (`users.guardian_pin_hash`, bcrypt; never all one digit or a straight run; wrong → 401 `invalid_pin`), the account's password (401 `invalid_credentials`, the `pwcheck:user:<id>` budget of endpoint 7 → 429; an account without a password → 400 `validation_error`, `details.fields.password` 「账号没有密码，请用 PIN 或验证码」) or a `reauth` code (85 from a guardian session, 106 from a switched child session; wrong → 400 `invalid_code`); two factors or none → 400 `validation_error` 「PIN、密码和验证码必须且只能提供一个」. Every failure counts on the lockout key `gate:user:<guardian id>` with the login cadence (10 failures → 15 min, doubling every 5 more, max 24 h; 423 `account_locked` with `details.retry_after_s`, checked before the factor, cleared by a success) — keyed per guardian, not per IP, because the guesser sits on the guardian's own device; the code-check windows of §1 are not used here. A success stamps `sessions.guardian_gate_at` on the guardian's session: the gate is passed **once per sitting** (10 minutes per session — `SessionInfo.gate_until` / `ChildrenResponse.gate_until` say until when), never per request; 102 stamps the current session, 105 the guardian session it creates (the guardian lands on 我的孩子 without a second prompt). A guardian without a PIN passes with the password or a code and sets the PIN in 95 or 103; a forgotten PIN is replaced the same way (103 needs the stamp once a PIN exists).

**94 `GET /api/guardian/children`** (`G`) → `200 ChildrenResponse {items: ChildAccount[] (by created_at), pin_set, ready, missing, gate_until}`: my children with the progress figures of `AdminUser` (`bank_size`, `streak_days`, `last_login_at`) and `sessions` = the child's live sessions (signed-in devices — the switched ones included), `pin_set` = `users.guardian_pin_hash IS NOT NULL`, `ready` / `missing` = the two-factor readiness, `gate_until` = the session's stamp as in `SessionInfo`. **95 `POST /api/guardian/children`** (`G+gate`) — `{display_name: string (1–32), pin?: string (6 digits), username?: string, password?: string}` → `201 ChildResponse {child}`. With a username + password the child can also sign in on the login page (3).
**97 `DELETE /api/guardian/children/{id}`** (`G+gate`) → `204`: the full cascade (sessions, identities, login codes, family codes, the bank, …; the private-word rule of endpoint 8 applies) and `system_events('child_deleted', {child_id, guardian_id})`. 404 `not_found` unless mine.
**98 `POST /api/guardian/children/{id}/sessions/revoke`** (`G+gate`) → `204`: every session of the child is deleted — the guardian-issued ones (104) and its own devices (107) alike. 404 unless mine.
**99 `POST /api/guardian/children/{id}/login-code`** (`G+gate`) → `201 ChildLoginCode {code: "12345678", expires_in_s: 600}`: readiness; 5 per hour per child (`child_code:user:<child id>`, 429); a fresh 8-digit one-time code (`family_codes` kind `child_login`; the child's older unused codes are voided, so one code is live per child) for the child's own device (107). Shown once, never logged (the log event `child_code_issued` carries ids only).
**100 `POST /api/guardian/children/{id}/code`** (`G+gate`) — `{target: string}` (a phone) → `202 CodeSendResponse`: the first step of 独立 — a `bind_phone` code to the number the child will own (template 100004; the §1 send throttles, the SMS caps, 409 `sms_unconfigured`; no captcha). Readiness; 400 `invalid_phone`; a live identity for the number on another account → 409 `identity_taken` (the child's own number — a claimed legacy account that kept it — is accepted: 101 re-verifies and keeps that identity). The code row belongs to the CHILD (`login_codes.user_id`), so only 101 can spend it.
**101 `POST /api/guardian/children/{id}/emancipate`** (`G+gate`) — `{target: string, code: string (6 digits), password: string}` → `200 ChildResponse` (the row as it is after the change, so the page can show the result before the card leaves the list). 独立 for a child who turned 14: readiness; the code of 100 is verified behind the §1 code-check windows and outside the transaction (400 `invalid_code`), the password follows the password rules (400 `weak_password`); then one transaction consumes the code, binds the phone (`identities`, `verified_at = last_login_at = now`; a number the child already holds is re-verified and kept, another number it held is replaced as in 88; 409 `identity_taken` when another account holds it), sets the password (every session of the child revoked — the shared tablet signs out of the child), detaches the child (`guardian_user_id NULL`, `account_kind 'learner'`, `age_band '14plus'`, `age_declared_at` / `age_declared_ip` = now), voids its login codes and writes `system_events('child_emancipated', {child_id, guardian_id})`. **Irreversible**: the account is an ordinary learner afterwards (a second call is 404 — it is nobody's child); it joins a family again only through the claim flow (108 / 109).
**102 `POST /api/guardian/gate`** (`G`) — `{pin?: string (6 digits), password?: string, code?: string (6 digits)}` (exactly one) → `200 GateResponse {gate_until}`: the 家长门 above for this session; `gate_until` = now + 10 min. 423 / 401 / 400 / 429 as described; the `reauth` code (85) is consumed together with the stamp.
**103 `PUT /api/guardian/pin`** (`G+gate`) — `{pin: string (6 digits)}` → `204`: set or change the 家长 PIN (400 `validation_error`, `details.fields.pin` with the PIN rule's text; 403 `guardian_gate_required` without a fresh stamp — the first PIN too: a guardian without one passes 102 with the password or a code, which is also how a forgotten PIN is replaced; whoever merely holds the guardian's signed-in tablet must not be able to plant a PIN and open the gate with it). Log event `guardian_pin_set`.
**104 `POST /api/auth/switch/{child_id}`** (`G`) → `200 AuthResponse` (the CHILD's `user` + `settings`) + `Set-Cookie`: this device becomes the child's — the guardian's session on this device is deleted and a child session with `actor_user_id` = the guardian is issued in one transaction (other devices keep the guardian; the child's `users.last_login_at` is refreshed). Readiness (409 `guardian_factors_required`); 404 `not_found` unless mine; a disabled child → 403 `account_disabled`. No gate (「一键切换到孩子账号学习，切回要过家长门」), never `login:ip`, never the lockout; the cookie keeps the guardian's `WD_SESSION_DAYS`. A child account — a switched session included — gets 403 `guardian_required` (the §1 restriction list); every other non-guardian 403 `forbidden`.
**105 `POST /api/auth/switch/back`** (`U`, a switched child session) — `{pin?, password?, code?}` (exactly one) → `200 AuthResponse` (the GUARDIAN's) + `Set-Cookie`: the 家长门 against the guardian behind the session (`sessions.actor_user_id`; a self session → 409 `invalid_transition` `details.reason:'not_switched'`; a guardian row that vanished → 401 `unauthorized` and the session is deleted; a disabled guardian → 403 `account_disabled`), then one transaction replaces the child session on this device by a fresh guardian session that already carries the gate stamp (the guardian's `last_login_at` refreshed). **106 `POST /api/auth/switch/code`** (`U`, a switched child session) — `{channel: CodeChannel}` → `202 CodeSendResponse`: a `reauth` code for 105 to the guardian's live phone (`'phone'`; none → 400 `validation_error`, `details.fields.channel` 「家长账号尚未绑定手机号」; 409 `sms_unconfigured`) or verified e-mail (`'email'`; none → 400 「家长账号尚未验证邮箱」; 409 `smtp_unconfigured`) — template 100005 / the 身份确认 mail, the §1 send throttles, no captcha (a session exists). 409 `not_switched` on a self session; the disabled / vanished guardian cases of 105.

Never `login:ip`, never the lockout; `setup_required` cannot occur (codes exist only with users). The session is a self session (`actor_user_id NULL`): no 「切回家长」, the restriction list applies.
**108 `POST /api/account/guardian/code`** (`U`, not a child) — `{target: string}` (the guardian's phone) → `202 CodeSendResponse`: 「这是孩子的账号」 — a claim code to the guardian's phone, a `family_codes` row of kind `claim_guardian` bound to (me, the number) — one live claim per account, an older unused one is voided whatever its number —, sent like a `bind_phone` code (template 100004; the §1 send throttles, the SMS caps, 409 `sms_unconfigured`; no captcha — a session exists). **109 `POST /api/account/guardian`** (`U`, not a child) — `{target: string, code: string (6 digits), age_band: 'u14' | '14plus'}` → `200 {user}` (me, now `is_child: true`): attach my account to the guardian who owns that phone. ### 3.3 Third-party sign-in (slice 2-A)

Design: docs/AUTH_SIGNUP_DESIGN.md §5.3 (微信、QQ、Apple — 第二步), §5.2 (the account model: `identities` rows with `provider ∈ {wechat_mini, qq, apple}` — the 0018 CHECK list already allows them — and `subject` = the mini-program openid / the QQ openid / the Apple `sub`, pseudonymous ids shown to nobody), §5.6 invariants; owner decisions D4 / D6 / D8; migration 0020 (`wechat_tickets`). Everything ships **dark**: without `WD_WECHAT_*` / `WD_QQ_*` / `WD_APPLE_*` (DEPLOY §4) the three `ServerFlags` / health flags are false, the SPA shows no 「其他方式登录」 row and 112–116 / 118–121 answer 409 `provider_unconfigured` (117 too when the provider is off AND nothing is bound). The rules shared by the three providers live in `wd/third_party.py` (`third_party_login_or_bind`, used by 116, 119 and 121 so the providers cannot drift): an identity's account signs in (an admin → 403 `password_required`, a disabled account → 403 `account_disabled`); an unknown identity creates a learner account like endpoint 81 (403 `setup_required` while `users` is empty; `closed` → 403 `registration_closed`; `invite` → the code given at the start must consume, else 403 `invalid_invite`; `open` / `verified` consume a given code; placeholder username, `password_set_at NULL` — `User.has_password` false, `needs_profile` true, and `/welcome` step 0 requires a password for a third-party-only account, the rule of 89); a bind attaches the identity to the session's account (409 `identity_taken` when another live account holds it or the account already has an identity of that provider; a child → 403 `guardian_required`). `User.providers` lists the bound providers; 117 unbinds one after the endpoint-7 re-authentication while at least one other way in remains (409 `last_login_method`). Every POST carries the CSRF header except 121, CSRF-exempt by path (§1) — its HMAC-signed `state` together with the `wd_oauth` browser cookie that 122 checks is its defence (only the browser that started the flow can finish it); the QQ / Apple results cross from the callback's origin (possibly the filed relay domain, DEPLOY §7.1) to the SPA's through the one-time grant of 122 (60 s, single use, `kv`). The dev-only fakes (`WD_AUTH_FAKE_PROVIDERS=1`, needs `WD_DEV=1`) replace the providers with deterministic doubles and add the consent pages `GET /api/auth/fake/qq?state=` / `GET /api/auth/fake/apple?state=&nonce=` (not part of the catalogue; never on a production instance).

**112 `POST /api/auth/wechat/ticket`** — `WechatTicketRequest {kind: 'login' | 'bind', invite_code?: string}` → `201 WechatTicket {ticket: string (26 base32 chars), pairing_code: string (6 digits), expires_in_s: 180, qr_url: "/api/auth/wechat/ticket/<ticket>/qr"}` + `Set-Cookie wd_wxt` (§1: HttpOnly, SameSite=Lax, `Secure` like the session cookie, `Path=/api/auth/wechat/ticket`, Max-Age 180 — the poll secret of this ticket). Order: `wx_ticket:ip:<ip>:m` 30/min and `wx_ticket:ip:<ip>:h` 300/h (429; §1 — sized for a classroom behind one NAT) → WeChat off (`app.state.wechat` is None: no `WD_WECHAT_*`, no dev fakes) → 409 `provider_unconfigured` → `kind='bind'` needs a session (401; a child → 403 `guardian_required`, `deps.require_not_child`; `bind_user_id` = the caller, fixed at creation) while `kind='login'` ignores a session (the SPA never sends one) → a given `invite_code` is checked read-only (`security.invite_valid`: uses left, not expired; else 403 `invalid_invite`) whatever the registration mode and stored on the row for the confirmation to consume (116); a login ticket in `invite` mode may come without a code (an existing binding signs in; a NEW account then fails at 116 with `invalid_invite`), and `closed` mode still issues login tickets (the confirmation refuses a NEW account with `registration_closed`). The row (`wechat_tickets`, migration 0020) stores `ticket_hash = sha256(ticket)`, `poll_hash = sha256(secret)`, `pair_hash = HMAC-SHA256(WD_SECRET_KEY, 'pair:' + code)` — the pairing code is drawn inside the write lock and regenerated while a live (pending / scanned, unexpired) ticket holds the same hash; the hash stays on the row for its whole life (116 must find a finished ticket by its code), so a finished ticket's code may be re-drawn by a live one —, `web_ip` = the client ip and `web_ua` = the User-Agent cut to 200 chars (both shown to the scanner masked / summarised, 115), `expires_at` = now + 180 s. Log `wx_ticket_created` (kind, ticket id, user id for a bind) — never the ticket, the code or the cookie.

( ) / & % $ @` — not starting with a hyphen (`-ish` is 400; `"Hello," she said.` and `(informal) hi` are fine); anything else is 400 `validation_error` (`details.fields.text`); an `accent` outside `en-US` (the default) / `en-GB` / `zh-CN` is 400 (`details.fields.accent`). **`accent=zh-CN`** (磨耳朵, endpoint 123: the Chinese gloss and the translated sentence — the learner's own accent setting, `Settings.accent`, keeps its two English values) selects the Chinese voice and its own text rule: whitespace-collapsed, 1–300 chars with **at least one Han character**, made of Han characters, the punctuation of a Chinese sentence — `， 。 ！ ？ ； ： 、 （ ） 《 》 「 」 『 』 【 】 … — ～ · “ ” ‘ ’` —, six symbols of a quantity the Chinese voice reads as the words they stand for — `℃ ° ％ ￥ ¥ 〇` (「30℃」 is spoken 「30摄氏度」, 「￥20」 「20元」; none of them counts as the Han character, and `+` `=` `~`, which the voice drops, stay refused) — and whatever the English rule allows (a translation carries `Tom`, `GDP`, digits); anything else is 400 (`details.fields.text`: 「1–300 个字符，需含汉字」) — an all-Latin text belongs to an English accent, and Chinese text under an English accent stays 400. Only `say` speaks Chinese so far: with `WD_AUDIO_SAY_VOICE_ZH` (a Chinese voice `say` lists, no Eloquence one — anything else is refused, not spoken) or the best installed zh_CN voice (DEPLOY §4), never with an English voice — and an English accent never gets the Chinese one. Without a Chinese voice (a Mac that has none; `youdao` / `bailian`) the answer is 503 `{reason: "failed"}`, under `cache` `{reason: "missing"}` — both before any budget is spent; `ServerFlags.audio_zh` tells the client beforehand — optimistically in the first seconds after a start, while the voice is not resolved yet (§9.1): the request then resolves it itself, as an English one does, and answers 503 `failed` if there is none. A Chinese clip has the same key (`accent` = `zh-CN`, the Chinese voice), the same headers, and its misses count against the same 60 per minute. Session cookie required (any logged-in user — the 推荐词 of the welcome screening speak too). → `200` `audio/mp4` (`say`, and `cache` — the mirrored `say` clips: AAC, ≈ 8 KB per word) or `audio/mpeg` (`youdao`; `bailian` — mp3 24 kHz), `Cache-Control: private, max-age=604800` (a clip changes only when the operator switches provider or voice — which changes `ServerFlags.audio_key`, so the client's URL changes too; the `v` query parameter it appends is accepted and ignored), `Accept-Ranges: bytes` (a `Range` request gets 206 — the client plays the URL in an `<audio>` element), `X-Content-Type-Options: nosniff`; 503 `audio_unavailable` `{reason: "off" | "busy" | "failed" | "missing"}` (§1.1 — `off` means the client should stop asking for this session, `missing` that the read-only `cache` provider lacks this one clip); 429 `rate_limited` when one user causes more than 60 cache misses in a minute (hits are free; under `cache` a miss is `missing` at once and costs nothing). The cache is bounded by `WD_AUDIO_CACHE_MB` (DEPLOY §4; the least recently played clips go first). Served under `/media/` like 52–53 because every `/api/*` answer carries `Cache-Control: no-store`. The browser plays the clip only when it lists no English voice (or the shell's TTS plugin rejected — no engine, no English voice); `ServerFlags.audio` tells it whether to try, and it fetches the URL itself only to learn why a clip would not play (FRONTEND §6.4). 磨耳朵 (123) is the one caller that asks the server **first**: its player needs to know when a segment has ended and plays one clip after another in a single `<audio>` element, falling back to the device's own voice only for a segment the server cannot give (FRONTEND §6.4 `audio/utter.ts`; docs/LISTEN_MODE_DESIGN.md §6.1).

### 9.1 Field notes

* `ServerFlags.audio` = `WD_AUDIO_PROVIDER` resolves to a provider (`say` / `youdao` / `bailian` / `cache`), i.e. endpoint 76 can answer; the client consults it before asking for a clip and treats a later 503 `{reason:"off"}` the same way. `ServerFlags.audio_key` = the first 8 hex chars of sha256 over the provider and, for `say`, `WD_AUDIO_SAY_VOICE`, the resolved voice per accent and then the Chinese voice — its name, or the empty string once it is settled that the Mac has none (newline-joined; `youdao`: the provider alone; `cache`: the two voices of `WD_AUDIO_CACHE_VOICES`, so a changed pair is a new URL too; `bailian`: `WD_BAILIAN_TTS_MODEL` and the two voices of `WD_BAILIAN_TTS_VOICES`, so a switched model or voice is a new URL), empty without a provider; a voice the startup warm-up has not resolved yet reads as a placeholder unique to that process, so the first `/me` after a start may carry another key than the next — two browser-cache entries for a clip, nothing worse.
* `ServerFlags.audio_zh` = endpoint 76 answers `accent=zh-CN`: the provider is `say` **and** its Chinese voice is resolved to a name (`WD_AUDIO_SAY_VOICE_ZH`, else the best installed zh_CN voice — `wd.audio.speaks_zh`) **or is not resolved yet**. It never blocks `/me` and never runs `say`: for the first seconds after a start, until the warm-up (or a first Chinese request) has resolved the voice, it is **optimistic** — `true`, unless the `say -v '?'` listing the process already holds has nothing to resolve (no zh_CN voice but Eloquence ones, or an override that is not a listed Chinese voice). A client reads `/me` once per page load and keeps the flag, and a device without a voice of its own (the HarmonyOS tablet) would have no Chinese for that whole session after a `false`; the price is paid by a Mac without a Chinese voice, where a page loaded in that window asks 76 once, gets 503 `failed` (the request resolves the voice itself, like an English one) and stops asking for Chinese. Once resolved the flag is the settled answer; a Mac without a Chinese voice is then `false`, and every other provider (`youdao`, `bailian`, `cache` — no Chinese clips yet) is `false` from the start. While false, 磨耳朵 (123) reads `gloss_zh` / `sentence_zh` with the device's own Chinese voice when it has one and leaves them out otherwise (a device that cannot tell beforehand — the app shell — tries the first one once, then leaves the rest out without re-reading the word); `audio: true, audio_zh: false` is therefore a normal state, not an error.
* `ListenItem.gloss_zh` (123) is rule-derived from `meaning_zh` (`services/listen.speakable_gloss`; no model call, so the pre-generated library needs no regeneration): bracketed asides are dropped (`（…）` `(…)` `[…]` `【…】` `<…>`, innermost first; a round pair may mix widths — `（…)`, `(…）`; an aside cut off by the length limit of `meaning_zh` goes up to the end of its sense), the text is cut into senses at `；` `;`, line breaks, `，` `,` `、`, a slash (`/` `／` — the Chinese voice of `say` reads one out as 「斜杠」) and before the next part-of-speech group, each sense loses its leading part-of-speech labels (`n.` `v.` `a.` and any lower-case abbreviation of two to seven letters with its dot: `vt.` `vi.` `adj.` `adv.` `ad.` `prep.` `conj.` `pron.` `num.` `int.` `interj.` `art.` `aux.` `det.` `abbr.` `pl.`, the dictionary's `na.` `un.` `pref.` `suf.`, and whatever else a model writes in that style — `phr.` `excl.`; runs like `adv./prep.` or `vt.vi.` included; never the shorthand `sb.` / `sth.`, a capitalised abbreviation or `a.m.`) and whatever is not a letter, digit or Han character at its edges, senses the Chinese text rule of 76 refuses (no Han character, a stray symbol) and repeats are dropped, and the first **two** are joined by 「，」; a result longer than 40 characters keeps the first sense alone (cut to 40 if need be); `null` when nothing speakable is left. `v. 分享；共用 n. 一份；股份` → `分享，共用` · `adv./prep. 在船(飞机、车)上;上船(车、飞机)` → `在船上，上船` · `国内生产总值（gross domestic product 的缩写）` → `国内生产总值` · `n. 能力, 才干` → `能力，才干` · `pron. 他/她/它的` → `他，她` · `phr. 照顾；照料` → `照顾，照料`. `ListenItem.done` = `push_items.result IS NOT NULL` (the `TodayCounts.done` predicate: an item in the 10-minute step is not done); `ListenItem.kind` is typed `ItemKind` but is never `screen`.
* `User.needs_profile` = `users.age_band IS NULL AND username` matches the placeholder pattern `^u_[a-z2-7]{8}$` — an account endpoint 81 created that has not completed endpoint 89 yet; the SPA shows the 「首次设置」 step (nickname, age band, optional username and password) before step 1 of `/welcome`, and `GET /api/auth/me` keeps reporting it until 89 succeeds. `User.has_password` = `users.password_set_at IS NOT NULL` (every pre-0018 account is backfilled `true`); while false, endpoints 7 / 8 / 87 take a `reauth` code (85) instead of the password and the login page cannot sign the account in with a password.
* `User.phone_masked` = the account's live phone identity (`identities.provider='phone' AND disputed_at IS NULL`) as `138****8000` — the first 3 and last 4 digits of the national number, never the full E.164 string (the server never returns, logs or stores a phone number unmasked anywhere but `identities.subject`); `null` without a binding. `DisputedIdentity.subject_masked` uses the same mask.
* `User.account_kind` (`users.account_kind`, slice 1-B) is `'guardian'` for an account that creates and manages child accounts (endpoints 94–105; 我的孩子 in the SPA) — chosen at `/welcome` step 0 (89), by the legacy prompt (110) or by a claim (109, which turns the phone's owner into a guardian); every other account is `'learner'`. `User.is_child` = `users.guardian_user_id IS NOT NULL`: the child restriction list of §1 applies (403 `guardian_required` on 6–10, 85–89, 104, 108–111 whatever the session — a self session signed in by a login code, a simple username + password or a switch); a child never satisfies `G`; the guardian renames, re-passwords, signs out, sets free or deletes the child through 94–101.
* `User.needs_profile_prompt` = `age_band IS NULL AND NOT needs_profile AND guardian_user_id IS NULL AND (profile_prompted_at IS NULL OR profile_prompted_at <= now − 30 days)` — an account with a real username (so not a `needs_profile` placeholder account; pre-1-A accounts and password registrations of endpoint 1 alike, admins included) that has not declared its kind / age band yet; the SPA shows 「补充信息」 once per sitting, 110 (declare) and 89 clear it, 111 (skip) snoozes it for 30 days by stamping `users.profile_prompted_at`.
* `SessionInfo` (`GET /api/auth/me`, slice 1-B): `guardian` = `{id, display_name}` of `sessions.actor_user_id` when this device was switched into a child account (endpoint 104; the SPA shows 「切回家长」 → 105), else `null`; `gate_until` = `sessions.guardian_gate_at + 600 s` as ISO while the caller is a guardian in its own session and the stamp is still valid (endpoints 102 / 105 write it; `G+gate` endpoints check it), else `null` — a passed gate lasts 10 minutes per session, never per request.
* `User.providers` (slice 2-A) = the account's live identities whose provider is `wechat_mini` / `qq` / `apple` (`identities.disputed_at IS NULL`), as a sorted list of `ThirdPartyProvider` values — never the openid / `sub` itself; `[]` without one. The settings page shows one row per provider the server offers (`ServerFlags.wechat_enabled` / `qq_enabled` / `apple_enabled`) and for a bound provider even when its flag is off, so it can still be unbound (117). A third-party-only account (`providers.length > 0 && !phone_masked && !(email && email_verified) && !has_password`) must set a password at `/welcome` step 0 (89).
* `ServerFlags.wechat_enabled` / `qq_enabled` / `apple_enabled` (and the same names in `GET /api/health`, slice 2-A) = `Settings.<provider>_configured or auth_fake_providers` — the provider's variables are set (DEPLOY §4) or the dev fakes are on; the login page renders the 「其他方式登录」 row from them (hidden entirely when all three are false) and `GET /api/auth/wechat/ticket` (112) / the `start` endpoints (118, 120) answer 409 `provider_unconfigured` while the flag is false.
* `WechatTicketStatus.status` (113): `pending` (no scan yet) → `scanned` (the mini program resolved the ticket; 「已扫码，请在微信里确认」) → `confirmed` (the only state that carries `user` / `settings` / `created`; a login ticket's response also sets the session cookie) or `cancelled` (reported once); `expired` is computed from `expires_at` (180 s; the SPA offers 刷新 = a new ticket). * `dance` (`StudyItem.word`, `WordDetail.word`) = the 「单词之舞」 `DanceSpec` that `wd.dance.spec_for_word` builds while the word is serialised: the rule spec `backend/wd/dance.py` derives from `display` + `phonetic` (`source: 'rule'`, `semantic: null`; docs/WORD_DANCE_DESIGN.md §4.1–4.2), overlaid — when the word has a stored annotation (the `word_dances` row `words.active_dance_id` points at, written by `generate_dance`, CLAUDE_INTEGRATION §6.8; `source: 'claude'`) — with that row's `semantic` primitive and, only where the model corrected the chunks or stress it was suggested (`word_dances.corrected = 1`, migration 0017), with its chunks and stress; a stored row the model merely confirmed therefore follows every later improvement of the rules (since 2026-11-09 P3b: wor·ker → work·er without another call), the marks are always the rules', and a stored row of a word without a rule spec serves as it is. The rules: `letters` is the display form cut into syllable chunks (`"".join(letters) == display`; the ECDICT transcription gives the syllable count — vowel nuclei plus syllabic consonants, an iə / uə read as two syllables when the spelling has i / u plus another vowel letter (se·ri·ous, Jan·u·a·ry), a schwa the transcription elides read back from the spelling (in·ter·est·ing) — and the vowel letters give the cuts: a stressed short vowel keeps the single consonant (vis·it), long vowels / ə / unstressed vowels leave it to the next chunk (pa·per, a·bout), r-coloured vowels and an unstressed er keep their r (or·ange, dif·fer·ent), digraphs and tch stay whole (tea·cher, moth·er, kitch·en), doubled consonants and s-clusters split (rab·bit, bas·ket), the ti / ci / si of /ʃ/ open their suffix (na·tion·al, spe·cial), -le / -ing / -ieth endings and the magic e are special-cased (ta·ble, meet·ing, twen·ti·eth, cre·ate); since P3b a derived -er word is cut after its stem — work·er, farm·er, sell·er, low·er, lis·ten·er — when `wd.dance.er_evidence` can prove the derivation from the two bank rows: the stem is a public word spelled exactly `display[:-2]` (lower-case letters only), the transcriptions compose (stem + /ə/, /ər/ or /ɚ/ — num·ber, lon·ger fail), the stem is a content word (pos n / v / j — with·er, quar·ter fail) and ECDICT's exchange marks the word as the stem's comparative, or (for a noun, or an adjective from an adjective — for·mer, ten·der, in·ner fail) the English definition names the stem, the two Chinese glosses share a two-character word or the gloss names the stem; `backend/tests/fixtures/dance_er_splits.json` lists the 65 seed words it applies to — cor·ner, cen·ter, but·ter, mas·ter, por·ter keep their cut), `stress` the index of the chunk carrying the primary stress — with ECDICT's old double marks (`'fif'tiːn`) the last one, the 13–19 numerals always on -teen, an unmarked polysyllable (`ʌŋkl`) on its first non-schwa chunk —, `marks.double` the index pairs of doubled letters, `marks.silent` the indexes of letters the rules know to be silent (kn- wr- wh-/h- tw- -mb -mn -igh-/-ough, l in walk/half/would, t in listen/often/castle, w in answer, the magic e). Two ECDICT quirks are overridden by word (`august` = the month, `email` = ˈiːmeɪl). When the spelling and the transcription still disagree on the syllable count the word stays ONE chunk (`stress` 0 for a monosyllable, else `null`); a display that is not plain letters (phrases, `Mr.`, `o'clock`, `ping-pong`) or has no phonetic gets `null`. Reviewed against dictionary syllabification on all 600 小学 words (docs/WORD_DANCE_DESIGN.md §10); what the rules cannot know (heteronyms such as record, a suffix cut the bank cannot prove) is left to the `source: 'claude'` specs — and only their corrections, see above.
