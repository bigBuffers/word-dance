## 3. Does each plan break the live-ledger loop without pausing the healthy fallback?

All three: yes, by construction — `claude.paused_until` becomes the primary's pause, the fallback gets `ai.fallback.paused_until`, the admin pause moves to a global `ai.paused_until`, the user gates read an "any provider available" helper, the same claimed group is retried at once, and fail-back is probe-driven (`maybe_probe` from `housekeeping`, which bypasses the pause because `run_claude(call_id=None)` inserts its own row). Replaying `ai_calls` 33–47: one `auth` row instead of 15, learners never see `503 ai_disabled` while the free model answers.

Differences that matter:
* **D1** reaches the fallback through the same binary, so every outage class that is *CLI-side* (managed-settings fetch, `forceLoginMethod`, the "Session cost is not a number … refusing to continue under --max-budget-usd" refusal, a CLI release changing the request shape) can take the fallback down with the primary. D1 names the kill criterion (T0) honestly, but it is a correlated-failure design.
* **D2** and **D3** have no correlated failure: the fallback path has no `claude` binary, no `~/.claude`, no anthropic.com traffic, explicit `thinking:disabled`, `trust_env=False` so the Mac's privoxy tunnel never leaks into the fallback.
* **D3** adds `select()` gating on `kv.ai.<p>.available != '0'`, the single-writer rule and a per-slot semaphore in the MVP — the most careful machine of the three; D2 gets the same with `choose()`'s `available != '0'` check but leaves the semaphore to the complete cut (safe only while `WD_AI_CONCURRENCY=1`).

## 4. Do budgets, hourly caps and concurrency stay meaningful?

* Free fallback → `cost_usd=0`, `reserved_usd=0` (all three) → the USD caps cannot bind and prewarm's `$`-stop never fires (`prewarm.py:144-151`): all three keep the hourly cap as the volume guard (D1 per-provider 60/40, D2 global 60 + slot 60, D3 per-slot 60). D2 additionally excludes prewarm (priority ≥ 90) from the free slot by default — the right default for a 912-call seed on a 1-concurrency tier.
* Paid step-up: D2/D3 price `usage` × a CNY table ÷ `WD_CNY_PER_USD` into `cost_usd`, so the owner's daily/monthly caps keep one unit; D2 adds an `ai_budget_overrun` event because HTTP has no `--max-budget-usd`; D3 adds tiered/peak pricing. D1 prices from the CLI envelope's `usage` for an unknown model — never observed in the fact base (open question in every slice) — and admits thinking cannot be switched off from the CLI, so the ¥15/month figure for qwen3.7-flash is not guaranteed on D1.
* Concurrency: only D3 enforces per-provider concurrency in the MVP; D1/D2 rely on `WD_AI_CONCURRENCY=1` until their complete cuts. With one worker thread (the owner's setting) all three are safe; with 2–3 threads D1/D2 can send 2–3 simultaneous requests to a 1-concurrency free tier and count the resulting 1302s as an overload streak.

## 6. Blind spots none of the plans covers

1. **`routers/words.py:326`** — right after the gate the content-request route calls `budget.can_spend(conn, "content", 1, CONTENT_REQUEST_PRIORITY, now)` **without a provider**; unless `can_spend`'s default provider resolves to the *active* slot, a learner's 生成例句 request during failover answers `budget_exhausted {resumes_at: <Claude pause>}` although the fallback is healthy. All three plans list `can_spend(…, provider)` but none names this call.
2. **`probe.check` side effects on every failed recovery probe** (`probe.py:140-149`): `claude.available=0` plus a `system_events('claude_unavailable')` row per tick → 16–18 extra events over an 8-hour outage in a feed capped at 100 (`EVENTS_24H_LIMIT`), and two 18-second CLI spawns on the single worker thread per tick. Nobody dedupes it or passes a "recovery" flag.
3. **`queue.STALE_LOCK_MINUTES=15` vs the retry chain**: primary attempt (content 180 s / consolidate 240 s) + immediate fallback retry (×1.5 → 270/360 s) stays under 15 min, but D3's semaphore wait "≤ the call timeout" can push a still-claimed consolidate group to 240+360+360 s = 16 min → `requeue_stale` requeues jobs that are still being processed (double `queue.finish`). No plan mentions `requeue_stale`.
4. **No alerting.** The app already has `send_email` / `send_webhook` IO job types (`queue.py:34`, `registry.py:36-37`); none of the plans enqueues a notification on `ai_failover`, `ai_fallback_auth`/balance or "both down" for a part-time owner who may not open the admin page for days.
5. **Restart / restore reconciliation.** None says what happens to `ai.active_provider`, `ai.failover.next_probe_at` and the provider pauses on service restart (a restart during an outage should probe immediately, not wait up to 30 min) or after `wd restore` of an older backup (stale sticky state resurrected).
6. **Concurrent switch idempotence.** With `WD_AI_CONCURRENCY` 2–3, two threads failing on Claude in the same second both run `record_failure` → two `ai_failover` events and two simultaneous immediate retries on a 1-concurrency free tier; only D3's `BEGIN IMMEDIATE` single-writer hints at it, none specifies compare-and-set on `ai.active_provider`.
7. **System-path managed settings** (`/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`) are not bypassed by `CLAUDE_CONFIG_DIR`; absent on this Mac today, unchecked on the VPS — relevant to D1's kill criterion only.
8. **Admin tiles mix providers**: `today_usd`, `calls_today`, `avg_cost_per_word_7d` (`budget.spend_summary`) count $0 fallback calls with Claude calls; D2 filters the average, nobody filters the tiles until the complete cut — the owner cannot see "fallback volume" vs "Claude spend" on the MVP.
9. **Key hygiene after a leak**: no plan says how a leaked fallback key is noticed (vendor console usage vs `ai_calls` by provider) or rotated without a restart; D1's 0600 file and D2's `_API_KEY_FILE` help, but rotation and the Zhipu console's usage page are not in any runbook.
