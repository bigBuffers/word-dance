## F4 — The Capacitor bridge is injected into `server.url` pages on both platforms

**Verdict: corrected** (conclusion true; the Android mechanism and its side effects are misdescribed).

iOS — confirmed verbatim: `capacitor-ios-8.6.0/package/Capacitor/Capacitor/JSExport.swift:18-21` `window.Capacitor = { DEBUG: …, isLoggingEnabled: …, Plugins: {} }; window.WEBVIEW_SERVER_URL = '…'` as `WKUserScript(source:, injectionTime: .atDocumentStart, forMainFrameOnly: true)`; `:107` plugin headers (`a.PluginHeaders … h.push(…)`) same way; `:212` `injectFile` (native-bridge.js) same way. `grep -n WKUserScript` → exactly lines 20, 107, 212. User scripts run in every main-frame document the WKWebView loads, regardless of origin.

Android — what the digest cites is the fallback path:
- `capacitor-android-8.6.0/…/Bridge.java:265-274`:
  ```java
  JSInjector injector = getJSInjector();
  if (WebViewFeature.isFeatureSupported(WebViewFeature.DOCUMENT_START_SCRIPT)) {
      String allowedOrigin = Uri.parse(appUrl).buildUpon().path(null).fragment(null).clearQuery().build().toString();
      try {
          WebViewCompat.addDocumentStartJavaScript(webView, injector.getScriptString(), Collections.singleton(allowedOrigin));
          injector = null;
      } catch (IllegalArgumentException ex) { Logger.warn("Invalid url, using fallback"); }
  }
  localServer = new WebViewLocalServer(context, this, injector, authorities, html5mode);
  ```
  `appUrl` is `server.url` when set (`Bridge.java:626-644`), so the whole bridge (global JS + native-bridge.js + plugin headers, `getJSInjector()` :1023-1040) is registered as a document-start script for the origin `https://<domain>` only, and the proxy gets `jsInjector == null`.
- `WebViewLocalServer.java:515-516` `handleProxyRequest(...) { if (jsInjector != null) { … fetch HTML via HttpURLConnection, forward headers + CookieManager cookies, inline <script> … } return null; }` — with `jsInjector == null` it returns `null`, i.e. the WebView loads the remote document itself (backend response headers, CSP and HSTS intact; no 30 s HttpURLConnection re-fetch). `:246-252` (`isMainUrl` false / `isAllowedUrl` true when `server.url` is set) and `:656-723` (handlers registered for every authority incl. the `server.url` authority, `Bridge.java:636-638`) are as the digest says, but they only lead to the inline-injection path when the feature is absent.
- `JSInjector.java:92-104` (insert after `<head>`) confirmed — fallback only.
- `Bridge.java:236-249` `setAllowedOriginRules()` adds `getServerUrl()`; `MessageHandler.java:36-38` uses them for `WebViewCompat.addWebMessageListener(webView, "androidBridge", …)` and falls back to `addJavascriptInterface` on exception.
- androidx semantics (fetched `WebViewCompat.java`, javadoc of `addDocumentStartJavaScript`): "executed in any frame whose origin matches `allowedOriginRules` when the document begins to load … will run before any of the page's JavaScript code … The script will only run in frames which begin loading after the call returns". `WebViewFeature.java:522-526` "This feature covers WebViewCompat#addDocumentStartJavaScript".
- When did WebView get it: GitHub commit search on chromium/chromium — "[JJI] Implement addDocumentStartJavascript" 2020-04-27 (#763015), "[JJI] Expose addDocumentStartJavascript related APIs" 2021-03-24 (#866192) → WebView ≈ M91 (June 2021) by commit position (milestone mapping inferred, not from a release note); androidx.webkit exposed it publicly in 1.9.0-alpha01 (2023-10-18, release notes) and the Capacitor template pins `androidxWebkitVersion = '1.14.0'`. With the digest's own `minWebViewVersion: 108` floor, every targeted device takes the document-start path; the proxy/inline path is effectively dead code for this project.

Corrections to the digest's implication paragraph: (1) "on Android the proxied document loses the backend's response headers (CSP/HSTS)" is false on every WebView ≥ ~91 — nothing is proxied; (2) new constraint: on Android the bridge exists **only for documents whose origin is exactly the `server.url` origin** (scheme+host+port); a redirect from `https://<domain>` to `https://www.<domain>` (or any other host) yields a page without `window.Capacitor` — and `launchIntent` (`Bridge.java:413-426`) would even hand that navigation to the system browser because host+scheme ≠ `appUrl`. On iOS the user scripts are injected into every main-frame document, so the two platforms differ here. `server.url` must therefore be the canonical, non-redirecting origin. (3) The injection is "exercised daily" by live-reload users — true for both paths.

## Omissions / new findings

1. **Android bridge is origin-scoped; `server.url` must be the final, non-redirecting origin.** `Bridge.java:265-274` registers the bridge with `WebViewCompat.addDocumentStartJavaScript(webView, script, {scheme://host[:port] of server.url})`; androidx javadoc: "executed in any frame whose origin matches allowedOriginRules". The `androidBridge` message listener uses the same rules (`Bridge.java:236-249`, `MessageHandler.java:36`). A `https://<domain>` → `https://www.<domain>` redirect (or a CDN/host rename) silently produces an app without `window.Capacitor` on Android, and `launchIntent` (`Bridge.java:413-426`) would open the redirected host in the system browser because host+scheme ≠ `appUrl`. iOS injects into every main-frame document, so the symptom is Android-only. Action: pin `server.url` to the canonical origin, add a device check "window.Capacitor.isNativePlatform() === true on Android" to step 4.
2. **Google's Android developer-verification rollout touches the APK-sideload channel.** developer.android.com/developer-verification (fetched today): "August 2026 Developer APIs, limited distribution accounts, and power user advanced flow launch. September 30, 2026 Protections begin for all users who install apps from participating stores in Brazil, Indonesia, Singapore, and Thailand on certified devices running Android 7+. 2027 and beyond Verification capability will be expanded globally for all apps on certified Android devices in 2027." · "Limited distribution accounts … students, teachers, and hobbyists can share apps with up to 20 devices without a government-issued ID or registration fee." · "advanced flow to ensure power users can sideload apps from unverified developers." For ≤10 friends a limited-distribution account (≤20 devices) is the matching path from 2027 on GMS-certified phones; whether mainland-market ROMs without GMS count as "certified devices" is not stated (unverified). The digest's F19/step 8 do not mention this.
3. **Notification-tap routing survives M1's network-loaded page.** Both plugin sides retain the `localNotificationActionPerformed` event until a listener is registered (`LocalNotificationsHandler.swift:98` `retainUntilConsumed: true`; `LocalNotificationsPlugin.kt:60` `notifyListeners(..., true)`), so the proposed `installNativeHandlers(navigate)` can be mounted after the SPA boots and still receive a cold-start tap. (Positive fact the design relies on without stating.)
4. **Android first-paint layout shift and the Capacitor-9 default.** `SystemBars.java:88-99` learns `viewport-fit=cover` only at `onPageCommitVisible` and then calls `requestApplyInsets()`, so on WebView ≥ 140 the remote page first renders padded and then jumps to edge-to-edge; `:116-120` reads `plugins.SystemBars.initialViewportFitValueHint` ("passing it here … can help prevent layout shifting") — set it to `'cover'` in `capacitor.config.ts`. `system-bars.md:29` additionally recommends `EdgeToEdge.enable(this)` in `BridgeActivity.onCreate` (automatic in Capacitor 9 where `insetsHandling` defaults to `native`). Neither is in the digest's config block.
5. **F2's Android `Origin` question (open question 2) is answered by the bridge source** — only GET/HEAD/OPTIONS/TRACE use the WebView interceptor (`native-bridge.js:484-510`, because of Chromium issue 40450316); mutations go native with page-supplied headers only (`:511-526`), and the backend never origin-checks safe methods (`deps.py:34,116`). If M2 is ever revisited, no CSRF change is needed on either platform; the remaining blockers are `<img>` auth and the absolute API base.
6. **Dark-mode parity and privacy manifest need no work (evidence the digest lacked).** Android template theme `AppTheme.NoActionBar` = `Theme.AppCompat.DayNight.NoActionBar` (`tpl-android/app/src/main/res/values/styles.xml:12`), and Android's WebView dark-theme doc ties `prefers-color-scheme` to the app theme for targetSdk ≥ 33, so the SPA's OS-scheme CSS follows the system in the app; the iOS template plist has no `UIUserInterfaceStyle` key. Capacitor's framework ships `Capacitor/Capacitor/PrivacyInfo.xcprivacy` (and `CapacitorCordova/.../PrivacyInfo.xcprivacy`), so a TestFlight upload has no missing-manifest issue from Capacitor itself; the app template has none and the shell's own code uses no required-reason API.
