## Omissions / new findings

1. **(material, already happening) The owner's Enterprise org enforces fail-closed server-managed settings, and the live DB shows 15 calls killed by it in 8 hours — all misfiled as "not logged in".** DB copy: `ai_calls` 33-47 (2026-11-02T18:43Z … 2026-11-03T02:26Z, kinds `consolidate` ×3 and `content` ×12, exit 1, claude 2.1.292) all carry `Your organization requires remote managed settings to load, but they could not be loaded. If the fetch fails, the CLI exits rather than proceeding without the policy. This setting self-perpetuates: once delivered from the server, it is also cached locally"; line 238: "When the fetch fails in any other way, or in any other kind of launch except a `claude auth` subcommand, the client exits with an error."; line 333: "Server-managed settings require a direct connection to `api.anthropic.com`"; line 254: the fetch "sends a `Cache-Control: no-cache` header"; line 171: fetched "at startup and polls for updates hourly". Consequences the digest misses: (a) with this login every `claude -p` spawn needs a live round-trip to `api.anthropic.com` before the model call, so a flaky tunnel/proxy or a VPS egress hiccup fails the call even though the credential is fine; (b) the classifier files it as `auth` (because of "auth login"), so one blip pauses all AI for 30 minutes and tells the admin to re-login, which is the wrong remedy; (c) `CLAUDE_CODE_OAUTH_TOKEN` and a Console API key of a *Console* organisation (line 342: a separate organisation from the claude.ai Enterprise org) would not carry this policy, an `apiKeyHelper` credential does not trigger the fetch at all (line 340) — a fact that bears directly on the deferred credential choice. Recommendation: treat the string as a distinct class (`policy_fetch`/network) with a short retry rather than the 30-min auth pause, and make the banner text credential-neutral.

2. **Subscription usage-limit messages are not recognised by the classifier.** errors.md lines 841-845 document `You've hit your session limit · resets 3:45pm`, `You've hit your weekly limit · resets Mon 12:00am`, `You've hit your Opus limit · resets 3:45pm`, `You've hit your Sonnet limit · resets 3:45pm` (line 852: "Usage counts against the session and weekly allowances at the same time. A single burst of heavy activity … can exhaust the weekly allowance before the session window resets"). Run through `parse_and_classify` today they come out as plain `error` (no "rate limit"/429/529 token), i.e. per-job backoff → bisect → dead instead of a pause until the reset. Relevant for as long as the service runs on a claude.ai login (Enterprise/Team/Pro/Max); an API key is governed by 429 (`Request rejected (429)`, errors.md 929), which the `overloaded` regex does catch. The exact `-p` wording of the limit message was not found in the docs (only the interactive form), so the regex extension should be generous (`hit your .* limit|usage limit`).

3. **2.1.318 exposes the stored login's expiry in machine-readable form** — CHANGELOG 2.1.318 line 8: "Added the date a stored claude.ai sign-in ends to `claude auth status` (`loginExpiresAt`) and to `claude -p` JSON results (`credential_expires_at`)". The runner parses only `result/subtype/is_error/usage/modelUsage/total_cost_usd/session_id/duration_ms` (runner.py:229-260) and would drop `credential_expires_at`, but the raw stdout is kept under `claude-logs/` (0600), so a VPS on 2.1.318+ can surface "login expires on …" in the admin page or a cron check without a new API call. The docs pages do not mention the fields yet (grep of headless/cli-reference/authentication/errors: none), only the CHANGELOG.

4. **Primary-source policy statement on claude.ai logins in products** (the owner has deferred the policy decision; recorded here only because it is the official sentence the decision will turn on): agent-sdk/overview.md line 45 (accessed 2026-11-04): "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Related: `claude setup-token` tokens "authenticate with your Claude subscription and require a Pro, Max, Ultra, Team, or Enterprise plan" (authentication.md 321); llm-gateway.md 48: with a gateway credential "the subscription's usage limits don't apply … That traffic is billed per token to whoever owns the credential".

5. **Installer details that change the VPS runbook slightly**: the sudo refusal is bypassable with `CLAUDE_INSTALL_ALLOW_SUDO=1` and does not apply to plain root (install.sh 13-36), so a root-provisioned VPS can silently end up with `/root/.local/bin/claude` and `/root/.claude` credentials — the digest's "run installer and login as the service user" rule is right but should say the installer will not stop you when you log in as root; the installer always fetches `latest` first and then runs `<binary> install <target>` (install.sh 148-149, 226), so pinning to `stable`/`2.1.311` still downloads the latest build; the apt `latest` channel already ships `2.1.318-1` while `stable` is at `2.1.311-1` (Release 2026-11-03), and the .deb is a 133.7 MB download for a 293.8 MB install (`Installed-Size: 286891` KiB).
