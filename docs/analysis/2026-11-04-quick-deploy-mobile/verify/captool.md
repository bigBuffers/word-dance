## F10 — `@capacitor/local-notifications` 8.3.1 scheduling semantics (corrected)

**Verdict: corrected.** Every statement in the claim is true as written, but two facts in the same files change the Android recommendation.

Confirmed:
- Registry: `latest = 8.3.1` (2026-08-19), `next = 9.0.0-alpha.2` (2026-07-15).
- iOS `ios/Sources/LocalNotificationsPlugin/LocalNotificationsPlugin.swift:518-568` `handleScheduledNotification`: `on` → `UNCalendarNotificationTrigger(dateMatching: dateComponents, repeats: true)` (line 555); `every` → `UNTimeIntervalNotificationTrigger(timeInterval: interval, repeats: true)` (line 565) with the interval from `getRepeatDateInterval` (lines 610-628: `"day"` → `DateInterval(start: now, end: now + count days)`), i.e. anchored to *now*; a past `at` returns a nil trigger ("deliver immediately"). `LocalNotificationsHandler.swift:14` `center.requestAuthorization(options: [.badge, .alert, .sound])`.
- Android `LocalNotificationManager.kt:350-378` `setExactIfPossible`: `useExact = isExactNotification && canScheduleExactAlarms`; exact → `setExactAndAllowWhileIdle(RTC_WAKEUP)` if `allowWhileIdle()` else `setExact(RTC)`; inexact → `setAndAllowWhileIdle(RTC_WAKEUP)` / `set(RTC)`; `every` → `setRepeating(RTC, now + interval, interval)` (line 334; `LocalNotificationSchedule.kt:69` `"day" -> count * DateUtils.DAY_IN_MILLIS`).
- `AndroidManifest.xml`: `LocalNotificationRestoreReceiver` (`directBootAware="true"`, actions `LOCKED_BOOT_COMPLETED`, `BOOT_COMPLETED`, `QUICKBOOT_POWERON`); `uses-permission` `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`. `LocalNotificationRestoreReceiver.kt` re-schedules every stored notification through `LocalNotificationManager.schedule(null, notifications)`.
- Docs https://capacitorjs.com/docs/apis/local-notifications (v8) and tarball README: "Starting on version 8.3.0 this requests the notification permission it needs"; `allowWhileIdle` "can only fire once per 9 minutes, per app"; Android 15 Private Space note; `checkExactNotificationSetting` / `changeExactNotificationSetting`.

Corrections:
1. **Re-arm path drops `allowWhileIdle` and the wake-up type.** An `on` schedule is a one-shot alarm plus `CRON_KEY`; after it fires, `TimedNotificationPublisher.kt:50-77` `rescheduleNotificationIfNeeded` re-arms it with `alarmManager.setExact(AlarmManager.RTC, trigger, pendingIntent)` (line 67) or `alarmManager.set(AlarmManager.RTC, trigger, pendingIntent)` (line 72) — never `*AllowWhileIdle`, never `RTC_WAKEUP`. Only the first occurrence (scheduled via `setExactIfPossible`) honours `allowWhileIdle: true`; from day 2 on, a 20:00 reminder on a dozing phone waits for the next wake-up. Mitigation: cancel + re-`schedule()` on every app launch/resume (cheap, idempotent), and/or `USE_EXACT_ALARM` for sideload.
2. **`schedule()` bounces the user to Settings on Android 12+ unless told not to.** `LocalNotificationsPlugin.kt:116-133`: when any notification has `isExactNotification` (default `true`, `LocalNotification.kt:43`) and `!canScheduleExactAlarms()`, `schedule()` calls `startActivityForResult(call, Intent(ACTION_REQUEST_SCHEDULE_EXACT_ALARM, "package:…"), "exactAlarmScheduleCallback")` before scheduling; README (`isExactNotification` row): "if the app isn't yet allowed to schedule exact alarms the system 'Alarms & reminders' settings screen is opened so the user can grant it — regardless of `isExactMandatory`. If the user still declines, the notification falls back to an inexact alarm … Set to `false` to schedule this notification as inexact outright, regardless of permission state." So the digest's "inexact fallback" is reached only after the Settings detour; for the no-permission variant pass `isExactNotification: false` explicitly. `isExactMandatory: true` turns the fallback into a rejection (`EXACT_ALARM_PERMISSION_REQUIRED`); a silent fallback is reported as `ScheduleResult.warning`.

## Omissions / new findings

1. **Critical CVE in the exact code path the shell relies on — pin Capacitor ≥ 8.5.1.** GHSA-rvm3-566m-v7fv / CVE-2026-103922, "Capacitor Android and iOS: remote content can be loaded at the app origin via the internal HTTP proxy path", published 2026-08-31, CVSS 9.3 (critical). Affected `@capacitor/android` and `@capacitor/ios` 6.0.0–6.2.1, 7.0.0–7.6.8, 8.0.0–8.3.4, 8.3.5–8.4.2, 8.5.0; patched 6.2.2, 7.6.9, 8.4.3, 8.5.1. "The WebView navigation guard validated only the host and scheme of a target URL, not its path"; a frame navigation to `/_capacitor_http_interceptor_` made native fetch an arbitrary URL and return it "at the app's own origin" with "access to localStorage, cookies, and every native capability the application exposes"; "the proxy handler was additionally served regardless of whether the CapacitorHttp plugin was enabled". Capacitor CHANGELOG 8.5.1 (2026-08-31): "block navigation to the internal HTTP proxy path"; the 8.6.0 sources carry the fix (`WebViewLocalServer.java:184-199`, `WebViewDelegationHandler.swift:77-80`, `Bridge.java:389-394`). A remote shell is the configuration where a malicious link in the WebView is most plausible, so the digest's "start on 8.6.x" is right for a reason it does not state; never fall back to 8.4.x/8.5.0 templates. Sources: https://github.com/advisories/GHSA-rvm3-566m-v7fv ; https://raw.githubusercontent.com/ionic-team/capacitor/8.6.0/CHANGELOG.md.
2. **Daily `on` reminders on Android lose `allowWhileIdle`/wake-up after the first fire** (`TimedNotificationPublisher.kt:64-72`, see F10 correction 1). Decision impact: a once-a-day exact reminder is only "exact while idle" on day one; re-scheduling from the app on every launch is the cheap fix.
3. **`schedule()` opens the "Alarms & reminders" Settings screen by itself on Android 12+** when exact alarms are not granted and `isExactNotification` is left at its default `true` (`LocalNotificationsPlugin.kt:126-133`; README). The digest's two options ("inexact, no extra permission" vs "exact with a one-time toggle") need `isExactNotification: false` for the first and `isExactMandatory` for a hard-fail variant of the second.
4. **WebView floor for the native injection path (digest's open question).** androidx `WebViewFeature.DOCUMENT_START_SCRIPT` was added in androidx.webkit 1.9.0; the WebView-side feature string `DOCUMENT_START_SCRIPT` is present in Chromium's `android_webview/support_library/java/src/org/chromium/support_lib_boundary/util/Features.java` (path `…/support_library/boundary_interfaces/src/…/util/Features.java`) from release tag 84.0.4147.135 (2020-07, line 181 `DOCUMENT_START_SCRIPT = "DOCUMENT_START_SCRIPT"`; absent at 79/81/83) and, re-versioned, at 86.0.4240.198 (line 184 `"DOCUMENT_START_SCRIPT:1"`) and on `main` (line 205, same `:1` string) — checked via chromium.googlesource.com, 2026-11-04; tag 85 returned 503 and was not checked. Because current androidx.webkit matches the versioned `:1` string, the effective floor for `isFeatureSupported(DOCUMENT_START_SCRIPT)` is Android System WebView ≈ 86 (October 2020), medium confidence (the androidx-side constant was not read). Capacitor's own floor is WebView 60 (`minWebViewVersion` default 60), so only WebViews 60–83 (2017–mid-2020 builds) would take the HTML-proxy fallback; current Xiaomi/Huawei/OPPO/vivo phones with an updatable WebView are on far newer builds. Huawei's own WebView (`minHuaweiWebViewVersion` 10) is unverified.
5. **The iOS shell still needs a local web directory even with `server.url`.** `CAPBridgeViewController.swift:172-174`: `guard FileManager.default.fileExists(atPath: bridge.config.appStartFileURL.path) else { fatalLoadError() }` runs before `appStartServerURL` is loaded; `appStartFileURL` is `webDir/index.html`. The shell repo therefore needs a placeholder `webDir` with an `index.html` (and `npx cap sync` must have copied it) or the app aborts at launch; Android similarly hosts `DEFAULT_WEB_ASSET_DIR` (`Bridge.java:276`). Not a blocker, but it is a one-line gotcha for a "remote-only" project.
6. **`addDocumentStartJavaScript` is origin-exact** (`Bridge.java:267`): a first-navigation redirect from `server.url` to another origin (apex→www, http→https) yields a page without the bridge. Set `server.url` to the canonical https origin the server actually serves. (Follows from F7; listed here because it is a silent failure mode.)
