# Reminders slice — how friends get the daily 今日词汇 reminder today (no APNs / FCM / Web Push)

Repo: /Users/sqin/word-dance @ 9ab13a5 · written 2026-11-04 · scope: delivery code facts, relay services, zero-code setups per phone platform, and the cost of the three "real push" alternatives. Web facts carry the access date 2026-11-04; live probes were run from the owner's Mac on its direct (non-proxy) mainland network and sent only the constant test string with throw-away keys (nothing was pushed to a real device, no money spent).

## Summary

- word-Dance already has two best-effort reminder channels wired into the scheduler: `send_email` and `send_webhook` with five POST formats (`generic`, `wecom`, `feishu`, `serverchan`, `bark`). Every channel fires once per user at that user's `push_time` in that user's `timezone`, carries the same digest (title + summary + first 10 words with phonetic/meaning/example + a `<WD_PUBLIC_URL>/today` link) and is skipped when the publish is more than 6 h late.
- Zero-code coverage of the four phone platforms is complete today: iPhone → Bark; any phone with WeChat (iPhone, GMS-less Android, HarmonyOS NEXT) → Server酱 Turbo (free tier 5 messages/day, enough for one digest); GMS-less Android with a real system notification → the Server酱³ app, which uses the vendor push channels (小米/华为/荣耀/vivo/OPPO/…/FCM) and accepts the backend's existing `serverchan` payload at a different URL; ntfy via the unchanged `generic` format plus ntfy's template query string (verified end-to-end against ntfy.sh); 企业微信/飞书 group bots for friends who already use those apps; e-mail once SMTP is configured.
- Two code defects matter for the Chinese group-bot formats: `safe_post` treats any 2xx as success and never reads the body, and both WeCom and Feishu answer HTTP 200 for a bogus key (verified live: `errcode 93000` / `code 19001`), so a broken 企业微信/飞书 URL shows 「测试成功」 and the daily job marks the batch `sent`. The WeCom `text` type also caps content at 2048 UTF-8 bytes and the real digest text measured 1982–2061 bytes, so a full 10-word batch is silently rejected (`errcode 45002`). Bark and Server酱 answer HTTP 400 for bad keys, so they are reported correctly.
- The live service has `WD_PUBLIC_URL` empty, so today every link would be the LAN guess `http://10.23.147.103:8000/today`; the public deployment must set `WD_PUBLIC_URL=https://<domain>` or all channels lose their deep link. The link opens the website in whichever browser the relay uses (Bark → Safari, Server酱 → WeChat's built-in browser); making it open a Capacitor app needs an AASA/assetlinks route and, on iOS, a paid Apple account.
- "Real push" without a relay costs real work: Capacitor local notifications need no backend change but need an app build (Xcode not installed; iOS distribution needs the $99/yr program; Android APK sideload is feasible, HarmonyOS NEXT cannot install APKs); Web Push is a ~6–10 person-day backend+frontend package (subscription table, VAPID, `send_webpush` job with a `jobs` table rebuild, pywebpush and five transitive dependencies, service worker/manifest) and only reaches iPhones that installed the site to the Home Screen from Safari plus GMS Android — it is dead on GMS-less mainland Android; APNs/FCM native is the prior 5–8 backend days plus a 3–5 week app route, and FCM is unusable on mainland phones.
- Recommendation: week 1 is configuration only (set `WD_PUBLIC_URL`, Bark for iPhones, Server酱 Turbo or Server酱³ for Android/HarmonyOS, hold off 企业微信/飞书 until the body-check fix); week 2 is a ~1 person-day hardening patch (parse `errcode`/`code`, cap/convert the WeCom text, keep the Server酱 title ≤ 32 chars, put the URL into the test message); the app/Web Push decision waits for a month of real usage.

## Findings

### F1 — The reminder pipeline: when, for whom, and what happens on failure (code facts)

- **Claim.** A reminder is produced only for users with `is_active=1`, `onboarding_state='done'`, `push_enabled=1` and a non-NULL `next_push_at`; the 60-s scheduler builds the batch from `max(next_push_at − WD_PREBUILD_HOURS(3), 00:00 local)` on, publishes exactly once at `next_push_at` (conditional UPDATE), enqueues `send_email`/`send_webhook` (dedupe `email:<id>`/`webhook:<id>`, priority 20) unless the publish is > 6 h late (then `email_status`/`webhook_status = 'skipped'`), and advances `next_push_at` with `compute_next_push` in the user's zone. After downtime the push is re-anchored to today's push instant when it is still ahead. Webhook transport/HTTP failures go through `queue.fail` — retry after 2 min, then 10 min, then `dead` on the third failure (`max_attempts=3`; the 60-min step is unreachable) with `webhook_status='failed'` and `delivery_error` truncated to 300 chars; SSRF rejections are final. Channel flags are re-read at send time (`channel_disabled` → `skipped`). The 发送测试 button is synchronous, limited to 1 per 10 min, and its message never carries a URL. No user-facing or admin DTO shows `webhook_status`/`email_status`/`delivery_error`; they are visible only in the DB and in `GET /api/admin/jobs`.
- **Evidence.** backend/wd/jobs/scheduler.py:49 (`STALE_DELIVERY = 6 h`), :83-92 (`build_from`), :102-110 (`due_users`), :124-138 (re-anchor), :145-157 (publish → `enqueue_deliveries(stale=…)` → advance), :478 (tick interval); backend/wd/services/batches.py:46 (`DELIVERY_PRIORITY = 20`), :365-373 (`publish_batch`), :1000-1032 (`enqueue_deliveries`), :1035-1047 (`push_now`); backend/wd/jobs/queue.py:31 (`BACKOFF_MINUTES = (2, 10, 60)`), :83 (`max_attempts=3`), :173-190 (`fail`); backend/wd/delivery/webhook.py:324-329 (already-sent / channel-disabled guards), :356-381 (handler: SSRF final, `WebhookError` → `queue.fail`), :342-353 (`send_test_webhook`, `url=None` at :351); backend/wd/routers/settings.py:136-145 + backend/wd/security.py:75 (`TEST_SEND_LIMIT, TEST_SEND_WINDOW_S = 1, 600`); backend/wd/config.py:82, :326 (`WD_PREBUILD_HOURS` default 3, range 0–23); docs/analysis/2026-11-03-public-launch/facts/delivery-push.md findings 4, 6, 7 (re-verified).
- **Implication.** A friend only needs to finish onboarding and keep 推送 on; the owner only needs a channel per friend. A relay that is down for > 12 min at push time costs that day's reminder (two retries), and a bad URL is invisible to the friend unless the owner looks at the DB or the admin job ledger.
- **Confidence.** high

### F2 — What the five formats send, with the real digest measured from the live snapshot

- **Claim.** `build_payload` sends: `generic` `{type:"daily_push", date, title, body, counts{review,new,screen,extra,deferred_reviews}, words:[{word,phonetic,meaning_zh}], url|null}`; `wecom` `{"msgtype":"text","text":{"content": title+"\n"+body}}`; `feishu` `{"msg_type":"text","content":{"text": title+"\n"+body}}`; `serverchan` `{"title","desp": body}`; `bark` `{"title","body"[,"url"]}` (the `url` key omitted when no public URL is known). `body` = summary line + up to 10 word lines + 「打开 word-Dance 开始学习：<url>」 or 「请在浏览器中打开 word-Dance」. Rendering the two published batches of the live snapshot with a public URL set: title 43–44 characters (`word-Dance 今日词汇 11月3日 · 复习 10 · 新词 3 · 推荐 15`), body 1,294–1,307 chars = 1,911–1,989 UTF-8 bytes, WeCom/Feishu `text` 1,982–2,061 bytes, Server酱 `desp`/Bark `body` 1,911–1,989 bytes, generic JSON 3,226–3,436 bytes. No Bark extras (`group`, `badge`, `level`, `isArchive`) and no Server酱 `short`/`channel` are sent. The POST is JSON with `Content-Type: application/json; charset=utf-8`, pinned to the resolved IP with `Host`/SNI set, 10 s timeout, no redirects, HTTP/1.1.
- **Evidence.** backend/wd/delivery/webhook.py:258-264 (`digest_body`), :267-303 (`build_payload`, `digest_payload`), :175-182 (`_client`), :224-254 (`safe_post`); backend/wd/delivery/email.py:37 (`DIGEST_WORDS = 10`), :131-157 (title, summary, word lines), :160-194 (`build_digest`); measurement script output saved at /private/tmp/claude-501/-Users-sqin-word-dance/729429d5-a7a1-4def-84e7-dc3ba571c437/scratchpad/quick/reminders/payload-sizes.json (run 2026-11-04 against the read-only copy live-copy.db, batches 2 and 3; cfg stub `public_url="https://wd.example.com"`).
- **Implication.** The sizes sit exactly at the WeCom text ceiling (F7) and near one-fifth of the APNs/ntfy 4 KB ceilings (F4, F9); a notification banner shows only the first lines, the rest is read in the relay app or on the detail page.
- **Confidence.** high

### F3 — `safe_post` ignores the response body; WeCom and Feishu report errors with HTTP 200 (verified live)

- **Claim.** `safe_post` returns success for any 2xx status and never parses the body. Posting the real test payload with throw-away keys from the Mac's direct network on 2026-11-04 gave: Bark → HTTP 400 `{"code":400,"message":"failed to get device token: …"}` (reported as `http_error`, correct); Server酱 Turbo → HTTP 400 `{"code":40001,"message":"[AUTH]错误的Key","scode":461}` (correct); **WeCom → HTTP 200 `{"errcode":93000,"errmsg":"invalid webhook url, …"}`** and **Feishu → HTTP 200 `{"code":19001,"msg":"param invalid: incoming webhook access token invalid"}`**, both of which `send_test_webhook` returned as `ok=True, reason=None` — the UI would show 「测试成功」 and the daily job would set `webhook_status='sent'`. WeCom's documented over-length error (`45002`, text > 2048 bytes) and Feishu's keyword/signature/rate errors (`19024`, `19021`, `9499`/`11232`) are delivered the same way.
- **Evidence.** backend/wd/delivery/webhook.py:252-254 (`if 200 <= status < 300: return PostResult(status, None, None)`), :332-336 (`sent` on `error is None`); live probe output (this session, 2026-11-04): `wecom (bogus key) → ok=True http=200`, `feishu (bogus hook) → ok=True http=200`, bodies quoted above; https://developer.work.weixin.qq.com/document/path/90313 (accessed 2026-11-04: `45002` "消息内容大小超过限制" — text ≤ 2048 bytes; `93000` "消息推送webhookurl不合法或者消息推送已经被移除出群"; errors are JSON `{errcode, errmsg}`); https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot (accessed 2026-11-04: success `{"code":0,"msg":"success"}`, `19024` "Key Words Not Found", `19021` sign/timestamp, `9499`, "All responses return HTTP 200 with error codes in the JSON body").
- **Implication.** Until a ~30-line body check lands (treat `errcode != 0` / `code != 0` as `WebhookError`), 企业微信 and 飞书 should be verified by the friend actually receiving the test, not by the green toast; retries also never happen for these errors.
- **Confidence.** high

From this network the host answered in 0.22 s (F3 probe).

### F9 — `generic` JSON already works with ntfy through ntfy's template mode (verified end-to-end); a native `ntfy` format would cost a `user_settings` rebuild

- **Claim.** ntfy expects either a raw text body on `POST /<topic>` or JSON `{topic, title, message, click, …}` on `POST /`, so the backend's `generic` payload posted to `https://ntfy.sh/<topic>` would arrive as a 3.2–3.4 KB JSON blob. ntfy's message templating (`?template=yes` / `?tpl=1`, Go-template `{{.field}}`, templates ≤ 32 KB) fixes that without any code: with the webhook URL `https://ntfy.sh/<topic>?template=yes&title={{.title}}&message={{.body}}&click=https://<domain>/today` the unchanged generic test payload produced, on 2026-11-04, a message whose poll-back read `title: "word-Dance 测试消息", message: "Webhook 配置成功，每日词汇将推送到这里。", click: "https://example.com/today"` (ntfy.sh answered HTTP 200 in 0.94 s). The query string survives `validate_url`/`pin` (verified: `query_kept=True`), and `click` can simply be the constant `/today` URL (templating of `click` is not documented). ntfy.sh limits: messages ≤ 4,096 bytes (longer ones become attachments; the templated message is the ≈ 2 KB body), title ≤ 1 KB, 60-request burst refilled 1 per 5 s and **250 messages per day per visitor IP** — the publishing IP is the VPS, so 250/day is shared by all friends (≤ 10 friends × 1–2/day is fine); repeated violations lead to temporary IP bans. Clients: iOS App Store app (delivery via APNs through ntfy.sh), Android Play flavour (FCM) or the F-Droid flavour where "all subscriptions use instant delivery by default" through a foreground service — the right build for GMS-less phones, at the price of a persistent notification and a battery-optimisation whitelist on MIUI/HyperOS/ColorOS-style ROMs; HarmonyOS NEXT has no ntfy app and cannot install APKs. A self-hosted ntfy on the VPS needs its own public https hostname (the SSRF guard refuses LAN names, verified `ntfy.home.lan` → `host_not_public`) and, for iOS, `upstream-base-url: https://ntfy.sh` so poll requests reach APNs (only the message id and a SHA-256 of the topic URL leave the server). Adding a first-class `ntfy` format to the backend is not a 5-line change: `user_settings.webhook_format` is a SQLite CHECK list, so it needs a `user_settings` table rebuild in migration 0010 plus `schemas.WebhookFormat`, `types.ts`, `SettingsPage.FORMATS`, zh labels and tests — about 1 person-day; a 30-line Cloudflare-Worker-style relay (generic → ntfy/PushPlus/…) is ~2 hours but adds a third party.
- **Evidence.** https://docs.ntfy.sh/publish/ (accessed 2026-11-04: "JSON must be POSTed to the root not /topic"; templating `template=yes`/`tpl=1`, `{{.title}}`, "32 KB in size"; click "Tapping the notification will open the web browser (or the app)"; limits: 4,096 bytes, 60 burst / 1 per 5 s, "Daily message limit on ntfy.sh: 250 messages", "The message title is limited to 1 KB"); https://docs.ntfy.sh/subscribe/phone/ (accessed 2026-11-04: F-Droid "all subscriptions use instant delivery by default, and there is no option to disable it"); https://docs.ntfy.sh/config/ (accessed 2026-11-04: `upstream-base-url`, "the SHA256 of the topic URL"); live probe and poll-back in this session (2026-11-04); backend/wd/delivery/webhook.py:154 (query preserved), :145-146 (local suffixes refused); backend/wd/migrations/0001_init.sql:156 (`webhook_format … CHECK (webhook_format IN ('generic','wecom','feishu','serverchan','bark'))`); backend/wd/schemas.py:37; frontend/src/api/types.ts:17; frontend/src/pages/SettingsPage.tsx:27; frontend/src/i18n/zh.ts:77.
- **Implication.** ntfy is the zero-code answer for friends who prefer an open-source client over WeChat — strongest on iPhone and GMS Android, workable on GMS-less Android with the F-Droid build, absent on HarmonyOS NEXT; ntfy.sh (129.212.146.227, DigitalOcean) was reachable from here but is overseas, so a self-hosted instance on the VPS is the robust variant.
- **Confidence.** high

### F10 — E-mail: exists, needs an SMTP relay, and the notification depends on the friend's mail app

### F12 — Alternative (a): Capacitor local notifications — no backend change, but an app must exist on each phone

- **Claim.** `@capacitor/local-notifications` (v8.3.0 docs) schedules on-device notifications with `at`/`repeats`/`every: 'day'` (or `on: {hour, minute}`), so a shell app could read `push_time` and `timezone` from `GET /api/settings` and schedule a daily reminder whose text is fixed at scheduling time (e.g. 「今日词汇已准备好」) and whose tap opens `/today` in the app — zero server work. Constraints: content cannot include the day's words (the batch is only guaranteed published at `push_time`); the schedule must be refreshed whenever the user changes 推送时间/时区 (only possible while the app runs); iOS keeps at most 64 pending requests per app (a repeating trigger counts once, so irrelevant here) and local notifications fire even if the app was swiped away; Android needs `POST_NOTIFICATIONS` (13+), `SCHEDULE_EXACT_ALARM` (12+) or `USE_EXACT_ALARM` (14) for an exact time, and a force-stopped app (or an aggressive 自启动/省电 policy on domestic ROMs) does not fire until the app is opened again. Toolchain on the owner's Mac: no Xcode (3.12 GB download; iOS builds need it), no Android Studio/JDK; iOS distribution to friends needs the $99/yr program (TestFlight or Ad Hoc — a free Personal Team signs for 7 days on the owner's own device only); Android can be sideloaded as an APK; HarmonyOS NEXT cannot run APKs at all. A "remote shell" (`server.url = https://<domain>`) avoids every backend change (same-origin cookies, no CSRF issue) and is acceptable for sideload/TestFlight even though App Review would reject it under 4.2.
- **Evidence.** https://capacitorjs.com/docs/apis/local-notifications (accessed 2026-11-04: `schedule`, `at`/`repeats`/`every`, `allowWhileIdle`, `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, `USE_EXACT_ALARM`, `checkExactNotificationSetting`, v8.3.0); https://developer.apple.com/forums/thread/811171 and /765490 (accessed 2026-11-04 via search: "limit of 64 … simultaneous notification requests", "soonest-firing 64 notifications (with automatically rescheduled notifications counting as a single notification)"); HarmonyOS NEXT APK incompatibility: https://www.wikipedia.com/wiki/HarmonyOS_NEXT (accessed 2026-11-04: "cannot run Android apk apps"); docs/analysis/2026-11-03-public-launch/facts/apple-appstore.md:35-36, :47-49; docs/analysis/2026-11-03-public-launch/facts/ios-tech-options.md:113-115, :203; docs/PUBLIC_LAUNCH_AND_IOS.md §4.2 (Capacitor 3–5 周 to pass 4.2), §5.3; KNOWN FACTS (no Xcode, no Java/Android SDK).
- **Implication.** As an Android-only sideloaded remote-shell app this is roughly 2–3 person-days (toolchain 0.5 d, project + plugin + schedule-from-settings + deep link 1 d, testing on two or three ROMs 0.5–1 d) and gives a daily nudge without any relay account; for iPhone it adds Xcode, $99/yr and TestFlight's Beta App Review, and it still cannot say which words are due.
- **Confidence.** high for plugin/OS facts; medium for the effort figures

## Recommendations

1. **Week 1 — configuration only (owner ≈ 0.5 person-day total).** Set `WD_PUBLIC_URL=https://<domain>` before anyone enables a channel (F11). iPhone friends: Bark (F4). Android/HarmonyOS friends: Server酱 Turbo → WeChat as the default (F5); offer Server酱³ to the one or two Android friends who want a real system notification, after a 15-minute owner trial with one phone (F6). Friends already on 企业微信/飞书 can use those bots only after the owner has watched a test message arrive on their phone (F3). Keep e-mail as the fallback and configure SMTP only if someone needs it (F10). Dry-run every format on the owner's own devices the day before.
2. **Week 2 — hardening patch (≈ 1 person-day, backend only, no schema change).** (a) In `safe_post`/`send_batch_webhook`, parse the JSON body for `wecom`/`feishu`/`serverchan` and raise `WebhookError` when `errcode`/`code` ≠ 0 (retries then work; the test button becomes truthful) — 0.25 d incl. tests. (b) `wecom`: switch to `msgtype: markdown` (4096 B, `[打开 word-Dance](url)`) or truncate the text to 2048 B — 0.25 d. (c) Keep the Server酱 title ≤ 32 chars (a shorter `Digest.title` or a per-format title) — 0.1 d. (d) Put the `url` into the test message so the deep link is checked before the first digest — 0.1 d. (e) Optional Bark extras (`group: "word-Dance"`, `isArchive: 1`) — 0.1 d. (f) Document the per-channel setup in zh in the settings page hint — 0.2 d.
3. **Month 1 — observe, do not build.** Count who taps the link (server logs for `/today` after push time) and which platform they use before spending on an app or Web Push.
4. **Decision point (after month 1).** If most friends are on iPhone and want a native badge/notification without a relay, Web Push for the Home-Screen app is the next channel (≈ 6–10 person-days, F13). If Android friends dominate, a sideloaded Capacitor remote-shell APK with local notifications (≈ 2–3 person-days, F12) or simply keeping Server酱³ is cheaper than any FCM/vendor-SDK work. Do the `jobs` table rebuild only once, adding `send_webpush` and `send_apns` together (prior doc §6.2 stage 3).
5. **Only if a native `ntfy` format is wanted** (self-hosted ntfy as the house relay): ≈ 1 person-day including the `user_settings` CHECK rebuild (F9); otherwise rely on ntfy's template URL, which needs no code.
