Collected 2026-11-04 against git main @ 9ab13a5. All URLs were accessed on 2026-11-04 unless noted; quotes are verbatim from the fetched page or, where marked "(search snippet)", from the search engine's excerpt of that page. ## Summary

For a circle of <= 10 mainland friends, the realistic Android delivery is the web app itself (opened or "添加到桌面"-shortcut from whichever browser the phone has) plus a reminder channel the repo already supports (Server酱 → WeChat 服务号, 企业微信/飞书 group bots), optionally followed by a sideloaded APK built in GitHub Actions; a domestic store listing is out of reach for this round because every store demands an APP备案号 (which presupposes a mainland-hosted, ICP-filed backend) and OPPO/vivo do not even let individual accounts publish APKs. Google's developer-verification regime does not touch mainland phones today: enforcement runs inside the "Android Developer Verifier" delivered "through Google Play services", is live only in BR/ID/SG/TH for installs from participating stores since 2026-09-30, goes global on certified devices in 2027, and leaves ADB, a 24-hour "advanced flow" and a free limited-distribution account (no ID; 20 devices per the June FAQ, 50 per the guide read today) as escape hatches. Huawei phones split hard: HarmonyOS 4.x still installs APKs, HarmonyOS NEXT (5/6/7 — every Huawei phone launched since late 2024) cannot run APKs at all and its Huawei Browser only offers a plain desktop shortcut (no documented manifest/standalone install); Huawei/HarmonyOS took 24% of China smartphone sales in Q2 2026 but native-HarmonyOS terminals are ~85 M across all device types, so a single-digit share of the installed phone base. Web Push is not an Android reminder path in the mainland: Chrome and Firefox both register through Google Play services/FCM, Edge Android's push has been broken since Oct 2025 builds, and no domestic browser documents Web Push. TTS works in real browsers (Chrome/Edge/Firefox bridge to the system TTS engine) but Android System WebView exposes no speechSynthesis, so any WebView/TWA-fallback wrapper needs a native TTS plugin; whether domestic default engines ship an English voice is untested. The repo is not installable as a PWA yet (no manifest, no icons, no service worker) — about one day of work fixes that for Chrome and gives every other browser a better shortcut.

## Findings

### F1 (high) Google developer verification — official timeline and status as of Nov 2026
- CLAIM: Verification protections began 2026-09-30 only in Brazil, Indonesia, Singapore and Thailand, only for installs from participating stores, only on certified devices running Android 7+; direct sideloading and non-listed stores are not enforced until the 2027 global expansion; the first wave is live.
- EVIDENCE: developer.android.com/developer-verification (Timeline table): "August 2026 | Developer APIs, limited distribution accounts, and power user advanced flow launch. … September 30, 2026 | Protections begin for all users who install apps from participating stores in Brazil, Indonesia, Singapore, and Thailand on certified devices running Android 7+. … 2027 and beyond | Verification capability will be expanded globally for all apps on certified Android devices in 2027." FAQ developer.android.com/developer-verification/guides/faq: "What happens starting September 30, 2026 if I sideload my app or distribute it through another store that isn't included in the list of participating stores? … If you distribute your app through other stores, or if users sideload your app directly, these new verification requirements won't apply to your app yet. (Last updated: July 15, 2026)". Android Developers Blog 2026-06-18 "Android developer verification: Building a safer ecosystem together": participating stores "Google (Google Play), Honor (HONOR App Market), OPlus (OPPO App Market), Samsung (Galaxy Store), Transsion (Palm Store), vivo (V-Appstore), Xiaomi (GetApps)"; "A new system service...will be automatically installed on most Android devices" from June 2026. Android Authority 2026-10-01 (androidauthority.com/android-sideloading-developer-verification-first-wave-rollout-3717921/): "apps installed through participating stores must be registered to a verified developer" on "certified devices running Android 7 or newer".
- IMPLICATION: Nothing changes for a friend-circle APK in 2026 anywhere; in 2027 a sideloaded, unregistered APK on a certified (GMS) phone will need the advanced flow, ADB, or a limited-distribution enrolment (F2, F3).
- CONFIDENCE: high.

### F2 (high) The "advanced flow" and the ADB exemption
- CLAIM: Power users can install unverified apps after a one-time setup: enable developer options → confirm not being coached → restart and re-authenticate → wait one day → confirm with biometrics/PIN → choose 7 days or indefinitely; afterwards every such install still shows an "unverified developer" warning with "Install Anyway". ADB installs need no verification and no waiting period, and unregistered apps can only be updated while the advanced flow is enabled or via ADB.
- EVIDENCE: FAQ (Last updated March 23, 2026): "Enable developer mode in system settings … Confirm you aren't being coached … Restart your phone and reauthenticate … There is a one-time, one-day wait and then you can confirm … with our biometric authentication (fingerprint or face unlock) or device PIN … with the option of enabling for 7 days or indefinitely. For safety, you'll still see a warning that the app is from an unverified developer, but you can just tap 'Install Anyway.'"; "Are ADB installs impacted by the 24-hour waiting period for advanced flow? No, there are no changes to how ADB works."; "Is there an ADB command to bypass the 24-hour waiting period? This option is not supported at this point."; "Unregistered apps can only be installed or updated when the advanced flow is enabled or by using ADB". Announced 2025-11-12 (9to5google.com/2025/11/12/android-sideload-unverified-apps/) and detailed in the blog "Android developer verification: Balancing openness and choice with safety" (android-developers.googleblog.com/2026/03/android-developer-verification.html, 2026-03-19).
- IMPLICATION: Even in 2027 a motivated friend on a GMS phone can keep sideloading, but the UX (24 h wait, warnings) is hostile for non-technical users; registering the package is the cleaner path (F3).
- CONFIDENCE: high.

### F3 (high) Limited distribution account — the designed path for a friend circle (device cap is stated inconsistently)
- CLAIM: A free Android Developer Console account type lets hobbyists register package names and share apps with a small, explicitly authorised set of devices without a government ID; the FAQ/June blog say 20 devices, the guide read today says 50; sharing works through a QR-code/link handshake with on-device consent.
- EVIDENCE: developer.android.com/developer-verification/guides/limited-distribution (read 2026-11-04): "Share apps with up to 50 devices that end-users have explicitly authorized."; "This account is free."; "a secure handshake process involving QR codes or links, user consent on the device, and registration using the Android Developer Console"; needs "A Google Account … 2-Step verification … Google payments profile … you don't need to provide a government ID". FAQ (June 18, 2026): "This lets you share apps with up to 20 specific devices for testing and personal use at no cost and without ID verification." Blog 2026-06-18: "share your apps to up to 20 devices without a government-issued ID or a fee".
- IMPLICATION: For <= 10 friends this is exactly the intended mechanism once the 2027 rollout reaches their (GMS) phones; the owner needs a Google account + payments profile reachable from the mainland (proxy). The on-device consent presumably runs inside the verifier (Play services), so it cannot be completed on GMS-less phones — which also do not enforce (F4). Treat the 20-vs-50 cap as unresolved.
- CONFIDENCE: high on existence/cost; medium on the cap.

### F9 (high) WebAPK minting needs Google services; GMS-less Chrome falls back to a shortcut
- CLAIM: Only Chrome on devices with Google Mobile Services (and Samsung Internet on Samsung hardware) mint WebAPKs through a cloud minting server; Chrome on GMS-less devices, Firefox, Edge, Opera and Brave add a browser-badged home-screen shortcut that opens the site in the browser.
- EVIDENCE: MDN (same page as F8): "On Android, the only browsers that install PWAs as WebAPKs are: Chrome on devices with Google Mobile Services (GMS), and Samsung Internet on Samsung devices. … Firefox, Edge, Opera, and other browsers including Chrome on devices where GMS is not present, instead add a browser-badged home-screen shortcut that opens the site in the browser." web.dev/learn/pwa/installation: "A WebAPK is an Android package (APK) created by a trusted provider of the user's device, typically in the cloud, on a WebAPK minting server"; "Firefox, Microsoft Edge, Opera, Brave, and Samsung Internet (on non-Samsung devices) don't have minting servers they trust, they'll create shortcuts."
- IMPLICATION: On default-state domestic phones a Chrome "install" (if Chrome is even installed) yields a shortcut, not an app entry; the user-visible difference from Huawei/Xiaomi browser shortcuts is small, so the manifest work (F8) mainly buys the icon/name/standalone hints and a correct Install on GMS phones.
- CONFIDENCE: high.

### F13 (high) TTS: real browsers bridge to the system engine; Android System WebView has no speechSynthesis
- CLAIM: Chrome's Android speech synthesis is a bridge to `android.speech.tts.TextToSpeech` that enumerates voices by probing `Locale.getAvailableLocales()` with `isLanguageAvailable`, so English pronunciation depends on the phone's default TTS engine having an en-US/en-GB voice. Android System WebView does not expose `window.speechSynthesis` at all (open Chromium issues; confirmed on WebView Chromium 138 in July 2026). The repo already degrades gracefully (SpeakButton disabled with a tooltip; `pickVoice` falls back to any English voice, then browser default). A wrapper app therefore needs a native TTS plugin, which itself depends on an installed engine with English data.

### F17 (medium) What "GMS phone" means for this circle

- IMPLICATION: Design for the GMS-less default; treat GMS features as a bonus that a minority of friends may enjoy.
- CONFIDENCE: medium.
