# Fact slice: captool — Nov 2026 toolchain for wrapping the word-Dance SPA as a remote-shell Capacitor app (iOS + Android) with a daily local reminder

Collected 2026-11-04 from primary sources (npm registry, Capacitor 8.6.0 source at the git tag and the published npm tarballs, capacitorjs.com docs, Apple/Google/WebKit docs) plus the word-Dance tree at /Users/sqin/word-dance (main @ 9ab13a5). Prior slices (docs/analysis/2026-11-03-public-launch/facts/ios-tech-options.md, apple-appstore.md) were re-verified where relied upon; where a figure is reused without re-verification it is marked.

## Summary

- Capacitor 8.6.0 is the current stable release (2026-10-28); 9.0.0-beta.0 is on the `next` tag and Ionic targets GA "at the end of November" 2026. Capacitor 8 needs Node 22+, Xcode 26+, iOS 15+, Android Studio 2025.2.1+, AGP 8.13 / Gradle 8.14.3, minSdk 24 / target 36, Java 21; Capacitor 9 raises this to Node 24, Xcode 27, iOS 16, Android Studio 2026.1.4, minSdk 26 / target 37. The Mac's Node 22.23.4 is enough for Capacitor 8 (and Expo 58, Bubblewrap, Vite 8) but not for Capacitor 9.
- The remote shell (`server.url = https://<domain>`) is explicitly "not intended for use in production" in the docs and the Capacitor team refuses to document it (app-store-rejection risk), but the mechanism is real and verifiable in source: iOS injects `window.Capacitor` + native-bridge.js as a `WKUserScript` at document start into every main-frame page the WKWebView loads; Android uses `WebViewCompat.addDocumentStartJavaScript` for the server.url origin (with an HTML-proxy fallback for old WebViews). Plugins are callable from the remote page via the natively injected `Capacitor.Plugins.<Name>` stubs / `Capacitor.nativePromise(...)` with no npm JS in the website, or more cleanly via `@capacitor/core`'s `registerPlugin`.
- For word-Dance specifically the remote shell is the design that needs **no backend change**: the page origin equals the API origin, so the `wd_session` cookie is first-party and persistent (WKWebView default data store; Android CookieManager), the CSRF Origin rule passes exactly as in a browser, and cookie-protected `/media` images load. The bundled-asset design analysed yesterday needed CapacitorHttp plus signed media URLs; the remote shell does not.
- Daily reminder: `@capacitor/local-notifications` 8.3.1 maps `schedule.on {hour, minute}` to a repeating `UNCalendarNotificationTrigger` on iOS and to an exact alarm (`setExactAndAllowWhileIdle` when `allowWhileIdle`) or an inexact fallback on Android, restores alarms after reboot, and declares `POST_NOTIFICATIONS` + `SCHEDULE_EXACT_ALARM`. Android 13+ needs the runtime notification permission; Android 14+ denies exact alarms by default for new installs (user toggle, or declare `USE_EXACT_ALARM` since Play policy is irrelevant for sideload); iOS keeps at most 64 pending notifications (one repeating trigger counts once). Xiaomi/Huawei/OPPO/vivo battery killers remain the main delivery risk.
- Android 15/16 edge-to-edge is enforced for targetSdk 35/36 (opt-out removed in 16); Capacitor 8 dropped `adjustMarginsForEdgeToEdge` for the bundled System Bars plugin (CSS `--safe-area-inset-*` injection, default `insetsHandling: css`). word-Dance already uses `viewport-fit=cover` and `env(safe-area-inset-*)`, so it is largely ready.
- Speech: Android System WebView has no `speechSynthesis` at all (still absent in Chromium 138 WebView, 2026-07), so the Android shell needs `@capacitor-community/text-to-speech` 8.0.2 (Android `TextToSpeech`, iOS `AVSpeechSynthesizer` with `category: playback`); WebKit enables the SpeechSynthesis API for all embedders by default, so WKWebView keeps the existing Web Speech path (gesture rule, pre-installed voices only).
- Alternatives are weaker for this use case: PWABuilder's iOS shell is community-maintained, "experimental", pushes only via Firebase and has no local scheduling; TWA/Bubblewrap needs Chrome 72+ (falls back to a plain WebView on GMS-less phones) and has no reminder API; Tauri 2 mobile is stable but adds Rust, CocoaPods and the NDK; Expo/RN + react-native-webview is an equivalent shell with a heavier toolchain (its EAS free tier does allow 15 iOS builds/month without a local Xcode).
- Build/distribute without CI: Xcode 27.2 (3.12 GB download, macOS 26.6+, met) + `xcodebuild -archive/-exportArchive` (`method app-store-connect`, `destination upload`) or `xcrun altool --upload-package --apiKey`; friends' iPhones need the $99/yr program (TestFlight internal testing = up to 100 App Store Connect users, **no Beta App Review**; external = review of the first build; 90-day expiry); a free Personal Team only signs 3 apps on 3 devices for 7 days. Android: Android Studio 2026.2.2 (1.5 GB) or command-line tools + JDK 21, `./gradlew assembleRelease` + keystore/apksigner, APK sideload via "Install unknown apps". Disk budget on this Mac: ~15 GB downloads (Xcode 3.1 + iOS simulator runtime ~7.9 optional + Android Studio 1.5 + SDK/emulator), ~30 GB installed.

### F5 (high) Official stance on `server.url` (remote content)
- CLAIM: Config docs: `server.url` — "Load an external URL in the Web View. This is intended for use with live-reload servers. **This is not intended for use in production.**"; the same warning is attached to `allowNavigation`, `cleartext`, `androidScheme` and `android.allowMixedContent`. Capacitor team member Eric Horodyski (issue #8242, 2025-11-16): "we do not recommend using Capacitor to load external websites. Doing so may put you at risk of app store rejection (which is why we don't recommend it). Therefore, we would not entertain adding documentation on how to do so." Community discussion #5075 (2021) records production users and their failure modes: native-plugin/web-bundle version mismatch, injection failing when a service worker serves the page on Android, offline behaviour, and Apple approval achieved only after adding native features (push).
- EVIDENCE: https://capacitorjs.com/docs/config (v8, accessed 2026-11-04); https://github.com/ionic-team/capacitor/issues/8242 (accessed 2026-11-04); https://github.com/ionic-team/capacitor/discussions/5075 (accessed 2026-11-04); `cli/src/declarations.ts` lines 618–660 at tag 8.6.0.
- IMPLICATION: Unsupported ≠ non-functional. For a ≤10-friend circle installed via TestFlight internal testing or APK sideload (no review), the policy objection disappears; the technical caveats (version coupling, service worker) remain and are addressed below. Do not add a service worker to the site while a shell depends on Android injection unless the DOCUMENT_START_SCRIPT path (F7) is confirmed on the friends' phones.

### F6 (high) iOS remote-shell mechanics verified in Capacitor 8.6.0 source
- CLAIM: With `server.url` set, `CAPBridgeViewController` loads it directly: `let url = bridge.config.appStartServerURL … webView?.load(URLRequest(url: url))` (lines 176–179). The bridge is injected with `WKUserScript(source:, injectionTime: .atDocumentStart, forMainFrameOnly: true)` for (a) `window.Capacitor = { DEBUG…, isLoggingEnabled…, Plugins: {} }; window.WEBVIEW_SERVER_URL = …` (JSExport.swift:19-22), (b) `native-bridge.js` (JSExport.swift:24-37,107) and (c) per-plugin stubs that create `Capacitor.Plugins['<Name>']` whose methods call `Capacitor.nativePromise/nativeCallback`, plus `Capacitor.PluginHeaders.push(...)` (JSExport.swift:73-110). WKUserScripts apply to every main-frame document the web view loads, so remote pages get the bridge. The web view uses `WKWebViewConfiguration()` with the **default** website data store (only a cookie observer is added, CAPBridgeViewController.swift:120-121); Apple: "A web view configured with the default data store saves website data persistenly to disk." Navigation policy (WebViewDelegationHandler.swift:67-125): URLs whose string starts with `serverURL` or `localURL` and hosts in `allowNavigation` are allowed; any other top-level navigation is cancelled and opened with `UIApplication.shared.open`. `ios.limitsNavigationsToAppBoundDomains` defaults to false; WebKit: apps that do not opt in "will experience pre-iOS 14.0 `WKWebView` behavior, with no restricted APIs on any domains", whereas opting in restricts "JavaScript injection, custom style sheets, cookie manipulation, and message handler use" to ≤10 `WKAppBoundDomains`.
- EVIDENCE: https://raw.githubusercontent.com/ionic-team/capacitor/8.6.0/ios/Capacitor/Capacitor/{CAPBridgeViewController,JSExport,WebViewDelegationHandler,CAPInstanceDescriptor}.swift (accessed 2026-11-04); https://developer.apple.com/documentation/webkit/wkwebsitedatastore/default() (accessed 2026-11-04 via the tutorials/data JSON endpoint); https://webkit.org/blog/10882/app-bound-domains/ (2020-06-26, accessed 2026-11-04).
- IMPLICATION: On iOS the shell is literally Safari-grade WebKit loading the live site with a persistent first-party cookie jar; external links open in Safari; leave `limitsNavigationsToAppBoundDomains` false (or list the domain) so injection keeps working. No CapacitorHttp/CapacitorCookies needed.

### F7 (high for mechanism; medium for WebView-version boundary) Android remote-shell mechanics verified in source
- CLAIM: `Bridge.java` adds `server.url` to the allowed-origin set (lines 237–254) and, when `WebViewFeature.isFeatureSupported(WebViewFeature.DOCUMENT_START_SCRIPT)`, calls `WebViewCompat.addDocumentStartJavaScript(webView, injector.getScriptString(), Collections.singleton(allowedOrigin))` with `allowedOrigin` = the origin of `appUrl` (= `server.url`) and then sets `injector = null` (lines 266–274) — i.e. the WebView loads the remote HTML natively and runs the bridge at document start for that origin only. Fallback for WebViews without the feature: `WebViewLocalServer.handleProxyRequest` (lines 515–560) fetches GET requests whose `Accept` contains `text/html` through `HttpURLConnection`, forwards `CookieManager` cookies, stores `Set-Cookie`, and `JSInjector.getInjectedStream` inserts `<script>…</script>` after `<head>` (or before `</head>`), logging "Unable to inject Capacitor, Plugins won't work" otherwise (JSInjector.java:91-105). Issue #7269 (2024) documents the old proxy path breaking on a UA-dependent server redirect and the maintainer noting "on Capacitor 6 the javascript is injected in a different way and it's not affected by this problem." `launchIntent` opens hosts other than the app URL host / `allowNavigation` in an external browser (Bridge.java:389-421). Cookies: Android `CookieManager` — "By default this is set to `true` and the WebView accepts cookies"; `flush()` "Ensures all cookies currently accessible through the getCookie API are written to persistent storage."
- EVIDENCE: https://raw.githubusercontent.com/ionic-team/capacitor/8.6.0/android/capacitor/src/main/java/com/getcapacitor/{Bridge,WebViewLocalServer,JSInjector,BridgeWebViewClient}.java (accessed 2026-11-04); https://github.com/ionic-team/capacitor/issues/7269 (accessed 2026-11-04); https://developer.android.com/reference/android/webkit/CookieManager (accessed 2026-11-04). word-Dance `frontend/index.html` has a literal `<head>` (line 3), so even the fallback injection point exists.
- IMPLICATION: On any reasonably current Android WebView (incl. Huawei's Chromium-based WebView ≥ 10 that Capacitor supports) the page is loaded by the WebView itself with the bridge pre-injected; only very old WebViews go through the HTTP proxy, where compression matters (F25). The exact Chromium version that introduced `DOCUMENT_START_SCRIPT` was not verified (open question).

### F8 (high) Calling native plugins from the remote page without bundling plugin JS
- CLAIM: What native injects: `window.Capacitor.toNative / nativePromise / nativeCallback` (native-bridge.ts:996-1127), `Capacitor.Plugins.<Name>` method stubs and `Capacitor.PluginHeaders` (iOS JSExport.exportJS; Android `JSInjector.getScriptString()` concatenates `globalJS + localUrlJS + bridgeJS + pluginJS + …`, JSInjector.java:62-84). What is **not** injected: `registerPlugin`, which lives in `@capacitor/core`'s runtime (`core/src/runtime.ts`: `const Plugins = (cap.Plugins = cap.Plugins || {})` line 19; looks up `cap.PluginHeaders?.find(h => h.name === pluginName)` line 44; `Plugins[pluginName] = proxy` line 183). The plugin's own npm package (e.g. `@capacitor/local-notifications`) contributes only TypeScript types and a web implementation; the native code must be installed in the **shell** project (`npm i @capacitor/local-notifications && npx cap sync`).
- EVIDENCE: https://raw.githubusercontent.com/ionic-team/capacitor/8.6.0/core/native-bridge.ts and core/src/runtime.ts (accessed 2026-11-04); JSExport.swift:73-110.
- IMPLICATION: Two workable patterns for word-Dance's SPA: (1) zero-dependency — `if (window.Capacitor?.isNativePlatform?.()) await window.Capacitor.nativePromise('LocalNotifications','schedule',{notifications:[...]})` (or `Capacitor.Plugins.LocalNotifications.schedule(...)`); (2) add `@capacitor/core` (+ plugin packages for types) to the website bundle and call `registerPlugin('LocalNotifications')`, gating on `Capacitor.isNativePlatform()` so desktop browsers never hit "not implemented on web". Either way the website and the native shell must agree on plugin names/method shapes — the version-coupling risk from F5; mitigate with a `?v=` check: the shell can send `appendUserAgent: "word-dance-shell/1"` and the site can feature-detect `Capacitor.isPluginAvailable('LocalNotifications')`.

### F9 (high) Why the remote shell needs no backend change for word-Dance
- CLAIM: The session is the `wd_session` cookie (`HttpOnly; SameSite=Lax; Path=/`, security.py:6,230-236); the CSRF rule requires `X-WD-Request: 1` on non-GET `/api/*` and, if an `Origin` header is present, it must equal the Host-derived origin or `WD_PUBLIC_URL` (deps.py:111-129; "no Origin header … SameSite=Lax + the custom header suffice", line 122). In a remote shell the document origin is `https://<domain>` — identical to the API — so fetches carry the same `Origin` as in Safari/Chrome, the cookie is first-party (persisted per F6/F7), `<img src="/media/…">` and `<input type=file>` imports behave as in the browser. The bundled-asset design (origin `capacitor://localhost` / `https://localhost`) was the one that needed CapacitorHttp + signed media URLs (ios-tech-options-19, re-verified against deps.py today).
- EVIDENCE: /Users/sqin/word-dance/backend/wd/deps.py:111-146; backend/wd/security.py:6,230-242; F6/F7 sources.
- IMPLICATION: Backend scope for the shell is zero; the only server-side nicety is `WD_PUBLIC_URL` set to the public origin (already required for deployment) and, optionally, recognising the shell UA for a "download in browser" hint (F23).

### F10 (high) `@capacitor/local-notifications` 8.3.1: scheduling semantics verified in the shipped code
- CLAIM: Latest 8.3.1 (2026-08-19), `next` 9.0.0-alpha.2 (2026-07-15). Schedule shapes: `at` (+`repeats`), `on` (`year|month|day|weekday|hour|minute|second`), `every` (`'year'|'month'|'two-weeks'|'week'|'day'|'hour'|'minute'|'second'`) with `count`, `allowWhileIdle`. iOS (LocalNotificationsPlugin.swift:518-567): `on` → `UNCalendarNotificationTrigger(dateMatching: dateComponents, repeats: true)` (wall-clock daily when only hour/minute are set); `every: 'day'` → `UNTimeIntervalNotificationTrigger(timeInterval: 86400, repeats: true)` anchored to *now* (not to a clock time); `at` in the past delivers immediately; `requestAuthorization(options: [.badge, .alert, .sound])`. Android (Kotlin, LocalNotificationManager.kt:357-378; TimedNotificationPublisher.kt:59-67): `useExact = isExactNotification && canScheduleExactAlarms()`; exact → `setExactAndAllowWhileIdle(RTC_WAKEUP)` if `allowWhileIdle` else `setExact(RTC)`; otherwise `setAndAllowWhileIdle` / `set` (inexact); `every` → `setRepeating(RTC, start, interval)`; `on` is re-armed per occurrence (DateMatch); alarms are restored on `BOOT_COMPLETED`, `LOCKED_BOOT_COMPLETED`, `QUICKBOOT_POWERON` by a `directBootAware` receiver. Manifest declares `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`. Docs: "As of version 8.3.0, `schedule()` automatically requests permissions if not granted"; `checkExactNotificationSetting()/changeExactNotificationSetting()` (opens `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`); Android 15 Private Space warning; `createChannel({id,name,importance…})` for Android channels.
- EVIDENCE: npm tarball `@capacitor/local-notifications@8.3.1` (ios/Sources/LocalNotificationsPlugin/LocalNotificationsPlugin.swift, android/src/main/kotlin/…/{LocalNotificationManager,TimedNotificationPublisher,LocalNotificationsPlugin,LocalNotificationRestoreReceiver}.kt, android/src/main/AndroidManifest.xml); https://capacitorjs.com/docs/apis/local-notifications (v8, accessed 2026-11-04); registry dist-tags (2026-11-04).
- IMPLICATION: Use `schedule({notifications:[{id:1,title,body,schedule:{on:{hour:H,minute:M},allowWhileIdle:true}}]})` — one repeating request on both platforms; re-schedule whenever the user changes `push_time` in Settings (cancel id 1, schedule again). Do not use `every:'day'` for a clock-time reminder.

### F11 (high) Android permission rules that govern the reminder
- CLAIM: Android 13+: "Android 13 (API level 33) and higher supports a runtime permission for sending non-exempt … notifications from an app: `POST_NOTIFICATIONS`"; on new installs "your app's **notifications are off by default**" until granted; apps targeting 33+ control when the prompt appears. Exact alarms: "If your app targets Android 12 or higher, you must declare one of the 'Alarms & reminders' permissions"; "The `SCHEDULE_EXACT_ALARM` permission is not pre-granted to fresh installs of apps targeting Android 13 (API level 33) and higher" (the Android 14 change) — the user enables it in Settings > Alarms & reminders (`ACTION_REQUEST_SCHEDULE_EXACT_ALARM`); `USE_EXACT_ALARM` is "Granted automatically", "Cannot be revoked by the user", "Subject to an upcoming Google Play policy", intended for alarm-clock/calendar apps. Google's guidance: "Most apps can schedule tasks and events using inexact alarms"; on Android 12+ an inexact alarm fires "within one hour of the supplied trigger time, unless any battery-saving restrictions are in effect"; `setWindow` minimum 10 minutes; "all repeating alarms are inexact alarms" since 4.4; `setExactAndAllowWhileIdle` fires at most once per 9 minutes in Doze (plugin docs).
- EVIDENCE: https://developer.android.com/develop/ui/views/notifications/notification-permission and https://developer.android.com/develop/background-work/services/alarms/schedule (both accessed 2026-11-04).
- IMPLICATION: For a 20:00 "today's words" nudge, decide between (a) inexact (no extra permission; may arrive up to ~1 h late, later under battery saver) and (b) exact (`allowWhileIdle:true`; on Android 14+ ask the user once to flip "Alarms & reminders"; since the APK is sideloaded, declaring `USE_EXACT_ALARM` instead is technically allowed and skips the toggle — add it to the shell's manifest, the plugin only declares `SCHEDULE_EXACT_ALARM`). Request `POST_NOTIFICATIONS` from a user gesture ("开启提醒" button), not at launch.

### F12 (high) iOS pending-notification limit
- CLAIM: "An app can have only a limited number of scheduled notifications; the system keeps the soonest-firing 64 notifications (with automatically rescheduled notifications counting as a single notification) and discards the rest."
- EVIDENCE: Apple, UILocalNotification class reference (legacy UIKit page still published), https://developer.apple.com/documentation/uikit/uilocalnotification (accessed 2026-11-04 via the tutorials/data JSON endpoint).
- IMPLICATION: One repeating calendar trigger consumes one slot; even per-stage reminders stay far below 64. The modern UserNotifications pages no longer state the number explicitly, so treat 64 as the documented historical ceiling (medium-high that it is unchanged).

### F13 (medium) OEM background restrictions on domestic Android
- CLAIM: dontkillmyapp.com ranks vendors that "prefer battery life over proper functionality of your apps": Huawei (1), Xiaomi (2), OnePlus (3), Samsung (4), Meizu (5), …, Oppo (8), with vivo/realme lower; user-side fixes: Xiaomi — enable Autostart and set Battery saver to "No restrictions"; Huawei — manual "Launch" management. Capacitor's docs add: on Android 15 an app installed in a locked Private Space may not show notifications.
- EVIDENCE: https://dontkillmyapp.com/ (accessed 2026-11-04); F10 plugin docs.
- IMPLICATION: `AlarmManager`-driven local notifications are the most robust client-side mechanism available (no FCM), but a one-page zh-CN onboarding ("小米：自启动 + 省电无限制；华为：应用启动管理手动") is mandatory for the friends on Xiaomi/Huawei, and the Bark/email/webhook channels that already exist remain the server-side backup.

### F14 (high) Android 15/16 edge-to-edge and Capacitor 8's handling
- CLAIM: Android 15: "Apps are edge-to-edge by default on devices running Android 15 if the app is targeting Android 15 (API level 35)"; status bar "Transparent by default … content draws behind the status bar unless insets are applied"; `windowOptOutEdgeToEdgeEnforcement` allowed an opt-out. Android 16: "For apps targeting Android 16 (API level 36), `R.attr#windowOptOutEdgeToEdgeEnforcement` is deprecated and disabled, and your app can't opt-out of going edge-to-edge"; predictive back is on by default for target 36. Capacitor 8 (target 36) removed `android.adjustMarginsForEdgeToEdge` "in favor of System Bars core plugin using CSS `env` variables" (the key is absent from the 8.6.0 config schema); the System Bars plugin is bundled with `@capacitor/core` (since 8.0.0): `insetsHandling` default `css` "injects CSS variables (`--safe-area-inset-*`)", `native` pads the WebView "for older Chromium versions" and honours `viewport-fit` for WebView ≥ 140; the Status Bar plugin's `overlaysWebView` and `backgroundColor` "no longer have any effect" on Android 16+. Google Play target-SDK deadlines (API 35 by 2025-08-31; API 36 by 2026-08-31, extension to 2026-11-01; non-compliant apps "stop being discoverable" to users on newer Android) do not apply to sideloaded APKs.

### F25 (medium-low; fallback path only) HTML compression and the Android proxy fallback
- CLAIM: The Android fallback injector copies the WebView's request headers into an `HttpURLConnection` (WebViewLocalServer.java:531-535). Android: "By default, this implementation of `HttpURLConnection` requests that servers use gzip compression and it automatically decompresses the data … Gzip compression can be disabled by setting the acceptable encodings in the request header" — i.e. an explicitly copied `Accept-Encoding` header disables transparent decompression (and zstd/brotli are never decompressed), after which `JSInjector` would not find `<head>` and would log "Unable to inject Capacitor, Plugins won't work". Reports differ on whether intercepted WebView requests expose `Accept-Encoding` (not verified). word-Dance's `deploy/Caddyfile.example:3` has `encode zstd gzip` (HTML included); `deploy/nginx.conf.example:6` gzips only json/css/js/svg. The primary `addDocumentStartJavaScript` path (F7) bypasses the proxy entirely.
- EVIDENCE: https://developer.android.com/reference/java/net/HttpURLConnection (accessed 2026-11-04); Capacitor 8.6.0 WebViewLocalServer.java/JSInjector.java; /Users/sqin/word-dance/deploy/Caddyfile.example:3, deploy/nginx.conf.example:6.
- IMPLICATION: Only phones whose WebView lacks `DOCUMENT_START_SCRIPT` are exposed; if such a phone shows "Plugins won't work" in logcat, exclude `text/html` from Caddy's `encode` (`encode zstd gzip { match { header Content-Type application/json* text/css* application/javascript* image/svg+xml* } }`) — a one-line change.

## Verdict: remote-shell viability with Capacitor

Technically viable and the cheapest route for this circle. Verified: the bridge is injected into remote pages on both platforms (F6, F7); plugins are callable without changing the website's dependencies (F8); the same-origin cookie/CSRF/media design works unchanged (F9); the daily reminder maps to one repeating local notification on both platforms (F10–F12); edge-to-edge is already handled by the site's CSS plus Capacitor 8's System Bars plugin (F14). Required work is small and all client-side: a TTS branch for Android (F15), an export fallback (F23), a reminder opt-in UI that calls `schedule()` and re-schedules on `push_time` changes (F10), a zh-CN battery-settings note (F13). Known costs: Ionic calls `server.url` unsupported for production and App Review 4.2 would apply to a public App Store submission — irrelevant for TestFlight internal testing and APK sideload, relevant if the circle ever grows into a storefront release (F5); offline = blank page (no cached shell); the native binary and the website must agree on plugin names (F8); Android WebView quality and OEM background policies vary (F7, F13). The remote shell should be treated as the "small circle" artefact; a bundled-asset shell (yesterday's analysis) remains the path for a storefront.
