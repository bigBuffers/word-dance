# Hosting slice — where to run word-Dance for ≤10 mainland-China friends (web, technical only)

Collected 2026-11-04 by the `hosting` research slice. All web sources were accessed on 2026-11-04 unless stated; prices were converted at USD 1 = CNY 6.684, EUR 1 = USD 1.119 (open.er-api.com, 2026-11-04 00:02 UTC). Policy questions (Anthropic terms, model licensing, domestic-model replacement) are out of scope by owner instruction; only *technical* reachability of api.anthropic.com is covered.

## Summary

1. The server must sit in a country on Anthropic's supported list: Japan, Singapore, Taiwan, South Korea and the US are listed; mainland China, Hong Kong and Macau are not, and Hong Kong datacentre IPs demonstrably get `403 {"type":"forbidden","message":"Request not allowed"}` (two independent October-2026 fixes moved workloads from Cloudflare's HKG colo to Singapore / US to clear it). Hong Kong is therefore out, despite its best mainland latency.
2. Tencent Cloud Lighthouse (中国站) sells Tokyo / Singapore / Silicon Valley bundles at ≈¥33/month (2 vCPU, 2 GB, 50 GB, 30 Mbps, 1 TB) and ≈¥42/month (2 vCPU, 4 GB) with WeChat/Alipay payment and the owner's existing 实名; the international site lists the identical bundles at $4.50 / $6.00. Alibaba Cloud SAS is ≈¥39/month for a 2 vCPU/2 GB overseas 国际型 plan but Alibaba's own docs say overseas regions are "非直连 … 不建议您使用" for mainland visitors.
3. Non-Chinese providers cost the same or more (Vultr $5–6, DigitalOcean $6–18, Hetzner €5.49 EU / €15.49–26.49 Singapore) and their mainland routes are worse (NTT-based Tokyo with 10–20 % evening loss for China Telecom users; Hetzner Singapore detours via Japan/US; Hetzner EU ≥160 ms). Their only advantage is a non-Chinese account, which the owner does not need.
4. No ICP filing is needed for any overseas host: Alibaba's filing FAQ says "若解析指向境外服务器（如中国香港），则无需ICP备案". Domestic DNS (DNSPod / Alibaba DNS) resolves un-filed domains to overseas IPs; the requirements are account 实名 and domain 实名 (unverified domains go `serverHold`). Only URL-forwarding records are 备案-gated.
5. Domains: Alibaba `.com` ¥85 first year / ¥95 renewal with mandatory 实名; abroad, Porkbun takes Alipay (`.com` $11.08, `.xyz` $2.04→$14.21, `.top` $1.63→$4.63), Namecheap and Cloudflare take UnionPay cards (Cloudflare at-cost `.com` ≈$11.17 after the 2026-11-01 Verisign increase). Keep DNS at DNSPod/Alibaba DNS (fast from the mainland) or Cloudflare DNS-only; do not put mainland users behind the Cloudflare proxy.
6. Publishing the Mac through Cloudflare Tunnel is free and technically compatible with the backend (cloudflared preserves `Host`, the edge sets `X-Forwarded-Proto`/`CF-Connecting-IP`, cloudflared appends `X-Forwarded-For`; the app trusts proxies on 127.0.0.1 and reads `X-Forwarded-Proto` when `WD_TRUST_PROXY=1`), but the free plan has no mainland PoPs (China Network is Enterprise-only), mainland users land on US-West PoPs with 80–300 ms+ latency, 40 KB/s-class throughput reports and recurring IP/SNI blocking episodes (104.16/13 in 2022, `.1` edge IPs in July 2025). Tailscale is not installable from the mainland App Store (iTunes lookup for app id 1470499037 returns 0 results for `country=cn`, 1 for us/jp/sg/hk), so it cannot serve the friend circle. frp needs a VPS anyway.
7. Default pick: Tencent Lighthouse 中国站, Tokyo region (Singapore as the fallback), 2 vCPU/4 GB bundle (~¥42/month), Ubuntu 24.04 image, Caddy via `deploy/install.sh --with-caddy`, a 实名'd domain with 300-second TTL and a re-IP runbook; total ≈1 person-day including data migration from the Mac.

## Findings

### F1 — Anthropic's supported-region list (official)
- **Claim**: Japan, Singapore, Taiwan, South Korea and the United States are supported; mainland China, Hong Kong and Macau are absent.
- **Evidence**: "Supported Regions Policy", https://www.anthropic.com/supported-countries (page shows "Last Updated: Nov 12, 2026" — a future-dated effective date as rendered on 2026-11-04): "Anthropic's products and services — including our apps (such as Claude.ai, Claude Code, and Cowork), our API and developer platform, and Claude models offered through cloud platforms and authorized resellers — are available only in the countries and regions listed below." The platform docs list (https://platform.claude.com/docs/en/api/supported-regions, accessed 2026-11-04) enumerates 175 entries including Japan, Singapore, South Korea, Taiwan, United States of America; no China, Hong Kong or Macau entry.
- **Implication**: Server placement is a hard filter: Tokyo, Singapore, Silicon Valley qualify; Hong Kong does not.
- **Confidence**: high.

### F2 — Hong Kong datacentre IPs are refused; Singapore/US placements work
- **Claim**: Requests leaving from Hong Kong infrastructure receive HTTP 403 `Request not allowed` from api.anthropic.com; moving the caller to Singapore or the US clears it.
- **Evidence**: theaiinc/leyline PR #17 "Leyline runs in Singapore so Anthropic answers it" (2026-10-14), https://github.com/theaiinc/leyline/pull/17: from Cloudflare's Hong Kong colo the API returned "403 forbidden: Request not allowed … because Hong Kong falls outside Anthropic's supported regions"; fix = Worker placement `gcp:asia-southeast1` (Singapore). JingJerYen/rcsolver PR #13 (2026-10-24), https://github.com/JingJerYen/rcsolver/pull/13: Taiwanese phones "sometimes routed through Cloudflare's Hong Kong data center, which Anthropic does not service" → `403 {"type":"forbidden","message":"Request not allowed"}`; fix = placement `aws:us-east-1`. Cloudflare Community thread "AI Gateway routes to restricted regions, causing API blocks" (https://community.cloudflare.com/t/ai-gateway-routes-to-restricted-regions-causing-api-blocks/808571, body not fetchable — HTTP 403 to this fetcher; title and search summary only). Gizmodo, "How to Use Claude in Hong Kong in 2026: What Still Works" (2026-10-26): "Open Claude from a Hong Kong connection, and you get a short message saying it's only available in certain regions." Claude Code issue #30318 (opened 2026-03-03) documents the same 403 from China without a proxy; Anthropic collaborator closed it 2026-08-17 noting they "do not provide workarounds for regions where Claude isn't available".
- **Implication**: A Hong Kong VPS would need a second relay in a supported region (the runner already honours `ANTHROPIC_BASE_URL`, backend/wd/ai/runner.py:56), doubling cost and moving parts. Tokyo (Japan) is on the list but I found no explicit "Vultr/Tencent Tokyo works" test; Singapore has the leyline confirmation; the US is trivially in-region.
- **Confidence**: high for the HK block; medium-high that any ordinary Tokyo/Singapore/US VPS IP is accepted (region-based, no evidence of datacentre-IP blocking at the API).

### F3 — Claude Code OAuth login from a VPS can hit a Cloudflare challenge; API keys do not
- **Claim**: `claude login` on a Hetzner VPS failed in Jan-2026 because claude.ai answered the token exchange with a Cloudflare JS challenge; console.anthropic.com (API-key path) was unaffected.
- **Evidence**: anthropics/claude-code issue #21678 "OAuth login fails from Hetzner VPS — Cloudflare JS challenge blocks token exchange" (2026-01-29, closed "not planned" 2026-04-02), https://github.com/anthropics/claude-code/issues/21678: `curl -sS -D - -o /dev/null https://claude.ai/` → `HTTP/2 403 … cf-mitigated: challenge`; "console.anthropic.com returns HTTP 302 (OK) — only claude.ai is blocked"; alternative noted: "Use API key authentication instead of OAuth". The current Mac setup drives `claude` through bin/claude-wrapper with a hand-started SOCKS tunnel (known fact); the runner passes `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL` through (backend/wd/ai/runner.py:49-62).
- **Implication**: Plan for the API-key path on the VPS (purely technical; billing/policy is deferred). If the subscription CLI is kept, budget time for the headless-login workaround and expect it to break on token refresh.
- **Confidence**: medium (single provider report; may vary by IP reputation).

### F16 — Cloudflare Tunnel header semantics vs. the word-Dance backend
- **Claim**: cloudflared forwards the public `Host` unchanged unless `httpHostHeader` is set (then it moves the original to `X-Forwarded-Host`); it sets/appends `X-Forwarded-For` (appending the visitor at the end — open bug #1426); the Cloudflare edge adds `CF-Connecting-IP` (all plans) and `X-Forwarded-Proto` ("default value is https"). The backend already reads `X-Forwarded-Proto` for the Secure cookie and CSRF scheme when `WD_TRUST_PROXY=1`, and uvicorn trusts only 127.0.0.1 as a proxy — exactly where a same-host cloudflared connects from.
- **Evidence**: cloudflared source `ingress/origin_proxy.go` (master, fetched 2026-11-04): `if o.hostHeader != "" { // Pass the original Host header as X-Forwarded-Host. req.Header.Set("X-Forwarded-Host", req.Host); req.Host = o.hostHeader }` — i.e. no rewrite by default; docs "Origin parameters": `httpHostHeader` "Default: """, "Sets the HTTP Host header on requests sent to the local service."; docs "Cloudflare HTTP headers" (updated 2026-10-28): "CF-Connecting-IP provides the client IP address connecting to Cloudflare to the origin web server" (all plans), "X-Forwarded-Proto is used to identify the protocol (HTTP or HTTPS) that a visitor used to connect to Cloudflare" (default https); cloudflared issue #1426 (2025-02-27, open): "X-Forwarded-For: a,b,c,d,e,f,g,203.0.113.1" instead of prepending. Backend: backend/wd/cli.py:147-148 (`proxy_headers=cfg.trust_proxy, forwarded_allow_ips="127.0.0.1"`), backend/wd/security.py:214-223 (Secure cookie from `X-Forwarded-Proto` behind a trusted proxy), backend/wd/deps.py:81-105 (client IP = right-most non-trusted XFF hop; scheme from `X-Forwarded-Proto`), backend/wd/main.py:159; docs/DEPLOY.md:117 (`--with-caddy` sets `WD_HOST=127.0.0.1`, `WD_PUBLIC_URL=https://DOMAIN`, `WD_TRUST_PROXY=1`).
- **Implication**: A tunnel on the Mac is a config-only change (`WD_TRUST_PROXY=1`, `WD_PUBLIC_URL=https://…`, cloudflared → `http://127.0.0.1:8000`); the right-most-XFF rule even tolerates #1426. The problem is not correctness but mainland reachability (F17).
- **Confidence**: high.

### F20 — GFW risk profile of a small private HTTPS site on an overseas IP
- **Claim**: Blocking happens by DNS pollution, IP blacklisting, SNI RST injection or throttling; SNI blocking is keyed on domain+IP with IP taking priority (an IP "认证" as bad blocks every domain on it); ordinary sites are rarely blocked unless the box also carries proxy traffic or shares a tainted range (Cloudflare edge IPs are the canonical example); mitigations are a clean IP, no proxy software, non-default SSH port, short DNS TTL so a re-IP propagates in minutes, and avoiding shared CDN ranges for mainland users.
- **Evidence**: gfw.report "Exposing and Circumventing China's Censorship of ESNI" (2020-08-07): "GFW审查SNI和HTTP的方式是向服务器和客户端注入伪造的TCP RST", residual blocking "有时持续120秒，有时持续180秒", "没有ESNI和SNI扩展的TLS ClientHello不能触发封锁"; flyzyblog.net provincial SNI post (2023-04-21): "IP triggers take priority—if an IP is 'authenticated' as problematic, multiple domains hosted there all trigger SNI blocking" (Fujian worst; Jiangsu/Ningxia/Guizhou/Shandong/Hainan mentioned); freex.cc (2025-10-27) enumerates "DNS 污染 / IP 封锁 / SNI 阻断 / TCP 重置" with diagnosis commands; V2EX t/941418: "Cloudflare的ip端都是公开的，被GFW收集然后定向监控，是非常容易的事情"; V2EX 2024–25 threads (t/1124979, t/1173454, t/719625) — consensus in search summary: IPs get blocked "specifically when used for tunneling circumvention traffic", legitimate sites usually fine; prior slice china-compliance-hosting F29 (low) recommends clean dedicated IP + re-IP ability + short TTL.
- **Implication**: For ≤10 friends the residual risk is "site unreachable until re-IP" (hours), not legal exposure; Tencent/Alibaba overseas IPs are also less likely to sit in proxy-abused ranges than cheap US VPS pools, though no data proves it.
- **Confidence**: medium (practitioner consensus; no measurable base rate exists).
