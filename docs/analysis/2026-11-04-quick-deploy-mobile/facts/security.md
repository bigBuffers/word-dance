# Security slice — what must be fixed before inviting ≤ 10 trusted friends to a public HTTPS domain

Scope: word-Dance @ git main 9ab13a5, verified 2026-11-04 against the code (file:line below), the docs, the read-only DB snapshot `scratchpad/quick/live-copy.db` (copy of the Mac's live DB) and one web source (Caddy docs). Policy / model-licensing questions are out of scope by owner decision. Audience assumption throughout: a trusted circle of ≤ 10 invited friends, mostly on mainland-China phones.

## Summary

- Nothing in the code must change before inviting ≤ 10 trusted friends. Every "must" item is configuration or an operating procedure: close the admin-bootstrap window (create the admin before DNS, or migrate the existing DB which already has the admin), run behind a same-host Caddy with `WD_TRUST_PROXY=1`, `WD_HOST=127.0.0.1`, `WD_PUBLIC_URL=https://…`, keep `WD_REGISTRATION_MODE=invite` with one single-use invite code per friend, use a strong admin password (there is no 2FA), and raise the AI caps (defaults $3/day, $40/month are enough per day but the month cap will be hit in weeks 2–4 and then defers all AI to the 1st of next month).
- The baseline that already exists is solid for this audience: CSP/HSTS/nosniff/frame-deny headers, HttpOnly+Lax(+Secure) 30-day sliding session cookie with sha256-stored tokens, custom-header CSRF rule, bcrypt-12 with a common-password list and constant-time unknown-user checks, persistent per-IP/per-user throttles and a per-username lockout, 1 MiB body cap, DNS-pinned SSRF guards, cookie-gated `/media`, server-side word visibility, 0700 data dir, masked secrets, admin kill switch/pause and global budget reservations.
- Only four routes answer without a session: `POST /api/auth/login`, `POST /api/auth/register`, `GET /api/health` and the SPA/static files (the `/media/images/*` route checks the cookie inside its handler); 71 other API routes require `current_user`, 21 of them `require_admin`.
- Lockout facts: key `login:user:<username lower-cased>`, 10 failures → 15 min, doubling every 5 more failures, 24 h maximum (reached at the 45th failure); there is no `wd unlock`; the fix is one `DELETE FROM auth_throttle WHERE key='login:user:<name>'` which can run while the service is up (WAL + 5 s busy_timeout).
- Per-IP login throttle (20 per 10 min) counts successful logins and registration is 5 per hour per IP; among friends this only bites when several of them register/log in from one Wi-Fi within the window — and it becomes SITE-WIDE if a proxy is used without `WD_TRUST_PROXY=1` (every visitor is then 127.0.0.1).
- AI exposure is bounded by construction, but one friend can enqueue every seed word lacking content (9,114 words, 92 batch-mark requests, < 1 min) with no per-user quota; among friends this is an accident-proof, zero-incentive path, and the admin can pause AI for 24 h or cancel the queue with SQL.
- The live Mac instance shows the photo providers are unreachable from that network (Wikimedia SSL EOF, Openverse timeouts): 30 of 31 active images are Claude SVGs and all 48 image fetches failed. If the production host behaves the same, every studied word costs an SVG ($0.012) up to the $0.50/day sub-cap and the rest get text-only cards — size the SVG cap (or turn it off) deliberately.
- Prewarm is optional for the daily-batch flow (content is generated at batch build, ≤ 3 h before push) but improves 筛词/词库 browsing; the friends' stages decide the bill: zk $9–12, zk+gk $18–21, zk+gk+cet4 $24–30, all 9,114 words $41–50 at $0.0045–0.0055/word, ≈ 600 words per hour at the 60 calls/h cap.

## Findings

### F1 — What already protects the service (baseline is adequate for a trusted circle)

- Claim: Every response carries CSP `default-src 'self' …; frame-ancestors 'none'`, nosniff, Referrer-Policy same-origin, X-Frame-Options DENY, Permissions-Policy, `Cache-Control: no-store` on `/api`, and HSTS (`max-age=31536000; includeSubDomains`) when the request is https or `WD_PUBLIC_URL` is https. Sessions are `secrets.token_urlsafe(32)` cookies `wd_session; HttpOnly; SameSite=Lax; Path=/; Max-Age=30 d` (Secure per F6), stored as sha256, capped at 20 per user, slid once per day. Every non-GET `/api` call needs `X-WD-Request: 1` and, when an Origin header is present, an Origin equal to the Host-derived or `WD_PUBLIC_URL` origin. Passwords are bcrypt cost 12, 8–64 chars, not the username, not in a 1k common list; unknown users are checked against a dummy hash. Bodies are capped at 1 MiB (Content-Length pre-check plus a streaming guard). `/media/images/<path>` accepts only `^[0-9a-f]{2}/[0-9a-f]{64}\.(jpg|svg)$` and then requires the cookie; the SPA fallback confines paths to the dist dir. Word visibility is enforced in SQL (`is_public OR created_by_user_id = me OR holder`). Outbound image/webhook fetches reject loopback/private/link-local/CGNAT/reserved addresses and pin the resolved IP. The serve process forces umask 0077, the data dir is 0700, secrets are masked in `GET /api/admin/config`. AI spend is gated per call by an atomic reservation against hourly/daily/monthly caps plus an admin pause and a kill switch.
- Evidence: backend/wd/main.py:93-103,159,168-177,184-211,242-268; backend/wd/security.py:56-60,62,98-122,137-147,174-192,229-238; backend/wd/deps.py:111-129,142-181,201-216; backend/wd/routers/media.py:26,38-48,51-57; backend/wd/images/fetch.py:46,101-107; backend/wd/security.py:489-525; backend/wd/cli.py:135; backend/wd/config.py:44-53,393-394,419-423; backend/wd/ai/budget.py:187-285; prior slice docs/analysis/2026-11-03-public-launch/facts/public-readiness.md §10, §13 (SSRF/SVG details not re-verified line by line here beyond fetch.py:101-107).
- Implication: No hardening work is a prerequisite for ≤ 10 trusted friends; the remaining risks are operational (F3, F5, F6) and cost/availability (F7–F11).
- Confidence: high.

### F2 — The unauthenticated surface is four routes plus the SPA

- Claim: Introspecting the FastAPI dependency trees of all 75 API routes (scratch script over `wd.main.ROUTERS`, 2026-11-04) gives: no auth dependency on `POST /api/auth/login`, `POST /api/auth/register`, `GET /api/health`, `GET /media/images/{path}`; 41 routes depend on `current_user`, 9 on `require_onboarded`, 21 on `require_admin`. The media route is nevertheless cookie-gated because it calls `current_user(request, conn)` inside the handler after the path regex (malformed path → 404 before auth). The SPA route `GET /{path:path}` serves `index.html`/assets without auth and refuses `/api*` and `/media*`. `/api/docs` and `/api/openapi.json` exist only under `WD_DEV=1`. `GET /api/health` publicly reveals `version`, `registration_mode` and `needs_setup`. The CSRF header rule applies to login/register too (the SPA sends it).
- Evidence: backend/wd/routers/auth.py:79,120; backend/wd/routers/health.py:24-44; backend/wd/routers/media.py:38-48 (auth at :42); backend/wd/main.py:242-268,529-531,188-192; introspection counts: `Counter({'current_user': 41, 'current_user,require_admin': 21, 'current_user,require_onboarded': 9, 'NONE': 4})`.
- Implication: The anonymous attack surface is login/register (both throttled, F4/F5) and static files; keep `WD_DEV` unset in production.
- Confidence: high.

### F3 — Admin bootstrap race and how to close it

- Claim: Inside one `BEGIN IMMEDIATE`, `POST /api/auth/register` makes the registrant `admin` whenever `SELECT COUNT(*) FROM users` is 0 — in ANY registration mode (the `closed`/`invite` checks run only in the `else` branch) and without an invite code; `/api/health` advertises `needs_setup: true` meanwhile. The window is "from the first `wd serve` on an empty DB until the first registration". Concurrent duplicates are handled (exactly one admin). Closing procedures, all zero-code: (a) set `WD_ADMIN_USERNAME`/`WD_ADMIN_PASSWORD` in `.env` before the first `deploy/install.sh` run — step `wd create-admin --if-none` (install.sh:144) runs BEFORE the unit is (re)started (:158) and before Caddy is configured (:168-170), so there is no window; then remove `WD_ADMIN_PASSWORD` from `.env` (env.example:125; DEPLOY.md:340) and restart so it leaves the process environment (it is masked in `/api/admin/config` but lingers in the 0600 file); (b) or run `wd create-admin --username <u>` (interactive prompt) before DNS/443 is opened; (c) or register from the box: `curl -H 'X-WD-Request: 1' -H 'Content-Type: application/json' -d '{"username":"…","password":"…"}' http://127.0.0.1:8000/api/auth/register`; (d) migrating the existing Mac DB (1 user, role admin, id 1 — live-copy.db `users`) closes the race by construction. Verify with `GET /api/health` → `needs_setup:false` before sharing the URL.
- Evidence: backend/wd/routers/auth.py:88-98; backend/wd/routers/health.py:42; backend/wd/security.py:734-766 (cmd_create_admin, `--if-none` :738-740, WD_ADMIN_PASSWORD default :756, :703-731); deploy/install.sh:144,158,168-170,181; deploy/env.example:125-127; backend/wd/config.py:44-53; backend/tests/integration/test_auth.py:186-190 (two racing first registrations → one admin).
- Implication: A 10-minute procedure; the only way to lose the admin seat is to expose the empty service first.
- Confidence: high.

### F4 — Username lockout: exact key, schedule, maximum, and the unlock statement

- Claim: Failed logins are counted per username in `auth_throttle` under key `login:user:<username.strip().lower()>` (usernames are `COLLATE NOCASE`, so case variants share one lock). `lock_seconds_for(n)` locks on the 10th consecutive failure for 15 min and doubles every further 5 failures, capped at 24 h: #10 → 15 min, #15 → 30 min, #20 → 1 h, #25 → 2 h, #30 → 4 h, #35 → 8 h, #40 → 16 h, #45 → 24 h, every 5 thereafter → 24 h. Failures 11–14 (after the first lock expired) return 401 but do not lock. While locked, `check_lockout` runs BEFORE `record_login_failure`, so hammering a locked name returns 423 and does not extend the lock; the correct password is also refused (423 `account_locked`, `Retry-After`, `details.retry_after_s`; the SPA shows 「登录失败次数过多，请 N 分钟后再试」). The streak persists until a successful login deletes the row, or until `window_start` (the first failure of the streak) is > 24 h old with no active lock; the scheduler's hourly GC deletes rows whose lock is over and whose `window_start` is older than one day. There is no `wd unlock` (grep `unlock` over backend/wd: nothing). Admin unlock, identical to `clear_login_failures`:
  `sqlite3 /path/to/word-dance-data/word-dance.db "DELETE FROM auth_throttle WHERE key = 'login:user:alice';"`
  (run as the service user — the DB is 0600; Python fallback when the `sqlite3` binary is absent: `.venv/bin/python -c "import sqlite3;c=sqlite3.connect('…/word-dance.db');c.execute(\"DELETE FROM auth_throttle WHERE key='login:user:alice'\");c.commit()"`). The service does NOT need to stop: journal_mode is WAL (persistent in the file) and every app connection uses `busy_timeout=5000`, so a one-row DELETE from another process only makes a concurrent writer wait milliseconds. Anyone who knows a username can lock it (no IP component in the key); usernames are not exposed to other users by any route (admin pages only), so among friends this is a nuisance, not a risk.
- Evidence: backend/wd/security.py:78-82 (constants), 282-283 (key), 297-301 (423), 304-308 (schedule), 311-335 (streak/lock logic), 338-339 (DELETE); backend/wd/routers/auth.py:125-137 (order: rate_limit → check_lockout → verify → record failure; clear on success); backend/wd/jobs/scheduler.py:169-190 (hourly GC, throttle prune :179-182); backend/wd/db.py:43-48 (WAL, busy_timeout); backend/wd/errors.py:61,109; frontend/src/api/client.ts:203-204, frontend/src/i18n/zh.ts:17; docs/SCHEMA.sql:113-123; tests backend/tests/integration/test_auth.py:236-257, backend/tests/unit/test_security.py:129-133.
- Implication: Tell friends "10 wrong passwords = 15 minutes"; keep the one-line SQL handy; the lock always expires by itself within 24 h.
- Confidence: high.

### F5 — Per-IP login/registration throttles: arithmetic for friends behind one NAT

- Claim: `POST /api/auth/login` calls `rate_limit(login:ip:<ip>, 20 per 600 s)` at auth.py:125, BEFORE `check_lockout` (:126) and `verify_password` (:129) — so every login POST counts, successful ones included; pinned by test_auth.py:260-267 (20 failed logins for other names, then alice's CORRECT password → 429 `retry_after_s` 600). `POST /api/auth/register` is 5 per 3600 s per IP (auth.py:84; test :193-200). Both limits are constants (security.py:72-73) with no env knob. The IP is the TCP peer, or — only when `WD_TRUST_PROXY=1` AND the peer is 127.0.0.1/::1 — the client address the local proxy appended to `X-Forwarded-For` (uvicorn `forwarded_allow_ips="127.0.0.1"`, deps.py:78-96; cli.py:147-148). Arithmetic for ≤ 10 friends: (i) invite evening on one home/office Wi-Fi: the 6th registration within an hour gets 429 (`Retry-After` ≤ 3600) — 10 friends need two hours or two networks (mobile data is a different IP); (ii) logins: 10 friends × 2 devices = 20 logins fit in one 10-minute window exactly; the 21st — or any failed attempts on top — gets 429 for ≤ 10 min; sessions last 30 days sliding, so after launch night logins are rare; (iii) carrier CGNAT in mainland China: 10 friends in different places practically never share one public IPv4 within a 10-minute window, and IPv6 gives per-device addresses; (iv) THE real failure mode: a reverse proxy/tunnel with `WD_TRUST_PROXY` unset → every visitor is 127.0.0.1 → 5 registrations per hour and 20 logins per 10 minutes for the whole site. install.sh `--with-caddy` sets `WD_TRUST_PROXY=1` (DEPLOY.md:117); a hand-made setup (e.g. the Mac, where `WD_PUBLIC_URL` is empty) must set it by hand.
- Evidence: backend/wd/routers/auth.py:84,125-129; backend/wd/security.py:72-73,250-279; backend/wd/deps.py:37,78-96; backend/wd/cli.py:146-148; backend/tests/integration/test_auth.py:193-200,260-267; backend/tests/integration/test_deps.py:81-82 (XFF resolution); docs/DEPLOY.md:117,306.
- Implication: Zero-code mitigations: stagger registrations or use mobile data; one login per device; verify `WD_TRUST_PROXY=1` by checking that `sessions.ip` (or the `login:ip:*` keys) show real client addresses after the first friend logs in. Code fix (A8, "do not count successes / move to per-account") is 0.5 day and can wait.
- Confidence: high.

### F6 — HSTS and Secure-cookie preconditions behind Caddy

- Claim: `Secure` is set when `WD_COOKIE_SECURE=1`, or (auto) when `WD_PUBLIC_URL` starts with `https://`, or the request scheme is https, or `WD_TRUST_PROXY=1` and the first `X-Forwarded-Proto` value is `https`. HSTS is appended under the same conditions (`is_https or cfg.public_url_is_https`). With `WD_TRUST_PROXY=1` the raw `X-Forwarded-Proto` header is read without checking the peer, so `wd serve` must stay bound to `127.0.0.1` (install.sh writes `WD_HOST="127.0.0.1"`, `WD_PUBLIC_URL="https://DOMAIN"`, `WD_TRUST_PROXY="1"` in `--with-caddy` mode). Caddy's `reverse_proxy` "sets or augments the `X-Forwarded-For` header field. It sets the `X-Forwarded-Proto` header field. It sets the `X-Forwarded-Host` header field" and "by default, the proxy will ignore their values from incoming requests, to prevent spoofing" (caddyserver.com/docs/caddyfile/directives/reverse_proxy, accessed 2026-11-04), so the shipped `deploy/Caddyfile.example` (`reverse_proxy 127.0.0.1:8000`, 2 MB body cap) needs no header directives. Pitfalls: with `WD_PUBLIC_URL=https://…` the cookie is Secure for ALL requests, so a friend reaching the box over plain http (LAN IP) cannot stay logged in — fine, since the proxy mode binds 127.0.0.1 anyway; HSTS is one year with `includeSubDomains` (affects sub-domains of the app host only); the CSRF Origin allow-set is the Host-derived origin plus `WD_PUBLIC_URL`'s origin, so the domain in `WD_PUBLIC_URL` must be the one friends type.
- Evidence: backend/wd/security.py:213-226; backend/wd/config.py:145-156; backend/wd/main.py:159,171-172; backend/wd/deps.py:104-107,126; deploy/install.sh:117; deploy/Caddyfile.example:1-6; docs/DEPLOY.md:302-307,360-386; prior slice auth-contract-4/-18.
- Implication: Must-before-invite checklist: `WD_HOST=127.0.0.1`, `WD_TRUST_PROXY=1`, `WD_PUBLIC_URL=https://<domain>`; then `curl -si https://<domain>/api/health | grep -i strict-transport` and a login's `Set-Cookie` must contain `; Secure`.
- Confidence: high (Caddy default from its docs; cloudflared/other tunnels not verified).

### F7 — Per-user quotas that exist, the mark path that has none, and the mass-mark worst case

- Claim: Persisted per-user daily (UTC day) quotas: custom adds 200/day (token-counted, shared with imports, ≤ 50 tokens per call), study-today extras 20/day, explicit content requests 60/day, image refresh 20/day, reports 20/day, password re-checks 10 per 15 min, and 300 non-GET requests per minute per user counted in `current_user`. Content generation triggered by marking a validated word unfamiliar/re-adding it (`_apply_unfamiliar` → `enqueue_content_if_needed`) has NO quota; the same path is used by screening verdicts (priority 20), the daily batch build (priority 20 for every push item, `screen` kind included), prefetch (priority 30, ≤ 50/user, skipped at ≥ 50 % spend), consolidation suggestions, and custom-word lookups (priority 10). A client-chosen `context` of `detail`/`today` yields priority 10 (same as explicit requests). Queue order is `priority, run_after, id` — strict priority, then FIFO. Worst case: `POST /api/words/batch-mark` takes ≤ 100 ids per request and is one mutation, so one account can enqueue content for every word lacking it — the whole missing seed is 9,114 words = 92 requests ≈ 19 s at 300/min — at priority 20 (context `browse`). That is 912 ten-word calls ≈ 15.2 h of worker time at 60 calls/h, $41–50 at $0.0045–0.0055/word, i.e. 14–17 days of the default $3 daily cap and past the $40 monthly cap on day ~13, after which everything (including other friends' priority-10 requests) defers to 00:05 WD_TZ on the 1st of next month. Other friends' batch jobs (also priority 20) are not out-prioritised but queue FIFO behind the flood and then hit the same daily cap; their "I am looking at this word" requests (priority 10) still jump ahead while the day's budget lasts. Among ≤ 10 friends: the path requires the desktop vocab page's bulk selection or the API, has no incentive, and is visible immediately in 概览 (`jobs.queued`, `ai.today_usd`). Zero-code counter-measures: admin AI pause (24 h, `POST /api/admin/ai/pause`) — note it pauses everyone — or cancel the flood with SQL mirroring `prewarm.cancel_leftovers`/`queue.cancel`:
  `UPDATE jobs SET status='cancelled', finished_at=strftime('%Y-%m-%dT%H:%M:%SZ','now'), updated_at=finished_at, locked_at=NULL, locked_by=NULL WHERE type='generate_content' AND status='queued' AND priority>=20;`
  `UPDATE words SET content_state='none' WHERE content_state='queued' AND NOT EXISTS (SELECT 1 FROM jobs j WHERE j.dedupe_key='content:'||words.id AND j.status IN ('queued','running'));`
  (the partial unique index on live dedupe keys covers only `queued`/`running`, so cancelled rows do not block re-enqueue).
- Evidence: backend/wd/services/bank.py:45,54-65,267-302,465-478,606-642 (:618,:641); backend/wd/routers/words.py:114-136,243-255,271,296,326; backend/wd/routers/bank.py:103-105,123,182-184; backend/wd/security.py:76-77,371-373; backend/wd/deps.py:177-180; backend/wd/schemas.py:651-654,670; backend/wd/services/screen.py:222-234; backend/wd/services/batches.py:45,639; backend/wd/jobs/scheduler.py:54-56,256,285-289; backend/wd/ai/lookup.py:51,487; backend/wd/jobs/queue.py:139,154,288-300; backend/wd/ai/prewarm.py:113-125; docs/SCHEMA.sql:491,503; backend/wd/routers/admin_ops.py:314-333; live-copy.db: 9,114 words with `content_state IN ('none','failed')`.
- Implication: A1/A2 (per-user AI quota + admin cancel) stay "later" for a trusted circle; what matters is that the admin looks at 概览 occasionally and knows the pause/SQL moves.
- Confidence: high.

### F8 — Global AI budget arithmetic for 10 friends

- Claim: Mechanics: `can_spend` checks kill switch → pause → hourly cap (60 calls of ANY kind in the last 60 min) → monthly cap → daily cap (`SUM(cost_usd)` of today's WD_TZ-day calls + running reservations; content reserved at `0.005 + 0.0045 × words`) → prewarm sub-cap (priority ≥ 90 only: `prewarm_spent_today < $1` and `spent_today < 50 %` of daily) → SVG sub-cap ($0.50/day, counted inside the daily cap). Refusal never fails a job: the group is `queue.defer`red to `resumes_at` = next day 00:05 WD_TZ (daily/prewarm/svg), the 1st of next month 00:05 (monthly) or next hour + 1 min (hourly); `system_events` `budget_daily`/`budget_monthly`/`budget_svg` are written once per day; the explicit request endpoint answers 409 `budget_exhausted` with `resumes_at`; detail/content endpoints expose `deferred_until` (the live job's far `run_after` or `paused_until`) and the SPA shows 「今日 AI 额度已用完，例句将在明天补齐」 and stops polling. The daily batch is still built and published (ECDICT definition + card). Capacity: 60 calls/h × 10 words = 600 words/h ≈ $2.70–3.30/h, so continuous demand drains the $3 daily cap in 55–67 min; $3/day ≈ 545–667 words/day; $40/month = 13.3 full days. Typical demand, 10 friends, defaults `daily_new_count 10`, `daily_screen_count 15` (both kinds get content at batch build), no prewarm: batch content ≤ 10 × 25 = 250 words/day = 25 calls = $1.13–1.38 as an upper bound, realistically 50–150 unique words/day ($0.25–0.83) because screening order is deterministic per stage (stage distance, then frequency) and new words enter banks only through screening verdicts and custom adds; custom words at 1–4 per friend per day: lookups $0.01–0.05 (20 strings per call) plus content in small groups at the measured $0.009–0.018/word → $0.09–0.72; SVG fallbacks up to the $0.50 sub-cap when photos miss (F10); nightly consolidation ≤ 10 × $0.016–0.024 measured ($0.05 reserved) → $0.16–0.50, only for banks that changed; prefetch mostly overlaps batch words. Week-1 total ≈ $0.6–2.5/day (upper bound ≈ $3.1 = the default cap), settling to ≈ $0.5–1.5/day as the shared cache fills → $20–60 in month 1. So the daily default suffices on most days with little headroom, and the $40 monthly cap is likely reached in weeks 2–4, which would silently defer all AI for everyone until the 1st (with "tomorrow" copy, F17). Recommended caps for 10 friends: `WD_AI_DAILY_BUDGET_USD=6`, `WD_AI_MONTHLY_BUDGET_USD=100` (hard ceiling $180/month, realistic $25–60), keep `WD_AI_HOURLY_CALL_CAP=60` as the runaway guard (90 if morning SVG bursts defer content), `WD_AI_SVG_DAILY_BUDGET_USD` 1.00 (≈ 80 cards) or 0 (text cards, no SVG spend) depending on F10, prewarm sub-cap back to 1.00 after any prewarm. Settings are read at process start, so a restart applies them. Hourly-cap interplay: SVG calls are one word each; 25 content + 40 SVG calls in one morning hour exceed 60 and the tail defers to the next hour.
- Evidence: backend/wd/ai/budget.py:29-37,88-110,169-170,187-235; backend/wd/ai/ledger.py:142-147; backend/wd/ai/common.py:146-169; backend/wd/routers/words.py:184-185,219-223,327-329; backend/wd/services/bank.py:233-238; backend/wd/errors.py:53; frontend/src/i18n/zh.ts:18,39; frontend/src/pages/WordDetailPage.tsx:139,349; backend/wd/config.py:103-107; docs/SCHEMA.sql:144-145; backend/wd/services/batches.py:60-61,243-274,639; backend/wd/jobs/scheduler.py:194-239,243-294; docs/CLAUDE_INTEGRATION.md:395-414.
- Implication: Raise daily/monthly caps before inviting; watch 概览 `today_usd`/`month_usd` weekly; the SVG decision depends on whether photos work from the production host.
- Confidence: medium for the demand model (assumption-driven), high for the mechanics and capacities.

### F12 — Shared image replacement rule (threshold 1)

## Recommendations

1. Launch-day procedure (≈ 1 hour, zero code): install with `deploy/install.sh --with-caddy <domain>` after putting `WD_ADMIN_USERNAME`/`WD_ADMIN_PASSWORD` (or the migrated DB) in place; confirm `/api/health` → `needs_setup:false`; remove `WD_ADMIN_PASSWORD` and restart; curl-check HSTS and `Set-Cookie … Secure`; set `WD_AI_DAILY_BUDGET_USD=6`, `WD_AI_MONTHLY_BUDGET_USD=100`, choose the SVG cap; create one `--uses 1 --days 7` invite per friend; send the invite with three sentences (10 wrong passwords lock 15 min; 换一张 changes the picture for everyone; words/notes are processed by Anthropic, export/delete in 设置).
2. Before the invites go out (2–4 h of wall time per stage, $5–11 per stage for the top 1,000–2,000 words; $41–50 for everything): prewarm the stages the friends will pick, with the temporary cap raise described in F11, then restore the caps.
3. First week: look at 概览 once a day (today/month spend, queued jobs, provider cooldowns, events `budget_*`/`claude_auth`); after the first friend logs in, check that `sessions.ip` shows a real client address (proves `WD_TRUST_PROXY` works).
4. First month (≈ 2 days total): A8 stop counting successful logins / per-account keying (0.5 d); external uptime ping + off-site backup cron (0.5–1 d); show the real `deferred_until` date instead of "tomorrow" (0.2 d); optionally a `wd unlock <username>` command (0.2 d).
5. Only if the circle grows beyond friends: per-user AI quota + admin "cancel user's queue" (A1/A2, 2–3 d), lockout keyed by username+IP with CAPTCHA (A4, 1 d), image vote threshold (A7, 1 d), password reset by e-mail (A6, 1–2 d), ToS/privacy pages (B1–B4), word curation tools (B5, 3–5 d), admin TOTP (2–3 d).

## Open questions

- Which stages will the friends study (zk/gk for children, cet4/cet6 for adults)? It decides the prewarm bill ($9–12 for zk up to $41–50 for everything) and the overlap that keeps daily content cost low.
- Will the existing Mac DB (1 admin, 52 user_words, 48 ready words) be migrated to the public host? If yes the bootstrap race is closed by construction and the owner's bank carries over; if not, the create-admin step is mandatory.
- Where does TLS terminate? Same-host Caddy is verified to work with `WD_TRUST_PROXY=1`; a tunnel (cloudflared/frp) or a cloud LB on another host makes every per-IP limit site-wide unless `forwarded_allow_ips`/`TRUSTED_PROXY_PEERS` change — and whether those set `X-Forwarded-Proto: https` was not verified.
- Are Wikimedia/Openverse reachable from the production host? The Mac shows SSL EOF/timeouts and an SVG-only image mix; the answer sets the SVG cap and whether keyed providers are worth configuring.
- What monthly AI spend is acceptable? The recommended caps bound it at $180/month (realistic $25–60); the default $40/month will be reached mid-month and silently defer AI for everyone.
- Will any friend be a minor? Then the invite message should carry a parental-consent sentence even for a trusted circle (no age gate exists).
- Should the admin pre-create friend accounts (`create-admin` + `demote`) to avoid the 5/h/IP registration limit on a shared Wi-Fi, or is staggering registrations acceptable?
- Is the "tomorrow" deferral copy acceptable until the monthly cap is raised, or should the date fix ship before inviting?
