# clivps — Running the project's `claude -p` runner on a Linux VPS (technical facts, 2026-11-04)

Scope: Linux installation of the Claude Code CLI, non-interactive credentials and where they live, the print-mode flags the repo uses, `--bare`, the `sonnet` alias, proxy / base-URL support, and exactly how an operator injects each credential type into the systemd service **without changing code**. Policy and credential-choice questions are deferred by the owner and are not analysed here. One neutral sentence on what exists: the CLI resolves, in this precedence order, cloud-provider credentials, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, an `apiKeyHelper` command, `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), Anthropic profile / federation credentials, and the claude.ai login that `/login` stores on disk (authentication.md, "Authentication precedence", accessed 2026-11-04).

All web sources were read on 2026-11-04 from code.claude.com/docs (the `.md` sources were also downloaded to the scratchpad for grep), the Claude Code CHANGELOG on GitHub, the npm registry, downloads.claude.ai and freedesktop.org. Repo facts refer to git main @ 9ab13a5. No real `claude` binary was executed and no money was spent; the two runtime experiments used `backend/tests/fake_claude.py` in a scratch data dir that was deleted afterwards.

## Summary

1. Current CLI: latest **2.1.318** (published 2026-11-03), stable channel **2.1.311** (2026-10-26); the native installer puts a launcher symlink at `~/.local/bin/claude` → `~/.local/share/claude/versions/<v>`, pins with `bash -s 2.1.311`, auto-updates unless `DISABLE_AUTOUPDATER=1`; a signed apt repo exists and installs a single 294 MB `/usr/bin/claude` (no auto-update).
2. On Linux a subscription login lives in `~/.claude/.credentials.json` (0600) under `$HOME` or `$CLAUDE_CONFIG_DIR`; there is no keychain, so the same Unix user's systemd service reads it as long as `HOME` is set and writable (the unit already does this). The macOS `USER/LOGNAME/TMPDIR` quirk is Keychain-specific and does not apply.
3. The runner builds the child env from an allow-list: `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, proxies, `SSL_CERT_*`, `CLAUDE_CONFIG_DIR`, `XDG_*` pass through; **`CLAUDE_CODE_OAUTH_TOKEN`, `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_EFFORT_LEVEL`, `NODE_EXTRA_CA_CERTS` do not**. `.env` may contain only `WD_*` lines (install.sh aborts otherwise). Therefore: `ANTHROPIC_*` → a second `EnvironmentFile=` in a systemd drop-in; everything else → a wrapper script named by `WD_CLAUDE_BIN` (exactly what the Mac does). Both paths were exercised with the fake binary: a variable exported in the service environment never reached the child; the same variable exported by a wrapper did.
4. `--bare` is still **not** the `-p` default in 2.1.318 (docs: "will become the default for `-p` in a future release"); it never reads OAuth credentials or `CLAUDE_CODE_OAUTH_TOKEN`, so the repo's "never `--bare`" rule is right for file-stored logins and wrong only once a static key is in use.
5. `sonnet` resolves to **Sonnet 5.5 = `claude-sonnet-5-5`** on the Anthropic API since 2.1.284 (the live DB shows `model_used = claude-sonnet-5-5` for all 49 successful calls); its default effort is `medium`; `--effort` exists; `CLAUDE_CODE_EFFORT_LEVEL` is stripped by the runner, so use `WD_AI_EXTRA_ARGS="--effort low"`.
6. HTTP(S)_PROXY / NO_PROXY are honoured, **SOCKS is not supported** (hence the Mac's privoxy front); `ANTHROPIC_BASE_URL` reroutes requests but, alone, keeps the saved login as the credential. A proxy must never be put in the whole service environment (it breaks the image pipeline) — wrapper only.
7. `wd claude-check` is the acceptance test: tier-1 then tier-0 probe (≤ $0.05 budget each, measured $0.002–0.007), prints `claude check OK: tier N, cost $…, model <id>, claude <version>` (exit 0) or `claude check FAILED: tier 1: …; tier 0: …` (exit 2), and records `kv.claude.{flag_tier,available,last_probe_at,version}` plus `ai_calls` rows and raw logs.
8. The auth classifier catches every documented `-p` login/401 string but files org-disabled, apiKeyHelper, 403 "Request not allowed" (network/region block), connection refused and low-credit messages as plain per-job `error` (no pause, no banner); banner/hint texts hard-code "run `claude` as sqin".

## Findings

### F1 — Linux installation methods, binary locations and version pinning (Nov 2026)
- **Claim.** Three supported Linux routes: (a) native installer `curl -fsSL https://claude.ai/install.sh | bash`, which downloads from `downloads.claude.ai/claude-code-releases`, verifies the manifest checksum and runs the binary's own `install` subcommand; the launcher is `~/.local/bin/claude`, a symlink into `~/.local/share/claude/versions/`; channel or exact version pin: `bash -s stable` / `bash -s 2.1.311`; the installer refuses to run under `sudo` from a user shell. (b) Signed apt/dnf/apk repositories (`https://downloads.claude.ai/claude-code/apt/{stable,latest}`), package `claude-code`, which installs one file `/usr/bin/claude` (294 MB, `Depends: libc6 (>= 2.17)`), newest in the stable repo today 2.1.311-1; package-manager installs do not auto-update. (c) `npm install -g @anthropic-ai/claude-code` installs the same native binary via a per-platform optional dependency (`@anthropic-ai/claude-code-linux-x64`, `…-linux-arm64`, musl variants); Node 22 is needed only for npm. Current versions: latest **2.1.318** (npm publish time 2026-11-03T21:55Z; `downloads.claude.ai/claude-code-releases/latest` returns `2.1.318`), stable **2.1.311** (2026-10-26T19:47Z). System requirements list Ubuntu 20.04+/Debian 10+, 4 GB RAM, x64/ARM64.
- **Evidence.** https://code.claude.com/docs/en/setup (2026-11-04): "On macOS and Linux, the native installer manages the launcher at `~/.local/bin/claude` as a symlink into `~/.local/share/claude/versions/`"; "To install a specific version number: `curl -fsSL https://claude.ai/install.sh | bash -s 2.1.89`"; "Claude Code publishes signed apt, dnf, and apk repositories … Package manager installations do not auto-update through Claude Code"; "The npm package installs the same native binary as the standalone installer … The installed `claude` binary does not itself invoke Node." Installer script https://claude.ai/install.sh (downloaded 2026-11-04) lines 13–26: "Refuse to run under sudo from a regular user's shell … `Error: do not run this installer with sudo.`", line 38 `DOWNLOAD_BASE_URL="https://downloads.claude.ai/claude-code-releases"`, line 226 `"$binary_path" install ${TARGET:+"$TARGET"}`. `https://downloads.claude.ai/claude-code-releases/latest` → `2.1.318`, `/stable` → `2.1.311` (curl 2026-11-04). apt index `…/apt/stable/dists/stable/main/binary-amd64/Packages` newest `Version: 2.1.311-1`; `claude-code_2.1.311-1_amd64.deb` contents: `./usr/bin/claude` (293,776,752 bytes), `./usr/share/doc/claude-code/copyright`; control: `Depends: libc6 (>= 2.17)`. npm packument `time` (2026-11-04): 2.1.318 → 2026-11-03, 2.1.311 → 2026-10-26, 2.1.299 → 2026-10-14, 2.1.292 → 2026-10-06. - **Implication.** The repo's defaults match the native-installer layout run **as the service user**; the apt route works too but gives `/usr/bin/claude`, which install.sh picks up automatically only when `.env` is created after the install. Pin the server to the stable channel (or an exact version) so the probe-verified flag set does not drift under the service.
- **Confidence.** high.

### F2 — Auto-update behaviour and how to switch it off on a server (and why the runner's allow-list matters)
- **Claim.** Native installs "check for updates on startup and periodically while running" and install them in the background; `DISABLE_AUTOUPDATER=1` stops the background updater (manual `claude update` still works), `DISABLE_UPDATES=1` blocks all update paths; `autoUpdatesChannel: "stable"` and `minimumVersion` are settings keys; apt installs never self-update. The documented way to set these is the `env` block of `~/.claude/settings.json` or the process environment — but the runner forwards only its allow-list, so a `DISABLE_AUTOUPDATER` placed in the systemd unit never reaches the child; and under tier 1 (`--restricted`) the CLI "loads only managed settings and `--settings`", so `~/.claude/settings.json` is ignored for the probe-selected tier-1 calls. Reliable places: the wrapper script, `/etc/claude-code/managed-settings.json` (root), or a `--settings <file>` passed through `WD_AI_EXTRA_ARGS`.
- **Evidence.** setup.md (2026-11-04): "Claude Code checks for updates on startup and periodically while running. Updates download and install in the background"; "`DISABLE_AUTOUPDATER` only stops the background check; `claude update` and `claude install` still work. To block all update paths, including manual updates, set `DISABLE_UPDATES` instead." env-vars.md: "`DISABLE_AUTOUPDATER` | Set to `1` to disable automatic background updates. Manual `claude update` still works. Use `DISABLE_UPDATES` to block both". cli-reference.md `--restricted` row: "loads only managed settings and `--settings` … Requires Claude Code v2.1.248 or later". managed-settings.md: "**Linux and WSL**: `/etc/claude-code/managed-settings.json`". settings-reference.md `env`: "From user settings, `--settings`, and managed settings: at startup". Repo: `backend/wd/ai/runner.py:49-62` (PASSTHROUGH_ENV), `:158-174` (`claude_env` builds a fresh dict: HOME, PATH, LANG, LC_ALL, TERM, NO_COLOR, TZ + allow-list), `docs/CLAUDE_INTEGRATION.md:83` "never: CLAUDECODE …, any other CLAUDE_CODE_* variable, WD_* variables"; `backend/wd/config.py:91,335` `WD_AI_EXTRA_ARGS` appended verbatim (`runner.py:147-148`).
- **Implication.** On a server the binary should not change underneath the service between probes: export `DISABLE_AUTOUPDATER=1` in the wrapper (simplest, covers both tiers), or deploy a managed-settings file. If the host must track updates, re-run `wd claude-check` after each `claude update`.
- **Confidence.** high.

### F3 — Where credentials live on Linux and whether a same-user systemd service can use them
- **Claim.** Linux stores the claude.ai / Console login in `~/.claude/.credentials.json` with mode 0600 (macOS uses the Keychain and falls back to the same file); with `CLAUDE_CONFIG_DIR` set, the file lives under that directory instead. No keychain, D-Bus or login-session variable is involved, so a systemd system service running as the same user with `HOME` pointing at that home directory reads the credential; the unit already sets `User=`, `Environment=HOME=/home/<user>` and deliberately omits `ProtectHome`, and `claude_env()` sets `HOME` from `WD_CLAUDE_HOME` or the parent's `HOME`. The file is rewritten on token refresh and parallel sessions coordinate the refresh, so `HOME` must be writable and `WD_AI_CONCURRENCY` 1–3 is fine. Stored logins expire ("within three days of expiring … warning"; "Once the stored login expires and can't be refreshed, each model request fails with `Login expired · Please run /login`"), and 2.1.318 improved exactly that failure for `claude -p`. The Mac-only "Not logged in" under the stripped env (fixed by exporting USER/LOGNAME/TMPDIR in the shim) is a Keychain code path. The Ubuntu deployment documented in DEPLOY.md ran this way with 2.1.299.
- **Evidence.** authentication.md (2026-11-04): "On Linux, credentials are stored in `~/.claude/.credentials.json` with file mode `0600`."; "If you've set the `CLAUDE_CONFIG_DIR` environment variable, Claude Code keeps the `.credentials.json` file under that directory instead"; "Renew an expiring login … `Your login expires in 3 days · run /login to renew` … Once the stored login expires and can't be refreshed, each model request fails with `Login expired · Please run /login`". troubleshoot-install.md: "Parallel sessions on one machine share a saved login and coordinate its renewal so that only one process refreshes the token at a time." claude-directory.md: "`~/.claude.json` … If it's missing, Claude Code creates it when you start a session or run a subcommand such as `claude auth status`"; "`sessions/`: holds one small file per running session". CHANGELOG 2.1.318: "Fixed the sign-in failure when a stored claude.ai login reaches its time limit: it now says so, and in `claude -p` names `claude auth login` and `claude setup-token`". Repo: `deploy/word-dance.service:11,15,33-34` ("Deliberately NOT set: ProtectHome / ProtectSystem=strict — the claude CLI must read and write /home/sqin/.claude and /home/sqin/.claude.json"); `backend/wd/ai/runner.py:162` `"HOME": cfg.claude_home or source.get("HOME", "/home/sqin")`; `docs/DEPLOY.md:3` "`claude` 2.1.299 at `/home/sqin/.local/bin/claude` authenticated for `sqin` (credentials in `/home/sqin/.claude*`, no `ANTHROPIC_API_KEY`)"; memory note `claude-cli-macos-needs-login-env.md` (Keychain item, macOS only). Live DB copy (`ai_calls`, Mac, claude 2.1.292): 19 `auth` rows "exit 1: Not logged in · Please run /login" before the shim, 49 successes after.
- **Implication.** On Ubuntu no shim is needed for the credential itself; the operator logs in once as the service user (same `HOME`, same `CLAUDE_CONFIG_DIR`), and must plan for the login's expiry (re-login via `sudo -iu sqin claude auth login`, ops.md §196) unless a static credential is used. Keep `HOME` writable (no `ProtectHome`), which the unit already does.
- **Confidence.** high for storage/location (documented); medium-high that nothing else is required on Linux (documented design plus the DEPLOY.md record, not re-executed here because the real binary must not be run).

### F4 — Interactive login over SSH and the non-interactive status check
- **Claim.** On a headless VPS the browser cannot open; `claude auth login` (or the interactive first run) prints a login URL; opening it in a local browser and signing in shows a **code** instead of redirecting to `localhost`; the code is pasted at the `Paste code here` prompt, and `claude auth login` reads it from stdin. `claude auth status` exits 0 when logged in / 1 otherwise and prints JSON with `authMethod` ∈ {`none`, `claude.ai`, `oauth_token`, `api_key`, `api_key_helper`, `third_party`} and `configDirectory` (v2.1.268+). The interactive first run also performs a connectivity check against `api.anthropic.com` and `platform.claude.com` (10 s each) and exits on failure; `-p` runs show no trust dialog and no onboarding prompt is documented for them.
- **Evidence.** troubleshoot-install.md "OAuth login fails in WSL2, SSH, or containers": "At the interactive login prompt, press `c` to copy the URL … With `claude auth login`, copy the URL that it prints … Open the URL in a browser on your local machine and sign in. The browser then shows a code instead of returning to `localhost` … Paste that code into the terminal at the prompt that begins `Paste code here` … or use `claude auth login` instead, which reads the pasted code from standard input". cli-reference.md: "`claude auth status` | Show authentication status as JSON … Exits with code 0 if logged in, 1 if not … `authMethod` field is one of `none`, `claude.ai`, `oauth_token`, `api_key`, `api_key_helper`, or `third_party`". errors.md "Unable to connect to Anthropic services": "During first-run setup, Claude Code checks that it can reach `api.anthropic.com` and `platform.claude.com` before showing the sign-in step … gives each probe 10 seconds". headless.md: "A `-p` session shows no workspace trust dialog and no per-server approval prompt." Repo: `docs/ops.md:196` recovery recipe "`sudo -iu sqin claude` (interactive login) → `wd claude-check`".
- **Implication.** Login step for the VPS: `sudo -iu <svcuser>` then `claude auth login`, paste the code, `claude auth status --text`. The status command must be run with the same `HOME`/`CLAUDE_CONFIG_DIR` the service uses (and, for env-based credentials, with the variable exported) or it answers for a different credential set.
- **Confidence.** high.

### F5 — `--bare`: what it disables, which credentials it ignores, and whether it is the `-p` default
- **Claim.** `--bare` (added 2.1.81, 2026-03-20; tightened 2.1.286, 2026-09-30) skips discovery of hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md, sends no system reminders, starts no background tasks, and "never reads OAuth credentials or the system keychain"; it also does not read `CLAUDE_CODE_OAUTH_TOKEN`, Anthropic profiles or `apiKeyHelper` from settings files (only from `--settings`); it is equivalent to `CLAUDE_CODE_SIMPLE=1`. The docs recommend it for scripts and say it "will become the default for `-p` in a future release" — as of 2.1.318 the CHANGELOG contains no such change, so today `-p` without `--bare` still uses file-stored logins. The repo forbids `--bare` for exactly this reason and tests assert its absence.
- **Evidence.** headless.md (2026-11-04): "In bare mode, Claude Code never reads OAuth credentials or the system keychain. For the Anthropic API, set `ANTHROPIC_API_KEY` in the environment … or supply an `apiKeyHelper` in the `--settings` JSON"; note: "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." authentication.md: "Bare mode does not read `CLAUDE_CODE_OAUTH_TOKEN`. If your script passes `--bare`, authenticate with `ANTHROPIC_API_KEY` or an `apiKeyHelper` instead." settings-reference.md `apiKeyHelper` (fetch summary): "Not read in `--bare` mode". env-vars.md `CLAUDE_CODE_SIMPLE`: "OAuth tokens and keychain credentials are not read … Equivalent to passing `--bare`". CHANGELOG: 2.1.81 "Added `--bare` flag for scripted `-p` calls — … requires `ANTHROPIC_API_KEY` or an `apiKeyHelper` via `--settings`"; 2.1.286 "Changed `--bare` to connect only the MCP servers named on the command line, send the model no system reminders, and start no background tasks"; no "default" change up to 2.1.318. Repo: `backend/wd/ai/runner.py:6` "Never `--bare`"; `docs/CLAUDE_INTEGRATION.md:33` "**Never** `--bare` (disables OAuth, FACTS §3)".
- **Implication.** With a file-stored login the runner must keep omitting `--bare`. With a static key (`ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`) `--bare` is safe for this workload (`--tools ""` already removes tools) and can be enabled today without code via `WD_AI_EXTRA_ARGS="--bare"`; it is the invocation Anthropic documents for scripts. The announced default flip is the main forward-compatibility risk for the OAuth-file setup; pinning the CLI version (F1/F2) is the mitigation until an opt-out is documented.
- **Confidence.** high for current behaviour; medium for the timing/shape of the future default.

### F7 — `sonnet` resolves to Sonnet 5.5 (`claude-sonnet-5-5`); effort defaults and how to set them here

The live instance confirms the resolution: every successful call recorded `model_used = claude-sonnet-5-5` (2.1.292).
- **Evidence.** model-config.md (2026-11-04) alias table row "| Anthropic API | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 |"; version history "v2.1.284 | `sonnet` resolves to Sonnet 5.5 on the Anthropic API", "v2.1.280 | `opus` resolves to Opus 5.5 …", "v2.1.293 | `haiku` resolves to Haiku 5.5 …"; "The model's default effort: `high` on every model that supports effort, except that Opus 5.5, Sonnet 5.5, and Haiku 5.5 default to `medium`"; `--model` accepts "Full model names (Anthropic API): `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`". env-vars.md: "`CLAUDE_CODE_EFFORT_LEVEL` … Takes precedence over `--effort`"; "`ANTHROPIC_DEFAULT_SONNET_MODEL` | Model ID that the `sonnet` alias resolves to". - **Confidence.** high.

### F8 — Proxy support, `ANTHROPIC_BASE_URL`, and the hosts a VPS must reach
- **Claim.** The CLI honours `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` (lower-case too; first of `https_proxy`, `HTTPS_PROXY`, `http_proxy`, `HTTP_PROXY`), basic auth in the proxy URL, `NODE_EXTRA_CA_CERTS`, and **does not support SOCKS proxies** — which is why the Mac fronts its SSH SOCKS tunnel with privoxy on 127.0.0.1:8118. `ANTHROPIC_BASE_URL` reroutes API traffic to a gateway/proxy that speaks the Anthropic format; set alone it keeps the saved claude.ai login as the credential (the gateway must forward the OAuth beta header), while `ANTHROPIC_AUTH_TOKEN` (sent as `Authorization: Bearer`) replaces it and outranks `ANTHROPIC_API_KEY` (`X-Api-Key`). Hosts: `api.anthropic.com` (all API calls), `platform.claude.com` (OAuth token exchange/refresh for claude.ai logins too), `claude.ai` and `claude.com` (login), `downloads.claude.ai` (installer/updates), optional Datadog intake hosts (telemetry). A `403` from these hosts is documented as "a proxy or network filter blocking the host, or Claude Code is not available in your region"; the owner's own network gets `403 Request not allowed` today. The runner forwards `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ANTHROPIC_BASE_URL`, `SSL_CERT_FILE`, `SSL_CERT_DIR` but not `NODE_EXTRA_CA_CERTS`.
