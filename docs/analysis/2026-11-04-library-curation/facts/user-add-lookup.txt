# SLICE user-add-lookup  (35 findings)
## SUMMARY
When a learner types a string on the add page, the client first mirrors the DESIGN §5.1 normaliser and then calls GET /api/lookup?q= (debounced 300 ms, cached
per lemma); the server normalises, looks for an exact lemma and a word_forms match under the visibility filter, probes the optional ECDICT stardict.db read-
only, and returns a preview with up to five prefix suggestions — it inserts nothing, enqueues nothing and never calls Claude. POST /api/bank/add (and /add-word,
/import, and suggestion-accept) then runs services.words.resolve: exact → form → ECDICT → provisional. If ECDICT is configured and knows the word, a GLOBAL
public words row (source='ecdict', is_public=1, is_valid_english=1) is created with no AI at all; otherwise a GLOBAL provisional words row is inserted
(source='user', is_public=0, is_valid_english=NULL, safe_for_sharing=NULL, created_by_user_id=me) and one lookup_word job is enqueued (dedupe lookup:<id>,
priority 10, run_after now+20 s). The PER-USER user_words row (state new, origin custom, priority 100, input_text, private note) is created immediately and the
item reports status pending_ai; no generate_content job is enqueued for a provisional word, it cannot be put in today's batch, and POST content/request returns
409 for it. The Claude worker claims up to 20 lookup jobs, reserves budget (kill switch, pause, hourly/daily/monthly caps — refusal defers the group without
consuming an attempt) and runs the claude CLI once with lookup_system.txt plus a JSON list of the words' display strings (no usernames, no notes), schema
lookup_v1: is_english, kind, headword, form_note_zh, phonetic, pos, meaning_zh, definition_en, difficulty, suggested_correction, safe_for_sharing, note_zh. On a
valid verdict the handler validates the proposed headword deterministically (charset + relatedness), merges/renames/keeps accordingly, fills only NULL
dictionary fields, sets is_valid_english=1, source='claude', is_public = safe_for_sharing, enqueues the single generate_content job (priority 10) and clears
pending flags; an invalid verdict sets is_valid_english=0, is_public=0, content_state='failed' and flags every holder's row 「未识别为英文单词」 with an optional never-
auto-applied did-you-mean. Visibility of the GLOBAL row is the one rule is_public=1 OR created_by_user_id=me OR holder (admins see all): the creator and anyone
who types the same string (UNIQUE lemma folds them onto one row and one live job) see it immediately in detail/content/image/bank/lookup, while a third user
gets 404, an empty /api/vocab and via='none' until the word becomes public; a word judged unsafe or invalid stays private forever for holders only, and even a
later content job can demote a public custom word back to private. If a lookup job dies after 3 attempts, or the kill switch (WD_AI_ENABLED=0 / kv
claude.enabled='0') is off, holders' rows are flagged 「暂时无法校验」 and get 修改/重试/保留/删除; 重试 re-enqueues the lookup (only while is_valid_english IS NULL), 保留 clears
the flag (仅收藏 for rejected words, never pushed, no content), and the nightly maintenance requeues dead lookup jobs once per day. Budget exhaustion or a pause is
different: the group is merely deferred, no flag is written, so the row sits at 待校验 with needs_attention=0 and no actionable button until the budget window
reopens. Adding is never blocked by AI state: there is no ai_enabled or budget check anywhere in the add/import path; the only user limits are 300
mutations/min, 200 custom adds/day (shared by add, add-word and import, with import charging only provisional rows), 50 tokens per add call, 20 study_today
extras/day, 2,000 rows per import; GET /api/lookup and PATCH attention:retry have no dedicated quota. Within this slice, the only code that ever sets
is_valid_english=1 is the seed importer, the ECDICT resolver and the lookup handler — there is no user, admin or CLI path to validate or publish a provisional
word by hand. Consequently, with Claude permanently off, every user-added word not covered by the seed or ECDICT is stuck private and unstudiable, which is the
central constraint for an admin-curated, no-end-user-AI deployment.
