# SLICE ops-change-management  (35 findings)
## SUMMARY
Production is one Ubuntu box, one systemd system unit (`wd serve` = uvicorn with workers=1 plus in-process Claude/IO workers and scheduler), one SQLite file in
WAL mode, and one data directory `WD_DATA_DIR` (default /home/sqin/word-dance-data, 0700) holding `.env`, `word-dance.db` (+-wal/-shm),
`images/<2hex>/<sha>.jpg|svg`, `backups/`, `claude-cwd/`, `claude-logs/`, `tmp/`, the live SPA symlink `frontend -> frontend-releases/<sha>` and optionally
`stardict.db`. Code lives in the git checkout and is changed only by `git pull && deploy/install.sh`, which builds the SPA into `frontend-releases/<sha>.new`,
stops the unit, publishes the snapshot with an atomic symlink rename (keeping two), runs `wd migrate` (which first writes `backups/pre-
migrate-<from>-to-<to>.db.gz`), runs `wd import-seed` (a no-op unless the sha256 of the tracked `data/seed/vocab.jsonl.gz` changed, so a release that ships a
new seed is applied automatically), runs the paid `wd claude-check` probe, re-renders the units and restarts; the service lifespan repeats migrate + seed-check
at every boot anyway. Backups are a separate systemd timer at 03:30 Asia/Shanghai running `wd backup --keep-daily 14 --keep-weekly 8` (VACUUM INTO ->
integrity_check -> gzip -> retention -> kv.backup.last), safe while the service runs; restore (`wd restore`) requires the service to be stopped and refuses
while the worker lease is live, systemctl reports the unit active, or any other connection holds an open transaction. Concurrency is plain SQLite: every
request/job/CLI opens its own autocommit connection with busy_timeout=5000 and writes under BEGIN IMMEDIATE with three short retries, so an external process may
modify the database while the service runs as long as its transactions are short; nothing in the code prevents it, and `wd migrate`, `wd import-seed`, `wd
fetch-image`, `wd images-prune`, `wd build-batch`, `wd push-now` all run next to the live service without a lease check, while `wd worker-once`, `wd tick`, `wd
consolidate --now` and `wd restore` exit 2 when `kv.worker_lease` is live. The lease (TTL 90 s, renewed every 30 s) plus the stale-lock sweep (`requeue_stale`
on boot and in the hourly GC) mean a separate "curation" process must never claim jobs from the `jobs` table, but it may freely write to global tables (`words`,
`word_contents`, `word_images`, `kv`) in short transactions. There is no CLI, endpoint or documented procedure for bulk word/content edits: the only shipped
bulk writers of `words` are the seed upsert (`import-seed`, which never touches content pointers or per-user tables) and numbered SQL migration files (0009 is a
data-only UPDATE precedent), and the only documented direct-DB access is read-only verification of backup copies. Runtime switches live in the global `kv` table
and are read on every call without caching: `POST /api/admin/ai/pause` sets `claude.paused_until` (+24 h) and resume deletes it and writes `claude.enabled='1'`;
`kv.claude.enabled='0'` is a hand-set kill switch that no code or CLI ever writes; `WD_AI_ENABLED=0` in `.env` is the restart-requiring equivalent. With AI off,
the Claude worker idles 30 s at a time, groups are deferred rather than failed, queued lookups are flagged 暂时无法校验, the client sees `ai_enabled:false` and the UI
falls back to dictionary data and template cards. `provider_usage`/`provider_state` are image-provider quota counters and cooldowns written only by
`images/quota.py` with no reset endpoint; `system_events` is the operator-visible event log. Two constraints matter for a no-AI public deployment: install.sh
preflight hard-fails without a `claude` binary in PATH and unconditionally runs the paid `wd claude-check`, and the unit deliberately omits ProtectHome because
all AI calls run under the operator's own `/home/sqin/.claude` OAuth login.
