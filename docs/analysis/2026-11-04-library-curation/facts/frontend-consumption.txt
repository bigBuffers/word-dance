# SLICE frontend-consumption  (36 findings)
## SUMMARY
The web client is a React SPA that talks only to the JSON API over same-origin cookie fetches: it has no service worker, no IndexedDB, no data-fetching cache
library, the HTTP client sends `cache: 'no-store'`, and the server stamps `Cache-Control: no-store` on every /api response, so every page mount re-reads the
server and a server-side library change is visible to every client on its next request. The 词库 page browses the GLOBAL `words` table through exactly two
endpoints, GET /api/vocab (offset-paged, 50 per page, max 100; filters stage/new_only/status/sort/letter/q) and GET /api/vocab/letters; an ASCII query is a
prefix match on lemma plus word_forms, a CJK query is a substring match on the ECDICT translation, and browsing never enqueues jobs. "Stages" are four boolean
columns on each global word (stage_zk/gk/cet4/cet6 plus stage_min) surfaced as the tabs 初中/高中/四级/六级 and by GET /api/stages, while the PER-USER setting is
`stages` (目标阶段, non-empty subset, default cet4+cet6) plus `current_stage` (主攻阶段). The daily batch (每日推送 / 今日词汇) is composed per user from three sources: due
reviews and 新词 come only from the user's own bank (user_words), and 推荐词 (daily_screen_count, default 15) are drawn from the global library: public, validated
(is_valid_english=1), unmerged words carrying any of the user's stage flags that the user has no user_words row for, ordered by stage distance from the 主攻阶段,
then frequency (NULL/0 frq last), then lemma. Consequently a word inserted server-side with is_public=1, is_valid_english=1, stage flags and a frq value becomes
a 筛词/推荐词 candidate for every matching user immediately, whereas the 词库 list and /api/stages do not require is_valid_english at all. Batch items are fixed
push_items rows with a frozen settings snapshot, but each item's content and image are read live at response time, so content generated later appears on the
card without rebuilding the batch, and with AI disabled finalize_building flips batches to ready immediately so pushes still go out dictionary-only. For a word
without content the UI always shows the dictionary data (translation lines / definition / forms) and a template SVG card captioned 系统生成卡片, plus a status line:
「例句生成中…」 while queued, 「今日 AI 额度已用完，例句将在明天补齐」 when deferred (which is also what the client shows once AI is disabled, because it treats queued+eta_s null as a
deferral), or 「今天的例句暂时生成不了，先用词典释义学习」 with a 「生成例句」 button for none/failed. AI is reached from this slice through five user-facing paths: the 生成例句 button (POST
content/request, 503 ai_disabled when off), 立即整理 (POST bank/consolidate, 503 when off), 添加生词/导入 (an unknown string creates a private provisional global `words`
row and enqueues lookup_word), marking 不熟悉 anywhere (bank.apply_action enqueues generate_content for a validated word lacking content), and 立即生成/再来一组/scheduled
builds (build_batch enqueues content for batch words lacking it). None of these entry points is hidden by the `ai_enabled` server flag, which the frontend
receives in ServerFlags but never reads; the user only sees the error toast 「AI 功能暂时关闭」 after clicking. Entry points that touch only per-user data (词库 row
buttons and bulk mark, 筛词 verdicts, bank state actions, screening) never create global rows and could stay unchanged in an admin-curated mode; the add/import
paths and the AI buttons would have to be restricted or re-copied. There is no admin endpoint in the 75-entry catalogue to create or edit a word, set stage
flags, or upload content; the admin UI's only content tools are prewarm/regenerate/refetch-image (all AI/IO jobs), and the only `INSERT INTO words` sites in the
backend are the seed importer and the user-add resolver.

1. [high] The 词库 (VocabPage) reads the global library through exactly two endpoints, GET /api/vocab and GET /api/vocab/letters, with query params stage/new_only/q/status/sort/letter/page/page_size (page_size fixed at 50 in the UI).

     why: These two read-only endpoints are the whole surface an admin-curated library must satisfy for browsing; nothing else feeds the 词库 page.
2. [high] Search semantics: an ASCII query is a prefix match on `lemma` OR on any `word_forms.form` (so `abandoned` finds `abandon`); any non-ASCII query is a `translation LIKE '%q%'` substring match on the ECDICT translation; `q` is capped at 64 chars.
     ev: backend/wd/routers/vocab.py:31; backend/wd/routers/vocab.py:41-45; backend/tests/integration/test_vocab.py:117-129
     q: """ASCII → prefix on ``lemma`` plus ``word_forms.form``; anything else → ``translation LIKE``."""
     why: Chinese search depends on the `translation` column being populated server-side; a curated word with no translation is unfindable by Chinese query.
3. [high] Paging is plain OFFSET paging (page >= 1, page_size 1..100, default 50) with a separate COUNT(*) for `total`; sort orders are freq (frq NULL/0 last), alpha, and difficulty (COALESCE(difficulty, stage_min, 5)).
     ev: backend/wd/routers/vocab.py:75-79; backend/wd/routers/vocab.py:114-117; backend/tests/integration/test_vocab.py:180-185
     q: "freq": "(w.frq IS NULL OR w.frq = 0), w.frq, w.lemma",
     why: A curated word without `frq` sorts to the very end of the default 词频 order, so admins must fill frq for new words to be discoverable.
