# DESIGN D1-minimal-ops — Minimal change, ship soonest: keep the existing seed pipeline, prewarm and backup/restore as the generation and transport tools; add only (1) a hard policy switch that turns WD_AI_ENABLED=0 from "worker idles" into "no AI job is ever created and no AI affordance is shown", (2) frontend hiding/re-copy keyed on the ServerFlags.ai_enabled flag the client already receives, (3) an install path that tolerates a box without the claude binary, and (4) a small content-pack CLI for ongoing updates after launch. Generation happens off the public server, by a co-admin in a supported region on their own Console key. Product limitations (no on-demand examples, no words outside ECDICT, no nightly 整理, pack-cadence freshness, template cards where Wikimedia misses) are accepted and stated.
## SUMMARY
The owner's question has a yes answer with the current data model: words/word_forms/word_contents/word_images are already global, every reader goes through
words.active_content / image_meta with no client cache, and the schema's partial-unique active rows plus logical pointers mean a row written by anyone (Claude
handler, importer, restore) is served on the next request. What is missing is not storage but (a) a policy guarantee, because WD_AI_ENABLED=0 only idles the
ClaudeWorker while bank.enqueue_content_if_needed (backend/wd/services/bank.py:465-477), words.resolve's provisional branch
(backend/wd/services/words.py:688-747) and scheduler.nightly_consolidation (backend/wd/jobs/scheduler.py:194-225) keep creating jobs and the SPA never reads
ServerFlags.ai_enabled; (b) a credential and location for generation, since the owner's Enterprise seat and mainland network are both unusable; and (c) a way to
move curated rows between machines, because the only cross-machine tools are the seed file (dictionary columns only) and whole-database restore. D1 answers each
with the smallest change. Policy: reuse WD_AI_ENABLED=0 on the public box as the authoritative, restart-only switch and gate the eight enqueue sites behind the
existing ai_enabled() helper so that, with the flag off, a full learner session leaves zero Claude-type jobs and zero content_state='queued' words (a new
integration test pins that). Frontend: hide 生成例句/立即整理/重试 and reword the three degraded copies when server.ai_enabled is false; the add page refuses strings
outside the seed/ECDICT with a clear message instead of creating a private provisional row that can never be validated. Generation: a co-admin physically in a
supported region runs the same repo on a staging box with WD_AI_ENABLED=1, their own personal Console API key injected as ANTHROPIC_API_KEY (the runner already
passes it through and -p prefers it over OAuth), WD_AI_MODEL pinned to claude-sonnet-5-5 and caps raised; they press 预生成 stage=all five times (9,162 words,
about 917 calls, $41-49, 4-7 h at a raised hourly cap), and the IoWorker fetches Wikimedia photos at priority 90 over the following days. Before the first
public user the finished staging database and images tar are shipped once with the existing wd backup --with-images / wd restore pair, so launch needs no new
transport code. After launch a 3.5-day content-pack CLI (wd content-export / content-import / content-wanted, keyed by lemma, idempotent by content equality and
image sha256, short transactions, never a job claimer) carries weekly updates and the reverse "which public words lack content" list; the same JSONL doubles as
the hand-authoring format (model='human'). ECDICT is installed on the public box so learner adds of real words still grow the library with no AI
(source='ecdict', public, validated); non-dictionary strings are refused, and a 0.5-day system_events('add_refused') log plus wd words-pending gives the admin a
review list whose promotion primitive already exists (adding the lemma to the curated seed JSONL promotes any same-lemma row, backend/wd/seed.py:77-81). The
owner's Mac contributes nothing to the public library: the 9,162 words come from the identical seed, the owner's bank moves via the per-user export/import, and
the 48 contents and 30 SVGs generated under the employer Enterprise seat should be regenerated on staging (under $1) rather than shipped. Effort: 6.5 dev-days
to a safe mainland-facing deployment (2.5 backend gating, 1.75 frontend, 1.0 install, 1.25 ops), 5.5 more in the first month for the pack tooling, prewarm CLI,
refused-add log and runbook; later items (domestic-model adapter, image governance, first-class API-key config) are listed but outside the 12-day D1 total.
Accepted limitations: examples appear only after the weekly cycle, words outside ECDICT cannot be added, no nightly 整理/易混 chips, images are Wikimedia-or-card,
reports are resolved by dismissal or by the next cycle, and the project depends on one co-admin until a domestic adapter exists. The two biggest non-code risks
are that serving pre-generated outputs to mainland users is an inference rather than a written safe harbour, and that the co-admin's Console outputs need a
simple written licence to the project.

## ARCHITECTURE
Three machines, two directions of flow, no new runtime component on the public box.  1. STAGING (co-admin, supported region): same repo commit; .env
WD_AI_ENABLED=1, WD_AI_MODEL=claude-sonnet-5-5, raised caps, WD_ECDICT_DB_PATH set (so wanted-words can be re-created), ANTHROPIC_API_KEY in the service
environment. wd serve → admin UI 预生成 → prewarm_plan job → generate_content jobs (priority 90, dedupe content:<id>) → claude -p (runner.py) →
content.store_content writes word_contents (active, prompt_version content-v1, model claude-sonnet-5-5) +
words.active_content_id/content_state='ready'/difficulty → content.enqueue_image → fetch_image (IoWorker, Wikimedia-only at priority 90) → images/store.activate
writes word_images + images/<2hex>/<sha>.jpg. Optional: wd fetch-image <word> --provider claude_svg for high-frequency words without a photo. Output artefacts:
(A) once, pre-launch: wd backup --with-images → backups/word-dance-YYYYMMDD-HHMM.db.gz + images-YYYYMMDD.tar; (B) weekly after launch: wd content-export --since
<last> --with-images → pack.jsonl.gz + pack.images.tar.  2. PUBLIC BOX (SG/Tokyo, no claude binary, no credentials): .env WD_AI_ENABLED=0, WD_SVG_VIA_CLAUDE=0,
WD_ECDICT_DB_PATH=$DATA/stardict.db, WD_IMAGES_ENABLED=1, WD_REGISTRATION_MODE=invite. wd serve runs API + SPA + scheduler + IoWorker; the ClaudeWorker thread
starts but idles 30 s loops (worker.py:249-258) and, with the gating, has nothing queued. Inbound: (A) pre-launch wd restore <snapshot> --yes while the unit is
stopped + tar -x images into $DATA/images; (B) wd content-import pack.jsonl.gz --images pack.images.tar run by the owner next to the live service (short BEGIN
IMMEDIATE chunks, writes words/word_contents/word_images/kv/system_events only, never touches jobs claims, no lease needed — same class as wd fetch-
image/import-seed). Dictionary updates: curated data/seed/vocab.jsonl.gz committed to the repo → git pull && deploy/install.sh (or restart) → main.seed_check
re-imports (idempotent upsert, promotes same-lemma provisional rows). Reads by every client: GET /api/vocab, /api/words/{id}, /api/words/{id}/content,
/api/today, /api/screen/next, /media/images/*, /media/card/{id}.svg — all no-store, read live from the four global tables, so an import is visible on the next
request (the only lag is the 24 h private cache on /media/card, whose server LRU key includes active_content_id). Per-user writes (user_words, review_logs,
push_batches/items, daily_stats, user_settings) continue unchanged. Outbound to staging: wd content-wanted --out wanted.jsonl (public validated words lacking
content, seed-record shape; --reported adds words with open content reports) → staging wd import-seed --file wanted.jsonl + wd prewarm --stage any (or --lemmas
--force for re-generation) → next pack.  3. OWNER'S MAC: stays a dev/test instance outside the production path; no library data flows from it.  Control plane:
policy = WD_AI_ENABLED in each box's .env (public 0, staging 1); library version signals = kv.seed_version (dictionary) and kv.content_pack.last (content, new)
shown on the admin health card; audit = system_events('seed_imported'|'content_pack_imported') plus the staging ai_calls ledger (carried inside the snapshot, so
word_contents.ai_call_id still resolves to a row showing where and with which model each row was generated).
