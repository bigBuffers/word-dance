# Design panel — word-Dance public launch + iOS (2026-11-03)

# Part 1 — Three independent roadmaps

## word-Dance public launch roadmap: web-first, iOS decided by evidence  [web-first]

**Thesis.** This plan optimises for getting real strangers studying on a public server and contributing words to the shared library within about seven weeks, while committing to nothing that is hard to undo. Every client (browser, iOS 26 Home-Screen web app, or a future native app) depends on the same backend work: a Claude Console API key instead of the operator's OAuth seat [anthropic-policy-4][ai-runner-cost-5], hosting in an Anthropic-supported region, per-user cost and abuse controls [ai-runner-cost-19], a curation loop for user-added words [public-readiness-33], and the missing legal layer [public-readiness-30]; those come first and are the only spend that matters. iOS is served from day one by what already works: iOS 26 opens any Home-Screen site as a standalone web app [apple-appstore-29], Bark delivers lock-screen pushes today with zero backend change [delivery-push-14], and Web Push closes the reminder gap without an Apple account [ios-tech-options-14]. A native app is deferred to an evidence gate about 12 weeks after open registration; if triggered, Capacitor 9 is the default route because it reuses ~95% of the React front end and the backend additions it needs (bearer token, signed media, APNs, version gate) are identical for every native route [ios-tech-options-35][ios-tech-options-36]. Two things cannot be engineered away and shape every choice: Anthropic's supported-regions policy excludes mainland China, Hong Kong and Macau and binds end users [anthropic-policy-15][anthropic-policy-16], and a China App Store listing requires a mainland-hosted ICP/APP filing that is incompatible with Claude for an individual [apple-appstore-21][china-compliance-hosting-18].

**iOS decision.** No native app now. Ship the existing SPA as an iOS 26 Home-Screen web app (standalone by default), add Web Push + Badging in Phase 3, and point iPhone users at Bark from day one. Hold a decision gate ~12 weeks after open registration; if it triggers, build a Capacitor 9 bundled shell (CapacitorHttp + CapacitorCookies, iOS 17 minimum) distributed via TestFlight first and then the App Store with China mainland excluded; Expo/React Native is the fallback only if the evidence says App Store polish/discovery is itself the goal. Admin stays web-only in every client.

_Rationale:_ Feature parity means the 15 learner-facing routes in [frontend-parity-35] (login, register, welcome, today, study, screen, vocab, word detail, bank, add, suggestions, history, batch, settings) with the behaviours pinned in [frontend-parity-34], defined by the shipped code rather than FRONTEND.md where they differ [frontend-parity-37]; the /admin console is already absent from the phone tab bar (TabBar.tsx:27-35) and is excluded [frontend-parity-13][frontend-parity-36]; offline study is new scope, not parity [frontend-parity-20]. 87% of the front end is React-DOM TSX plus CSS and only ~2,261 lines are DOM-free [ios-tech-options-1], so only the PWA and Capacitor routes avoid a 9-11k-line rewrite [ios-tech-options-27][ios-tech-options-31]. The PWA already gets standalone launch, Web Push and Badging since iOS 16.4, Declarative Web Push since 18.4, and exemption from the 7-day ITP purge [ios-tech-options-13][ios-tech-options-14][ios-tech-options-15]; the only new code is a manifest, a service worker, a subscribe button and one backend channel [ios-tech-options-17]. Every store route needs the $99/yr program, Xcode 26/27 (the Mac has none, 3.12 GB download on a proxy-dependent network) [apple-appstore-5][ios-tech-options-33], a token/APNs/version-gate backend extension [ios-tech-options-35], and carries the April SDK deadline each year [apple-appstore-4]; Capacitor additionally carries the Guideline 4.2 'repackaged website' risk [apple-appstore-10][ios-tech-options-21]. For mainland users the App Store route is closed regardless: a China storefront listing needs an APP 备案号 tied to mainland hosting [apple-appstore-21][china-compliance-hosting-12] and mainland Apple IDs cannot use other storefronts [china-compliance-hosting-13], so the PWA loses nothing there. What the owner gives up by not listing now, for overseas users: App Store discoverability and its trust signal; push without the add-to-Home-Screen-and-tap-subscribe ritual (Safari-tab users get no Web Push) [ios-tech-options-14]; local scheduled reminders, widgets, Live Activities, Siri/Shortcuts [apple-appstore-32]; haptics and silent-switch-overriding TTS with downloadable voices (web TTS needs a first tap per page load and only sees pre-installed voices) [ios-tech-options-6][ios-tech-options-17]; a clean file-export UX in installed web apps [ios-tech-options-16]; and background prefetch of 'examples ready' [ios-tech-options-8]. Capacitor is the default native route because its backend prerequisites (bearer token on the sessions table [auth-contract-8], signed media URLs [ios-tech-options-4], APNs channel [delivery-push-13], min_client_version [auth-contract-16]) are reused by any later RN/Swift client even if a 4.2 rejection forces a change of route, and TestFlight (10,000 external testers, no territory restriction) remains a usable channel meanwhile [apple-appstore-25][china-compliance-hosting-14]. Gate criteria: proceed only if iOS users are a large share but Home-Screen installs/push opt-ins stay low despite the in-app hint, or users explicitly ask for an App Store app, or the owner wants widgets/local reminders; do not proceed if most users are mainland-located, because then the PWA is the terminal answer.

**Prerequisites.**
- DECIDE the audience and confirm your own physical location and billing country: Anthropic's policy excludes persons physically in mainland China, Hong Kong and Macau and binds end users of your product [anthropic-policy-15][anthropic-policy-16]; the 403 'Request not allowed' your own network gets from api.anthropic.com without a tunnel is the signature of that geo-block [china-compliance-hosting-5]. The plan assumes a supported-region billing country for the Console account and a region gate for live AI features (Phase 2).
- Create a Claude Console organization (Commercial Terms), add a payment method, create an API key, set a $100/month spend limit for Phase 1; expect Evaluation then Start tier ($500/month cap) [anthropic-policy-11][anthropic-policy-14][anthropic-policy-19]. Do not use the employer Enterprise seat for any public traffic [anthropic-policy-7].
- Buy a domain outside the .cn namespace at a non-mainland registrar (a mainland host would require ICP 备案 and a footer number [china-compliance-hosting-7]); use short-TTL DNS so a GFW IP block costs hours [china-compliance-hosting-29].
- Rent one Ubuntu 24.04 VPS, 2 vCPU / 4 GB, Tokyo (30-60 ms to east China) or Singapore: Tencent Lighthouse $8.50/mo, Alibaba SAS $15/mo, Lightsail $24/mo [china-compliance-hosting-28][china-compliance-hosting-29]; Ubuntu + systemd is what deploy/install.sh supports [public-readiness-26].
- Open a transactional e-mail account with a sending domain (SPF/DKIM/DMARC) and mainland deliverability (QQ/163) [delivery-push-19]; e-mail backs verification codes, password reset and the daily digest [delivery-push-17].
- Create an S3-compatible bucket (B2/R2/COS) for encrypted off-site backups including .env and images/ [public-readiness-21].
- Install Bark or a WeCom bot on your own phone: it is the alert channel for Phase 1 and the day-one iOS push for users [delivery-push-2][delivery-push-14].
- Write or approve the zh-CN Terms of Service, Privacy Notice (with retention periods), contribution licence and public contact e-mail; the code has none of these [public-readiness-30][china-compliance-hosting-2].
- Approve the budget: ≈ $60-110 one-off (domain, seed prewarm ≈ $41-49) and ≈ $120-280/month at 100 active users; Apple's $99 is NOT needed until the Phase 4 gate [ai-runner-cost-17][apple-appstore-1].
- Choose 20-50 invited testers (a class, friends, a study group) for the Phase 1 invite-only beta; invite codes exist (POST /api/admin/invites) [frontend-parity-13].
- Plan ~10.5 full-time developer weeks to the iOS gate (Phases 1-3), plus ~7 weeks if Phase 4 is triggered.

## word-Dance: public server first, then a Capacitor iOS shell to TestFlight and the App Store (no UI rewrite)  [store-first]

**Thesis.** This plan optimises for the shortest credible path to an App Store presence while keeping one React codebase: phase 0 puts the existing SPA on a public Singapore/Tokyo server under a Claude Console API key (the operator OAuth/Enterprise seat cannot back a public service [anthropic-policy-4, -7]), because every client, including App Review's reviewer, depends on that server [apple-appstore-8, -13]. The iOS app is a Capacitor shell over the bundled Vite build with CapacitorHttp, native TTS/push/haptics/share plugins and a small backend contract extension (bearer tokens, signed /media URLs, APNs device table + send_apns job, a client-version gate) [ios-tech-options-19, -20, -35]. Feature parity is defined as the 15 learner-facing routes the phone tab bar already exposes; the admin console stays web-only [frontend-parity-13, -35, -36]. The price of this route is Guideline 4.2 risk, so the plan front-loads differentiators (APNs reminders, offline today-batch, haptics, system TTS, native share) and names the fallback: TestFlight public link plus the iOS 26 Home-Screen web app, with an Expo/RN rebuild only if Apple rejects twice [apple-appstore-10, -25, -29; ios-tech-options-21, -27]. Mainland China App Store listing is out of scope (ICP/APP 备案 needs mainland hosting that Claude cannot have) and TestFlight is the mainland distribution channel [china-compliance-hosting-12, -14, -18]. Effort figures are full-time days for one experienced developer; total about 16 weeks to a store submission, with external TestFlight around week 12.

**iOS decision.** Capacitor 8.6 (migrate to 9 after GA) shell around the existing SPA: bundled Vite assets (never server.url), CapacitorHttp + CapacitorCookies, bearer-token auth stored in @capacitor/preferences, signed /media URLs for <img>, @capacitor/push-notifications -> APNs, @capacitor-community/text-to-speech, @capacitor/haptics, @capacitor/filesystem + @capacitor/share. Parity = the 15 learner routes (/login, /register, /welcome, /today, /study, /screen(/:stage), /vocab, /words/:id, /bank, /bank/add, /bank/suggestions, /history(/:batchId), /settings) with the behaviours pinned by the page tests; /admin, keyboard shortcuts, bulk-select and the desktop pager are web-only. Distribution: TestFlight internal (week ~11) -> TestFlight external public link as the mainland channel (week ~12-13) -> App Store worldwide except China mainland (week ~15-16). Fallback if 4.2 rejects twice: stay on TestFlight + the Home-Screen web app, and only then decide on an Expo/RN rebuild.

_Rationale:_ 87% of the front end is React-DOM TSX and CSS (16,962 non-test lines; only ~2,261 lines are DOM-free), so only the PWA and Capacitor routes reuse the 17 screens; Expo/RN reuses ~13-16% and needs 6-10 weeks of rewrite, SwiftUI reuses 0% and needs 8-14 weeks [ios-tech-options-1, -27, -31, -36]. The backend delta (token auth, APNs job, version gate) is essentially identical for every store route, so it does not discriminate; the UI rewrite and review risk do [ios-tech-options-35]. Capacitor with CapacitorHttp passes the unchanged CSRF rule because native requests carry no Origin [auth-contract-1; ios-tech-options-3, -19]; the only hard breakages are cookie-protected <img> loads and <a download>, fixed by signed media URLs and the Filesystem/Share plugins [ios-tech-options-4, -5]. Parity is scoped from the code, not FRONTEND.md: no image actions on the study card, pollers with the code's intervals, wd.pendingGrades as the only non-server state to persist durably [frontend-parity-18, -27, -28, -34]. Admin is excluded because it is already absent from the phone TabBar and removes ~1,400 lines and 21 endpoints plus review friction over an operator console [frontend-parity-13, -36]. 4.2 is the dominant risk of this route (medium-high) and is accepted knowingly because the owner asked for App Store presence as fast as reasonably possible; the mitigations and the fallback are explicit work items [apple-appstore-10; ios-tech-options-21, -22]. TestFlight has no territory restriction and reaches mainland iPhones without ICP, at the cost of 90-day rebuilds and a legally grey status under the MIIT notice [apple-appstore-25; china-compliance-hosting-14].

## word-Dance: public server first, then a parity-grade Expo/React Native client built for the long run  [native-parity]

**Thesis.** This plan optimises for a service that can legally and operationally serve strangers for years, and only then for a native client, because every client depends on the server and because the long-run cost of an iOS app is maintenance, not the first build. Phases 0-1 move word-Dance from the owner Mac to a Tokyo/Singapore VPS under a personal Claude Console API key (the only permitted auth for a public service, [anthropic-policy-4], [anthropic-policy-14]), open registration behind abuse and per-user AI quotas, and add the curation loop that makes "the public improves the shared word library" real instead of a Claude-only verdict ([public-readiness-32], [public-readiness-33]). Phase 2 gives the server what any binary client needs: bearer tokens on the existing sessions table, APNs, an additive-only API with min_client_version, and an exported OpenAPI contract ([auth-contract-8], [auth-contract-16], [delivery-push-11]). Phases 3-5 build an Expo/React Native client rather than SwiftUI because it reuses the ~2,300 lines of pure TypeScript, ~110 pure-logic tests and the zh.ts copy table, produces Android as a by-product, builds on EAS without a local Xcode, and carries low App Review 4.2 risk ([ios-tech-options-1], [ios-tech-options-27], [ios-tech-options-36]); the study session is built first, admin stays web-only, and double maintenance is contained by a shared wd-core package, contract tests, server-side feature flags and OTA updates. The whole programme is about 21 weeks (≈102 full-time developer-days) and $150-250/month at 100 active users; it is only viable if the audience and the owner are in Anthropic-supported regions, which is the first decision the owner must make ([anthropic-policy-15], [china-compliance-hosting-5]).

**iOS decision.** Expo SDK 58 / React Native 0.88 (New Architecture, expo-router native tabs), iOS 17+, bearer-token auth plus APNs, built and signed on EAS (no local Xcode required), admin console excluded (web-only), Android produced from the same project as a sideloadable APK. Timing: start only after the public server exists (phases 0-2, ~10 weeks); first TestFlight at ~week 17; App Store release to all storefronts except China mainland at ~week 21. Parity means the 15 learner-facing routes of [frontend-parity-35] with the behaviours pinned in [frontend-parity-34]; it excludes /admin, keyboard shortcuts, bulk-select, the numeric pager and cross-tab sync ([frontend-parity-13], [frontend-parity-36]); the study card matches the shipped web (no in-session image actions, [frontend-parity-28]); export/import move to the share sheet and document picker ([auth-contract-21]); TTS uses system voices; dark mode follows the OS; the APNs daily digest is an addition, not parity ([auth-contract-22]).

_Rationale:_ Expo/RN beats SwiftUI on the metric that dominates a solo owner's long run, which is the cost of keeping two clients in sync. RN reuses api/types+endpoints+client (1,015 lines), study/queue.ts (373), utils/ (770), i18n/zh.ts (103) and ~400 lines of extractable helpers unchanged, and about 110 of the 208 vitest cases pin exactly that logic ([frontend-parity-15], [frontend-parity-33]); SwiftUI reuses 0% and must re-implement and re-pin all of it, including the 288-line SRS preview and the queue reducer ([ios-tech-options-31]). Effort: 6-10 weeks to a parity TestFlight for RN (5-8 without admin) versus 8-14 weeks for SwiftUI plus 4-8 if the owner is new to Swift ([ios-tech-options-27], [ios-tech-options-31]). Toolchain: the owner Mac has no Xcode and a proxy-dependent network; EAS Free gives 15 iOS builds/month and signing without a Mac, so the 3.1 GB Xcode + ~8 GB simulator download is optional ([ios-tech-options-24], [ios-tech-options-33], [apple-appstore-6]). Review risk is low for RN and lowest for SwiftUI, a difference that does not justify a third language; Capacitor is rejected because a bundled WKWebView shell is the Guideline 4.2 anti-pattern and today's CSRF Origin rule, SameSite=Lax cookie and cookie-gated /media break it without backend changes ([ios-tech-options-19], [ios-tech-options-21], [auth-contract-1], [auth-contract-6]). The backend delta (token auth, APNs, version gate) is identical for RN and SwiftUI, so the backend does not discriminate ([ios-tech-options-35]). RN's known weaknesses are handled explicitly: unstable cookie auth is avoided by issuing bearer tokens on the existing sessions table ([ios-tech-options-26], [auth-contract-8]); Hermes gaps (regex lookbehind, NFKC, Intl formatToParts, TextEncoder, randomUUID) are verified by running the shared test suite under Hermes in the first app week ([frontend-parity-17]); quarterly SDK churn is budgeted in a maintenance calendar ([ios-tech-options-23]). SwiftUI would be the right call only if the owner already writes Swift, wants widgets/Live Activities/Siri as product goals (they are outside the parity inventory), and accepts no Android and the highest ongoing cost. Android is a technical by-product only: mainland stores need ICP + 软著 + a Chinese entity and FCM push is unusable there, so it ships as an APK link ([ios-tech-options-34]).

**Thesis.** 本计划优化的目标是：在约 10 周内让陌生人真正在公开服务器上学习并向共享词库贡献词汇，同时不做任何难以撤销的投入；所有客户端（浏览器、iOS 26 主屏 Web App、未来的原生 App）都依赖同一批后端工作——Claude Console API key 取代 operator 的 OAuth 席位 [anthropic-policy-4][ai-runner-cost-5]、部署在 Anthropic 支持地区、按请求生效的地区闸门 [anthropic-policy-15][anthropic-policy-16]、每用户成本/滥用控制 [ai-runner-cost-19]、用户新增词的策展闭环 [public-readiness-33][public-readiness-34] 与缺失的法律层 [public-readiness-30]，这些先行，且是唯一真正重要的开销。iOS 的决策是一棵树而不是一个答案：Q0（第 1 周 go/no-go）你本人与目标受众是否在 Anthropic 支持地区、能否以支持地区的账单国开 Console 组织？否 → Claude 驱动的公开服务不上线（Mac 保留为个人实例；大陆版只能是基于已备案国产模型的另一产品，不在本计划内），iOS 问题随之消失 [china-compliance-hosting-5][china-compliance-hosting-18]；是 → 进入 Phase 1。Q1（Phase 1–2 期间，由 users.region_cc 与注册数据回答）受众是否以中国大陆为主？是 → App Store 路线被结构性关闭（大陆 Apple ID 无法安装其他商店、中国区上架需挂钩大陆主机的 ICP/APP 备案且 Claude 无法登记 [china-compliance-hosting-12][china-compliance-hosting-13][apple-appstore-21]），iOS 的终局答案就是 iOS 26 主屏 Web App + Bark（今天）+ Web Push（Phase 3）[apple-appstore-29][delivery-push-14][ios-tech-options-14]，Phase 4 不启动（TestFlight 对大陆用户是灰色渠道且在地区闸门下只能得到字典模式 [china-compliance-hosting-14]）；否（台/新/日/美与海外华人学习者为主）→ 进入 Q2。Q2（开放注册后约 12 周的证据闸门，Phase 3 埋点回答）是否有任一触发：iOS 占比高但主屏安装/推送 opt-in 持续偏低、用户明确索要 App Store 版、你需要 widgets/本地提醒/Siri、或商店发现性成为增长瓶颈？否 → PWA 即产品，6 个月后复议；是 → Q3：若要最快的商店存在感且接受 Guideline 4.2 风险 → Capacitor 9 外壳（默认路线，≈7 周，复用 ≈95% 前端，TestFlight 先行、App Store 排除中国大陆，预先约定两次 4.2 拒绝即回退到 TestFlight + PWA 而后端工作保留）[ios-tech-options-22][ios-tech-options-35]；若原生打磨与商店本身就是产品目标且接受第二套 UI 的长期维护（多 5–8 周、每季 SDK 升级）→ Expo/RN（EAS 云构建、无需本地 Xcode）[ios-tech-options-27][ios-tech-options-24]；只有在 widgets/Live Activities/Siri 是目标且你会写 Swift 时才考虑 SwiftUI [ios-tech-options-31]；Android 任何路线都只是可侧载 APK，不进大陆商店 [ios-tech-options-34]。时间线：Phase 1（5 周）→ Phase 2 开放注册（第 10 周）→ Phase 3（第 14 周）→ 闸门约第 22 周 → 若触发，Phase 4 约第 29 周提交 App Store。
