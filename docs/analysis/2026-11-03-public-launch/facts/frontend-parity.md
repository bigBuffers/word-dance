# Fact slice: frontend-parity (39 findings)

## Summary

The web front end is a 12,344-line (non-test) React 19 + react-router 7 SPA with 4,661 lines of plain CSS, 4,620 lines of vitest tests (208 cases) and one 18 KB zh-CN string table; it exposes 18 routes over 75 typed endpoint wrappers, all authenticated by an HttpOnly cookie plus an X-WD-Request CSRF header. "Feature parity" for iOS means 15 learner-facing routes; the study session (/study: StudyPage 735 lines + StudyCard 402 + queue reducer 373) is the only L-sized screen, settings and admin are the other two L screens, and admin is already effectively web-only (it is not in the phone tab bar). About 2,500 lines are platform-neutral TypeScript that an RN/Capacitor client can import unchanged or with a base-URL/cookie tweak: api/types+endpoints+client (1,015), study/queue.ts (373), utils (770), i18n/zh.ts (103) and four DOM-free hooks (251); five hooks (377 lines: keyboard, localStorage, page title, visibility-aware polling, Web Speech) need platform adapters, and every component/page TSX and all CSS are DOM-bound. The only client-persisted state that is not server-backed is the localStorage grade outbox wd.pendingGrades (grades the card already advanced past) plus five UI-preference keys; there is no service worker, no manifest and no offline data, so the app is online-only apart from that outbox and its 1/3/10/30/60 s retry loop. Dark mode follows the OS only (no in-app toggle), safe areas are handled via env() insets, and copy is strictly centralised with a lint that forbids CJK outside i18n, so a port can reuse zh.ts verbatim. The backend facts that shape the port: cookie-only sessions (no token endpoint), an Origin check that rejects any Origin not equal to the Host-derived origin or WD_PUBLIC_URL (a Capacitor WebView's capacitor://localhost would be refused today; a native HTTP client sending no Origin passes), and /media images that require the cookie. Several documented behaviours differ from code (usePolling not used for today/content/image polls, two undocumented localStorage keys, no image refresh/flag actions on the in-session card), which a parity spec should take from the code.

## Open questions

- Architecture choice drives everything else: a WebView shell (Capacitor) over the existing SPA is blocked today by the CSRF Origin rule (backend/wd/deps.py:111-129 rejects capacitor://localhost) unless the shell loads the SPA from the server's own https origin or the backend allowlists the WebView origin; a React Native client can reuse ~2,500 lines of pure TS; a Swift client reuses nothing but the API contract. Which is intended?
- Does the owner want /admin on iOS at all? It is not in the phone tab bar today (TabBar.tsx:27-35), so 'parity with the web front end on a phone' already excludes it; confirming this removes ~1,400 lines and 21 endpoints from scope.
- Session auth is cookie-only with no token endpoint (endpoints.ts:370-556; security.py:230-242). Is persisting the wd_session cookie in the app acceptable, or will the backend add bearer-token auth (outside this slice)?
- The web has no push notifications (daily 'push' is e-mail/webhook; no Web Push code). Is an APNs daily reminder part of the iOS requirement? It would be new backend + client work, not a port.
- Must the study-grade outbox (localStorage wd.pendingGrades, StudyPage.tsx:53-106,185-189) survive app termination on iOS exactly as it survives a reload on the web? This is the only non-server state with real data.
- Should the iOS study card include 换一张/不合适 image actions as FRONTEND.md §5.1 promises, or match the shipped web where they exist only on the detail page (StudyPage.tsx:686-706)?
- Which JS engine/version would host the shared TS (Hermes vs JSC) — regex lookbehind (highlight.ts:39), String.normalize NFKC (normalizeInput.ts:74), Intl formatToParts with IANA zones (srsPreview.ts:104), TextEncoder (srsPreview.ts:83) and crypto.randomUUID (format.ts:63-73) need verifying or polyfilling there.
- Is offline study (caching today's batch, content and images) a requirement for the app? The web is strictly online-only (no service worker/manifest/IndexedDB), so this would be new scope rather than parity.
- Does CSS actually hide the vocab bulk-select toggle on phones (VocabPage.tsx:245-256 renders it unconditionally; docs call it desktop-only)? Not verified in VocabPage.css/list.css.
- Export (<a download>) and import (<input type=file>) on iOS need a share sheet and document picker; is import of a previous CSV/JSON export a required mobile feature or can it stay web-only?
- Is there a browser E2E suite or manual QA script elsewhere in the repo (StudyPage.tsx:60 references docs/qa-study.md) that should be mirrored for the app? None exists under frontend/.
