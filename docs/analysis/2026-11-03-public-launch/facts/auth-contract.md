# Fact slice: auth-contract (23 findings)

## Summary

The backend's auth contract is cookie-only and browser-shaped, but it is already friendly to a native URLSession client and hostile to a WKWebView/Capacitor shell. The CSRF rule (deps.py:111-129, enforced globally in main.py:188-192) requires `X-WD-Request: 1` on every non-GET `/api/*` call and, when an `Origin` header is present, requires it to equal the Host-derived origin or `WD_PUBLIC_URL`'s origin; an absent Origin passes, `capacitor://localhost`, `ionic://localhost` and `Origin: null` are rejected with 403 `csrf_rejected`, and there is no CORS at all (an OPTIONS preflight answers 405), so a shell whose origin is not the server's cannot use fetch without backend changes, while a native client only has to add the custom header. The session is an opaque `wd_session` cookie (`HttpOnly; Max-Age=WD_SESSION_DAYS*86400; Path=/; SameSite=lax`, `Secure` on https/behind the proxy), the token is never in the JSON body, and `/media/*` is authenticated by that same cookie, which URLSession's cookie jar handles transparently (including image loads) but which WKWebView's third-party-cookie/ITP rules and SameSite=Lax break for cross-site fetches. There is no bearer/API-key path today; the `sessions` table is already generic enough that a bearer mode is mostly a change in `deps.current_user` plus a login variant that returns the token, inheriting revocation-on-password-change, the 20-session cap and all throttles for free. Lifetime rules a mobile client must handle: 30-day sliding sessions re-issued once per day (also on media responses), 401 `unauthorized` with no clearing cookie (the client must drop its own credential, but must not sign out on `invalid_credentials`), 403 `account_disabled`, a silent eviction of the oldest session beyond 20 per user, a per-IP login throttle that counts successful logins (20 per 10 min), a username lockout whose 10th failure still returns 401 and whose next attempt returns 423 with `Retry-After` even for the right password, and 429s that always carry `Retry-After` plus `details.retry_after_s`. Nothing is versioned beyond a `version: "0.1.0"` string in `/api/health` and `ServerFlags`; every request model is `extra="forbid"`, so a newer store-distributed client sending a new field to an older server gets a 400, and there is no min-client-version signal. CSP and the other security headers only matter for a web view that loads the remote SPA, where they do not block anything (frame-ancestors/X-Frame-Options affect iframes only), but the SPA has no configurable API base URL and uses relative paths with `credentials: 'same-origin'`, so a bundled-SPA shell needs code changes regardless. OpenAPI is served only under `WD_DEV=1` (70 paths, no securitySchemes, only 200 responses, `/media` routes excluded) but can be generated offline from `create_app().openapi()`. Browser-only assumptions a parity client must replace: `<a download>` export, `<input type=file>` import (which posts a JSON body, not multipart, under a 1 MB cap), `speechSynthesis` TTS, cookie-authenticated `<img>`, localStorage-persisted pending grades, and clipboard; there is no push-notification/APNs endpoint, no forgot-password flow, and no user-facing session list/revoke-others endpoint.

## Findings

### [auth-contract-1] (high) (a) CSRF rule — exact logic

- CLAIM: For every request whose path is `/api` or starts with `/api/` and whose method is not GET/HEAD/OPTIONS, the middleware requires header `X-WD-Request` to equal exactly `1` (else 403 `csrf_rejected`, details.reason `missing X-WD-Request header`); if an `Origin` header is ABSENT the request passes with no further check; if present it is lower-cased, a trailing slash stripped, `null` is rejected (`Origin null`), otherwise it must be in {scheme://host from the Host header (scheme from X-Forwarded-Proto when WD_TRUST_PROXY=1), origin of WD_PUBLIC_URL, plus `http://localhost:5173` when WD_DEV=1} or it is rejected (`Origin mismatch`). The check runs before routing and before authentication.
- EVIDENCE: backend/wd/deps.py:32-35 (CSRF_HEADER, SAFE_METHODS, DEV_ORIGIN), deps.py:99-129 (host_origin, csrf_violation), backend/wd/main.py:158,188-192 (is_api + middleware call); pinned by backend/tests/integration/test_health.py:72-83 and test_auth.py:284-291. Probe run 2026-11-03 (scratchpad/probe_auth_contract.py): no Origin → 201; `capacitor://localhost`, `ionic://localhost`, `http://localhost` → 403 'Origin mismatch'; `null` → 403 'Origin null'; missing header → 403 'missing X-WD-Request header'.
- IMPLICATION: A native iOS client (URLSession sends no Origin) works today by adding `X-WD-Request: 1` to every non-GET call. A WKWebView/Capacitor shell whose page origin is `capacitor://localhost`/`ionic://localhost` (or `file://`, which yields `Origin: null`) is rejected on every mutation regardless of cookies; the fix is either routing HTTP through native (no Origin) or adding those origins to the allow-set at deps.py:126-128 (which alone is insufficient, see CORS/cookie findings).

### [auth-contract-2] (high) (a) No CORS; preflight fails

- CLAIM: There is no CORS middleware or Access-Control-* header anywhere in the backend; a browser preflight `OPTIONS /api/auth/login` with `Origin: capacitor://localhost` and `Access-Control-Request-Headers: content-type,x-wd-request` passes the CSRF check (OPTIONS is a safe method) and then answers 405 `method_not_allowed` with `Allow: POST` and no Access-Control-Allow-Origin/Headers. Because `X-WD-Request` is a custom header, every cross-origin browser context triggers a preflight, so no web view with a foreign origin can call the API via fetch.
- EVIDENCE: grep for CORSMiddleware/Access-Control/allow_origins over backend/wd: no hits (only outbound provider auth in images/providers); docs/API.md:12 ('No CORS'), docs/DESIGN.md:565; backend/wd/errors.py:68-80,206-214 (405 → method_not_allowed); probe: OPTIONS → 405, allow='POST', access-control-allow-origin=None.
- IMPLICATION: A Capacitor/Ionic shell that keeps the SPA's `fetch` needs (1) CORS with an explicit origin allow-list and `Access-Control-Allow-Credentials: true`, (2) the shell origin added to the CSRF allow-set, and (3) a cookie policy change (SameSite=None; Secure) — or it must proxy HTTP through the native layer (CapacitorHttp), which removes the Origin header and makes the server see an ordinary URLSession client.

### [auth-contract-3] (high) (a) SPA client has no API base URL and uses same-origin credentials

- CLAIM: The SPA issues every call with a server-relative path (`/api/...`, `/media/...`) and `credentials: 'same-origin'`, sets `X-WD-Request: 1` on non-GET only, and has no configurable API base (the only VITE_* variable is VITE_REQUEUE_SECONDS); media URLs returned by the server are also server-relative strings.
- EVIDENCE: frontend/src/api/client.ts:99-112 (headers, credentials 'same-origin', fetch(path)), frontend/src/api/endpoints.ts:364,503-505 (relative paths, mediaImageUrl/cardUrl), frontend/src/api/types.ts:81 (ImageMeta.url '/media/images/…'), grep import.meta.env over frontend/src: StudyPage.tsx:60-65 only; frontend/vite.config.ts:4-25 (dev proxy keeps Host so CSRF passes).
- IMPLICATION: Reusing the SPA inside a bundled web view requires adding a base-URL layer (API and ImageMeta.url prefixing) and `credentials: 'include'`; a WKWebView that simply loads the remote `https://host/` SPA needs none of this because everything stays same-origin.

### [auth-contract-4] (high) (b) Session cookie — exact attributes and Secure logic

- CLAIM: Login/register answer `Set-Cookie: wd_session=<token_urlsafe(32)>; HttpOnly; Max-Age=<WD_SESSION_DAYS*86400, default 2592000>; Path=/; SameSite=lax` plus `; Secure` when WD_COOKIE_SECURE=1, or (auto) when WD_PUBLIC_URL is https, the request scheme is https, or WD_TRUST_PROXY=1 and X-Forwarded-Proto says https; WD_COOKIE_SECURE=0 disables it. HSTS is added under the same https conditions. The JSON body of login/register contains only `{user, settings}` — the token exists only in Set-Cookie. install.sh's proxy mode writes WD_PUBLIC_URL=https://DOMAIN, WD_TRUST_PROXY=1, WD_HOST=127.0.0.1, so a public deployment issues Secure cookies.
- EVIDENCE: backend/wd/security.py:213-242 (cookie_secure, set_session_cookie, clear_session_cookie), backend/wd/config.py:73,78,322 (cookie_secure modes, session_days 1–3650), backend/wd/main.py:159,171-172 (HSTS), backend/wd/routers/auth.py:32-49 (_issue_session, _auth_payload), docs/DEPLOY.md:117; probe: plain http → no Secure/no HSTS; trust_proxy + XFP https → '; Secure' + HSTS; WD_PUBLIC_URL https → '; Secure'. Tests: backend/tests/integration/test_auth.py:294-299.
- IMPLICATION: A native client must use https in production (URLSession will not send a Secure cookie over http) and cannot obtain the session token from the response body; it either lets HTTPCookieStorage manage the cookie or parses `Set-Cookie` itself. Note the DESIGN.md:564 wording ('Secure when WD_PUBLIC_URL is https or WD_COOKIE_SECURE=1') under-describes the code's per-request https / X-Forwarded-Proto detection, and the documented fixed `Max-Age=2592000` is actually WD_SESSION_DAYS-dependent.

### [auth-contract-5] (high) (b) Native URLSession can use wd_session as-is, including /media

- CLAIM: Nothing in the server distinguishes a browser from URLSession: the cookie is parsed from the `Cookie` header only (`request.cookies.get('wd_session')`), HttpOnly and SameSite are browser-side restrictions that do not affect a native cookie jar, and `/media/images/*` and `/media/card/*.svg` authenticate by the same cookie (401 JSON envelope without it, 404 for a malformed path even before auth). Media responses are cacheable client-side (`private, max-age=31536000, immutable` for content-addressed images, `private, max-age=86400` for cards).
- EVIDENCE: backend/wd/deps.py:142-149; backend/wd/routers/media.py:26-29,38-57; probe: /media/card/1.svg → 401 application/json without cookie, 401 with a bogus cookie, 200 image/svg+xml with cache-control 'private, max-age=86400' with a valid cookie; /media/images/zz/notahash.jpg → 404 even with a valid cookie.
- IMPLICATION: A SwiftUI/UIKit client using `URLSession.shared` (default HTTPCookieStorage) will send the cookie on API calls and on image downloads alike, and may cache images per URL safely. Platform behaviour (cookie jar semantics) is from general iOS knowledge, not this repo; a third-party image loader with its own URLSession configuration must be configured to share the cookie storage.

### [auth-contract-6] (medium) (b) What breaks in a WKWebView shell

- CLAIM: In a WKWebView whose document origin is not the server's (capacitor://localhost, ionic://localhost, file://), a fetch to the server is cross-site: SameSite=Lax forbids sending the cookie on cross-site requests and WKWebView's Intelligent Tracking Prevention (on by default since iOS 14) blocks third-party cookies, so even after a successful login the session is not sent back; `<img src="/media/...">` suffers the same cookie problem; and HttpOnly prevents the page's JavaScript from reading the token to work around it. A WKWebView that loads the remote SPA from `https://host/` is same-origin and works like Safari.
- EVIDENCE: Cookie attributes security.py:229-238; WKWebView ITP/third-party-cookie behaviour and Capacitor's CapacitorHttp/CapacitorCookies workaround are platform facts from general knowledge (Apple WebKit, Capacitor docs), not verified in this repo.
- IMPLICATION: The cookie session cannot be made to work for a bundled-SPA shell by server changes alone without `SameSite=None; Secure` plus CORS and still being subject to ITP; the robust options are (1) a WKWebView that loads the remote SPA, (2) native HTTP (CapacitorHttp) which behaves like URLSession, or (3) a bearer-token mode (next findings).

### [auth-contract-7] (high) (c) No bearer / API-key authentication exists

- CLAIM: `current_user` accepts only the `wd_session` cookie; the `Authorization` header is never read for inbound requests (the only Authorization/Bearer code is outbound to Openverse/Pexels), the OpenAPI document declares no securitySchemes, and no API-key table or endpoint exists.
- EVIDENCE: backend/wd/deps.py:146-149; grep Authorization/Bearer/api_key over backend/wd: only images/providers/openverse.py:44-70 and pexels.py:3,36; probe: openapi.json components.securitySchemes = null; migrations dir has only 0001_init, 0008_fk_child_indexes, 0009_strip_phonetic_delimiters.
- IMPLICATION: A native app has exactly one credential today: the opaque cookie token. Any header-based scheme is new backend work.

### [auth-contract-8] (high) (c) Minimal backend change for a token mode

- CLAIM: The existing `sessions` table (token_hash PK = sha256(token), user_id, created_at, expires_at, last_seen_at, user_agent, ip; WITHOUT ROWID) is already a generic bearer-session store, so a minimal token mode needs no new table: (1) in `deps.current_user` accept `Authorization: Bearer <token>` as an alternative source of the same opaque token and hash it with `hash_token`; (2) a login/register variant (opt-in header or body flag) that returns `{token, expires_at}` in the JSON and skips Set-Cookie, built on `security.create_session` which already records user_agent/ip; (3) in the CSRF middleware skip the Origin check (and optionally the X-WD-Request requirement) when an Authorization header is present — safe because browsers cannot attach Authorization cross-site without a CORS preflight, which fails here; (4) revocation is inherited: password change deletes all other sessions (keeps the current one), admin password reset and deactivation delete all sessions, account deletion cascades; (5) all throttles already key on user/IP and apply unchanged (login IP 20/10 min, register 5/h, mutations 300/min); (6) media routes would accept the header automatically through `current_user`, but `<img>` in a web view cannot send Authorization, so a web-view shell would additionally need a signed-URL or cookie path for `/media/*`; optional extras are a `client`/`label` column and `GET/DELETE /api/auth/sessions` endpoints for device management, which do not exist today.
- EVIDENCE: docs/SCHEMA.sql:87-96 (sessions), backend/wd/deps.py:54-56,142-181 (hash_token, current_user), backend/wd/security.py:174-205,677-681 (create_session, delete_sessions, set_password), backend/wd/routers/account.py:84 (keep_token_hash=current), backend/wd/routers/admin_users.py:101,110-111 (revoke all on reset/deactivate), docs/SCHEMA.sql:89 (ON DELETE CASCADE), backend/wd/main.py:188-192 (CSRF before auth), backend/wd/routers/media.py:42,52.
- IMPLICATION: Token mode is a small, low-risk change (two functions plus one router branch, no migration unless device labels are wanted) and gives a native client a credential it can store in the Keychain instead of a cookie jar; the sliding expiry then happens only in the DB (no cookie re-issue to parse) and the client just reacts to 401.

### [auth-contract-9] (high) (d) Session lifetime and sliding rules

- CLAIM: Sessions last WD_SESSION_DAYS (default 30, allowed 1–3650) from creation; on any authenticated request whose session `last_seen_at` is older than one day the server slides `expires_at` to now+WD_SESSION_DAYS and the middleware re-sends the cookie with a fresh Max-Age (also on raw responses such as /media), at most once per day; an expired row is deleted and the request gets 401 `unauthorized`; an unknown/bogus token also gets 401 `unauthorized` and the server sends NO clearing Set-Cookie; a disabled account gets 403 `account_disabled` while its session row remains.
- EVIDENCE: backend/wd/config.py:78,322; backend/wd/security.py:190 (expires_at); backend/wd/deps.py:157-173 (401 paths, sliding, reissue flag); backend/wd/main.py:175-177 (re-issue); backend/tests/integration/test_deps.py:93-118 (once per day, also on /media/card); probe: bogus cookie → 401 with set-cookie=None.
- IMPLICATION: A mobile client must treat 401 `unauthorized` as 'credential gone, sign out locally' (the server will not clear anything for it), must treat 403 `account_disabled` the same way, and if it stores the token itself rather than using the cookie jar it must either parse re-issued Set-Cookie headers on any response or ignore Max-Age and rely on 401. A client using the cookie jar gets the sliding renewal for free as long as it is used at least once every 30 days.

### [auth-contract-10] (high) (d) 401 semantics the client must mirror from the SPA

- CLAIM: The SPA dispatches its `auth:expired` sign-out only for HTTP 401 whose envelope code is `unauthorized`; a 401 `invalid_credentials` from login (or from the password re-check of change-password/delete-account) is an ordinary error and must not sign the user out; the bootstrap `/api/auth/me` 401 is ignored while no session is held; `account_disabled` is mapped to the generic forbidden copy.
- EVIDENCE: frontend/src/api/client.ts:4-8,94-97,114-129; frontend/src/auth/AuthContext.tsx:50-55,66-79,99-109; frontend/src/api/client.ts:168-225 (errorMessage mapping); backend/wd/errors.py:35-38 (unauthorized vs invalid_credentials vs account_disabled).
- IMPLICATION: A parity client needs the same code-based (not status-based) distinction, plus the zh error copy table (client.ts errorMessage / i18n/zh.ts) since the server's `message` is Simplified Chinese and the SPA overrides several codes with its own copy.

### [auth-contract-11] (high) (d) Session cap: 20 per user, silent eviction

- CLAIM: Each new login/register inserts a fresh session and first deletes the oldest rows (ordered by last_seen_at, created_at) beyond 20 per user; evicted sessions get 401 without any notice. Login never reuses a session (no fixation).
- EVIDENCE: backend/wd/security.py:62,162-192 (MAX_SESSIONS_PER_USER, _trim_sessions, create_session); backend/wd/routers/auth.py:6-7,136-142; probe: after 30 create_session calls the user has exactly 20 rows and the original register session answers 401.
- IMPLICATION: A native client must persist its session and must not log in on every launch (or every token refresh), otherwise it evicts the user's browser/tablet sessions and, combined with the IP throttle, locks itself out; the same applies to any 'refresh by re-login' design.

### [auth-contract-12] (high) (d) Login IP throttle counts successful logins; registration 5/h per IP

- CLAIM: `POST /api/auth/login` consumes the per-IP budget (20 per 600 s, key `login:ip:<ip>`) before the password is verified, so successful logins count too: the 21st login from one IP within 10 minutes is 429 `rate_limited` with `Retry-After` even with correct credentials. `POST /api/auth/register` is 5 per hour per IP. The IP is the TCP peer, or behind WD_TRUST_PROXY=1 the right-most X-Forwarded-For hop (uvicorn proxy_headers with forwarded_allow_ips=127.0.0.1). Throttle rows persist in `auth_throttle` across restarts.
- EVIDENCE: backend/wd/routers/auth.py:122-131 (rate_limit before verify_password), auth.py:83-84 (register); backend/wd/security.py:72-73,250-279; backend/wd/deps.py:78-96; backend/wd/cli.py:140-150; docs/SCHEMA.sql:118-123; probe: 22 correct logins from one IP → 20×200 then 429 with Retry-After 596.
- IMPLICATION: For a public server this is a shared budget per public IP: a school, office or carrier CGNAT (common for Chinese mobile users) gets 20 logins per 10 minutes and 5 sign-ups per hour in total. The native client should log in once and keep the session; the operator may want to stop counting successful logins or raise the limits before launch.

### [auth-contract-13] (high) (d) Lockout (423) semantics

- CLAIM: Failed logins are counted per lower-cased username; the 10th consecutive failure sets a 15-minute lock (doubling every further 5 failures, max 24 h; the streak resets after 24 h without a lock, and a successful login clears it). The 10th failing attempt itself still returns 401 `invalid_credentials` (the lock duration returned by record_login_failure is discarded); from the next attempt on, the server answers 423 `account_locked` with `Retry-After: <s>` and `details.retry_after_s` before checking the password, so the correct password is also refused until the lock ends.
- EVIDENCE: backend/wd/security.py:78-82,282-339 (lockout_key, check_lockout, lock_seconds_for, record_login_failure, clear_login_failures); backend/wd/routers/auth.py:126-137; backend/wd/errors.py:61,106-111 (Retry-After on 423/429); probe: 10th failure → 401 (no Retry-After); then 423 Retry-After 900 for the correct password and for 'BOB'.
- IMPLICATION: The client must render 423 from `details.retry_after_s` (the SPA shows ceil(s/60) minutes, i18n/zh.ts:17) and must not retry automatically; it cannot learn from the 10th 401 that the lock just started. Since the lock is per username, anyone can lock any account by name for 15 minutes to 24 hours — a public-deployment nuisance worth noting.

### [auth-contract-14] (high) (d) Other budgets that return 429 with Retry-After

- CLAIM: Password re-checks for change-password and delete-account share 10 attempts per 15 min per user (cleared by a correct password); e-mail verification codes 3 per hour per user, 5 attempts per code, 15 min TTL; webhook/e-mail test sends 1 per 10 min; every authenticated non-GET request counts toward 300 per minute per user (checked inside `current_user`, so it also covers /media? no — only non-GET, and media is GET); custom adds and imports share 200 per day; content requests 60/day, image refresh 20/day, reports 20/day. GETs are never throttled. Every 429 and 423 carries the `Retry-After` header and `details.retry_after_s`.
- EVIDENCE: backend/wd/security.py:68-77,346-373; backend/wd/deps.py:177-180; backend/wd/routers/bank.py:180-185; backend/wd/routers/account.py:82,94,127; backend/wd/routers/settings.py:143,155; docs/API.md:14,151-156 and endpoints 28-30; backend/wd/errors.py:106-111; probe: 11th wrong current_password → 429 Retry-After 898.
- IMPLICATION: A parity client needs one generic 429 handler that honours Retry-After, and must keep the SPA's write-side discipline: grades carry a `client_event_id` and are idempotent, transient failures (network, 429, 5xx) are retried with backoff, everything else is final (frontend/src/pages/StudyPage.tsx:79-82, 184-189).

### [auth-contract-15] (high) (d) Logout, revoke-others, password reset gaps

- CLAIM: `POST /api/auth/logout` (204) deletes only the current session and clears the cookie. There is no user-facing session list or revoke-others endpoint; other sessions are revoked only as a side effect of changing the password (current session kept), an admin password reset or deactivation (all sessions), the CLI `wd set-password` (all sessions) or account deletion (cascade). There is no forgot-password / reset-by-e-mail flow: e-mail codes only verify the address.
- EVIDENCE: backend/wd/routers/auth.py:145-151; backend/wd/routers/account.py:79-86,117-151; backend/wd/security.py:199-205,677-681,769-784; backend/wd/routers/admin_users.py:90-111; docs/SCHEMA.sql:89; grep 'gc_sessions' shows it is called only at login (auth.py:138) despite security.py:9 and docs/DESIGN.md:564 ('GC hourly') — expired rows are otherwise removed only when presented (deps.py:159-162).
- IMPLICATION: For strangers on a public server, 'I forgot my password' currently ends at the admin; a mobile 'sign out everywhere / manage devices' screen has no API; the hourly GC claim in the docs is not implemented (harmless but a docs/code mismatch).

### [auth-contract-16] (high) (e) No API versioning or min-client signal

- CLAIM: Paths carry no version segment; the only version information is the string `version: "0.1.0"` (wd.__version__) in `GET /api/health` and in `ServerFlags.version` from `/api/auth/me`; no response header or field expresses a minimum client version, and the contract is maintained in lockstep (API.md, schemas.py and types.ts 'in one commit'). All request models are `extra="forbid"`, so an older server rejects any request field it does not know with 400 `validation_error` (`details.fields.<name>: "未知字段"`).
- EVIDENCE: backend/wd/__init__.py:7; backend/wd/routers/health.py:38-44; backend/wd/routers/auth.py:52-64; backend/wd/schemas.py:4,86-89,114-147; frontend/src/api/types.ts:27-31; docs/API.md:3; backend/wd/errors.py:131 (extra_forbidden → 未知字段); backend/wd/main.py:167 (X-Request-Id on every response).
- IMPLICATION: A store-distributed client cannot be deployed in lockstep with the server, so before the first release the server needs an explicit compatibility contract (e.g. `api_version`/`min_client_version` in /api/health or a header) and an additive-only evolution rule; the client should check it at launch and use `X-Request-Id` for support reports.

### [auth-contract-17] (high) (f) Security headers and CSP as seen by an embedded web view

- CLAIM: Every response (JSON, SPA, media unless the route sets its own) carries CSP `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, HSTS only on https, `Cache-Control: no-store` on /api; SVG media gets its own CSP `default-src 'none'; style-src 'unsafe-inline'`. frame-ancestors/X-Frame-Options affect iframes only, so a WKWebView top-level load of the remote SPA is not blocked; `connect-src 'self'`/`img-src 'self'` bind the served SPA to same-origin API and media, and CSP headers do not govern a locally bundled copy of the SPA at all.
- EVIDENCE: backend/wd/main.py:92-103,164-177; backend/wd/routers/media.py:27,34-35,47-48,57; docs/DESIGN.md:568; probe: CSP/X-Frame-Options/no-store present on GET /api/health, HSTS absent on plain http and present behind XFP https.
- IMPLICATION: Option 'WKWebView loads https://host/' works without header changes (speechSynthesis and localStorage are available in WKWebView; the Permissions-Policy only disables unused features). Splitting API or media onto another host, or embedding the remote SPA in an iframe, would require CSP changes; a bundled-SPA shell is unaffected by CSP but hits the CSRF/CORS/cookie walls above.

### [auth-contract-18] (high) (f) X-WD-Request and the proxy header trust

- CLAIM: `X-WD-Request: 1` is the only custom request header the server demands; it blocks nothing for native code but makes every cross-origin browser request preflighted. Separately, with WD_TRUST_PROXY=1 the application reads the raw `X-Forwarded-Proto` header for the Secure flag, the Host-derived CSRF origin and HSTS without checking that the peer is the local proxy (uvicorn's ProxyHeadersMiddleware rewrites `scope['scheme']`/client only for peer 127.0.0.1, but the raw header stays visible), which is harmless as long as `wd serve` binds 127.0.0.1 behind the proxy as install.sh configures.
- EVIDENCE: backend/wd/deps.py:33,118-119,104-107; backend/wd/security.py:222-225; backend/wd/main.py:159; backend/wd/cli.py:146-148; .venv/lib/python3.12/site-packages/uvicorn/middleware/proxy_headers.py:32-61; docs/DEPLOY.md:117,302-306; probe section B.
- IMPLICATION: Public deployment checklist item: keep WD_HOST=127.0.0.1 (never expose :8000 directly) when WD_TRUST_PROXY=1; the native client simply always sends `X-WD-Request: 1` on non-GET.

### [auth-contract-19] (high) (g) OpenAPI availability and quality for client generation

- CLAIM: `/api/openapi.json` and `/api/docs` exist only when WD_DEV=1 (404 otherwise). The document is OpenAPI 3.1.0, info.version 0.1.0, 70 paths (the 75 catalogue entries minus the two `/media` routes, which are `include_in_schema=False`, with GET+PUT/DELETE merges on /api/account, /api/settings, /api/admin/invites); it has no securitySchemes and documents only the 200 responses (the error envelope and 4xx codes are absent). Because DTOs are Pydantic models, request/response schemas are complete. The spec can be produced offline with `create_app(settings_with_dev=True).openapi()` — no running server is needed — and the TypeScript types are a hand-maintained copy of API.md §9.
- EVIDENCE: backend/wd/main.py:526-533; backend/wd/routers/media.py:38,51; docs/API.md:3,58-137; probe section C (paths=70, media paths [], securitySchemes null, /api/auth/me responses ['200']).
- IMPLICATION: A Swift (e.g. swift-openapi-generator) or TS client can be generated from a build-time export of the spec, but auth (cookie or future bearer), the error envelope `{error:{code,message,details}}` and the 401/403/409/423/429 semantics must be added by hand or by post-processing the spec; the generated spec should be committed/published rather than relying on a WD_DEV server.

### [auth-contract-21] (high) Browser-only assumptions: export and import

- CLAIM: Export (`GET /api/account/export?format=csv|json`) is a cookie-authenticated download with `Content-Disposition: attachment; filename="word-dance-export-YYYYMMDD.csv|json"`, triggered in the SPA by `<a href download>`; the JSON export includes up to 365 days of review_logs (several MB). Import (`POST /api/bank/import`) is NOT multipart: the SPA reads the chosen file with `File.text()`, reduces a JSON export to `{version, words}` (dropping review_logs), and posts a JSON body `{format: 'csv'|'json', data: <file text>}` that must stay under WD_MAX_BODY_BYTES (1 MB; 413 `payload_too_large` from Content-Length alone, before CSRF) and under the proxies' 2 MB caps; ≤ 2,000 rows else 400 `import_too_large`; imports count against the 200/day custom-add quota.
- EVIDENCE: backend/wd/routers/account.py:174-201; frontend/src/pages/SettingsPage.tsx:35-45,515-535,597-611; frontend/src/api/endpoints.ts:390-394,555-574; backend/wd/schemas.py:844-846; backend/wd/routers/bank.py:172-188; backend/wd/config.py:79; backend/wd/main.py:184-186; deploy/Caddyfile.example:4; deploy/nginx.conf.example:6; probe: export headers, 413 on Content-Length 2 MB.
- IMPLICATION: A native client implements export as an authenticated GET saved via the Files/share sheet (URLSession handles the cookie; a bearer client just sets the header) and import via a document picker that reads text and posts JSON — no multipart support is needed, but the 1 MB body cap and the client-side review_logs stripping must be replicated.

### [auth-contract-23] (high) Docs vs code discrepancies found in this slice

## Open questions

- Will the iOS client be fully native (URLSession/Swift) or a WKWebView/Capacitor shell? Native needs no CSRF/CORS/cookie changes (just `X-WD-Request: 1`); a bundled-SPA shell needs CORS + Origin allow-list + SameSite=None cookies (still fragile under ITP) or native HTTP routing; a WKWebView that loads the remote https SPA needs nothing but offers the least App Store differentiation.
- Should a bearer-token mode be added before the app ships (small change in deps.current_user + a login variant on the existing `sessions` table), and should it come with user-visible device sessions (`GET/DELETE /api/auth/sessions`) and a `client` column?
- How should `/media/*` be authenticated for non-cookie clients: Authorization header only (fine for native), or also signed/expiring URLs so `<img>` in a web view can load images?
- Which compatibility signal will the server expose before the first store release (e.g. `api_version` + `min_client_version` in /api/health), and will the team commit to additive-only changes given `extra="forbid"` on every request model?
- Is the admin console (endpoints 54–74) part of 'feature parity' for the iOS app or does it stay web-only?
- For a public server with strangers: should the login IP throttle stop counting successful logins and should the 20/10 min and 5 registrations/hour per-IP limits be raised for CGNAT/campus NATs; and is a forgot-password (reset-by-e-mail) flow in scope given e-mail is optional and SMTP may be unconfigured?
- Should the per-username lockout (anyone can lock any account by name for 15 min–24 h) be tightened (e.g. IP+username keying or CAPTCHA) before public exposure?
- Will the OpenAPI document be exported at build time and committed/published for Swift/TS client generation, with securitySchemes and the error envelope added by post-processing, instead of relying on a WD_DEV=1 server?
- Does the mobile client need daily reminders? If so, local notifications scheduled from `settings.next_push_at` versus a new APNs device-token endpoint on the server is a product decision outside this slice.
- Should the unimplemented hourly session GC (docs say hourly, code GCs only at login) be wired into the scheduler as part of the public-deployment hardening?
