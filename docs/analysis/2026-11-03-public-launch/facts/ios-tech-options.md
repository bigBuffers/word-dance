# Fact slice: ios-tech-options (36 findings)

## Summary

The web front end is 16,962 non-test lines, of which only ~2,261 lines (13%) are DOM-free TypeScript (api/, utils/, study/queue.ts, i18n) — the other 87% is React-DOM TSX (9,000 lines) and plain CSS (4,661 lines), so only the PWA and Capacitor routes reuse the 17 screens; Expo/RN and SwiftUI re-implement them. The backend is deliberately same-origin-only: the session is a cookie read nowhere else (deps.py:146), the CSRF rule accepts only the Host-derived or WD_PUBLIC_URL Origin (deps.py:111-129), there is no CORS, and even /media images require the session cookie (media.py:42) — which is why a Capacitor WKWebView at capacitor://localhost breaks cookies and <img> loads unless the app uses CapacitorHttp plus signed/tokenised media URLs, while native URLSession/RN clients pass the CSRF rule simply by sending X-WD-Request: 1 with no Origin. Current platform facts (verified 2026-11-03): iOS 26 makes every Home-Screen site open as a web app by default, Web Push/Badging have worked for installed web apps since iOS 16.4 and Declarative Web Push since 18.4, and installed web apps are exempt from ITP's 7-day storage purge — so a PWA closes most of the gap except file download UX and the lack of an App Store listing. Capacitor is at 8.6.0 (iOS 15+, Xcode 26+, Node 22) with 9.0.0-beta.0 published 2026-10-28 and GA targeted end-November; Expo SDK 58 (2026-10-15) ships React Native 0.88 built for iOS 27 with free EAS at 15 iOS builds/month and 1K MAU updates; Xcode 27.2 is the current Mac App Store build (3.12 GB download, needs macOS 26.6+, Apple silicon only), Apple already requires the iOS 26 SDK for uploads and will require iOS 27 SDK from April 2027, and 86% of recent iPhones run iOS 26 so an iOS 17 or 18 minimum costs almost nothing. App Review 4.2 ("features, content, and UI that elevate it beyond a repackaged website") is the dominant risk for the Capacitor route; it is negligible for RN/SwiftUI and irrelevant for the PWA. Every App Store route needs the $99/yr Developer Program, a token/APNs backend extension (new device-token table + send_apns job next to the existing send_email/send_webhook jobs), and an API versioning/min-client gate because native binaries break today's atomic SPA+API deploy. The "Android by-product" of Capacitor/RN is technical only: mainland Chinese stores (71% Android share) require an ICP filing, a software copyright certificate and a Chinese entity or local publisher, and FCM-based push is unusable there, whereas iOS Web Push/APNs work. The facts that dominate the choice are: how much of the 13% reusable code matters versus a rewrite, the owner's appetite for a 4.2 rejection fight, whether an App Store listing (discovery) is actually required versus "installable + notifications" (which a PWA plus the already-supported Bark webhook delivers today), and whether mainland distribution with ICP is in scope.

### [ios-tech-options-2] (high) Codebase: session is cookie-only, no token path

- CLAIM: Authentication is exclusively the `wd_session` cookie (HttpOnly; SameSite=Lax; Path=/; Max-Age = WD_SESSION_DAYS×86400, default 30 days; Secure per WD_COOKIE_SECURE/https). deps.current_user reads only request.cookies and raises 401 otherwise; there is no Authorization/Bearer handling anywhere. Expiry slides once per day and the middleware re-sends Set-Cookie on any response.
- EVIDENCE: backend/wd/security.py:229-242 (set/clear cookie flags); backend/wd/config.py:322 (session_days default 30), :317 (cookie_secure 'auto'); backend/wd/deps.py:146-149 (cookie read, 401), :164-173 (sliding expiry + reissue flag); backend/wd/main.py:174-177 (Set-Cookie re-issue in middleware)
- IMPLICATION: Native clients can work with the cookie as-is (URLSession/HTTPCookieStorage and RN's NSURLSession store Set-Cookie automatically; SameSite is not enforced by URLSession), but a bearer-token endpoint mapped onto the existing `sessions` table is a small backend change that removes RN cookie instability, enables Keychain/SecureStore storage and background fetch, and is the clean fix for cookie-protected images.

### [ios-tech-options-3] (high) Codebase: CSRF/Origin rule and absence of CORS

- CLAIM: Every non-GET /api/* request must carry `X-WD-Request: 1`; if an Origin header is present it must equal the request's Host-derived origin or the origin of WD_PUBLIC_URL (plus http://localhost:5173 under WD_DEV=1); `Origin: null` is rejected; a request WITHOUT an Origin header passes. There is no CORSMiddleware; API.md §1 states 'No CORS'. The check runs in the ASGI middleware for every /api path.
- EVIDENCE: backend/wd/deps.py:111-129 (csrf_violation), :32-35 (header/dev-origin constants); backend/wd/main.py:188-191 (middleware enforcement); grep CORSMiddleware → no hits; docs/API.md lines 11-12 ('No CORS')
- IMPLICATION: A Capacitor WebView fetch from capacitor://localhost sends Origin: capacitor://localhost → 403 csrf_rejected ('Origin mismatch'), and a browser preflight would also fail (custom header, no CORS). Native stacks (CapacitorHttp, URLSession, RN fetch) send no Origin, so they pass unchanged once they add the header. Supporting a browser-stack hybrid would need a new allowed-origins config AND a CORS layer with credentials — a larger and riskier change than token auth.

### [ios-tech-options-4] (high) Codebase: /media images require the session cookie and are relative URLs

- CLAIM: GET /media/images/{path} and /media/card/{id}.svg call current_user (401 without the cookie) and are cached `private`. ImageMeta.url is server-relative ('/media/images/ab/…jpg' | '/media/card/123.svg') and WordImage renders a plain <img src={image.url}>. The whole API client also uses server-relative '/api/…' paths (47 call sites) with credentials:'same-origin' and has no API-base environment variable.
- EVIDENCE: backend/wd/routers/media.py:38-48 and :51-57; docs/API.md lines 222-223 ('Session cookie required'); frontend/src/api/types.ts:79-81; frontend/src/components/study/WordImage.tsx:53-64; frontend/src/api/client.ts:103,107; grep api.(get|post…)('/api/ → 47; grep VITE_API/API_BASE → none
- IMPLICATION: Capacitor: <img> requests from capacitor://localhost to https://host are cross-site; WKWebView does not attach cookies to cross-origin image loads (WebKit bug 204109, iOS 13.3 regression) and since iOS 18 WKWebView's default SameSite is Lax (Apple forum thread 765199), and CapacitorHttp patches only fetch/XHR, not <img>. So images 401 unless the backend adds signed/tokenised media URLs or the app fetches blobs via CapacitorHttp. RN/SwiftUI: Image/AsyncImage go through NSURLSession with shared cookies, or can send a bearer header. Any non-PWA route needs an API-base + credentials:'include' change in client.ts and absolute media URLs.

### [ios-tech-options-15] (high) Route A (PWA): storage eviction and quota rules on iOS

- CLAIM: ITP deletes all script-writable storage (localStorage, IndexedDB, Service Worker registrations and cache) after seven days of Safari use without user interaction on the site — but 'Web applications added to the home screen are not part of Safari and thus have their own counter of days of use… We do not expect the first-party in such a web application to have its website data deleted.' Since Safari 17 the origin quota is up to 60% of disk (80% overall), a standalone Home-Screen web app has the same quota as in the browser, StorageManager.estimate() is supported and persistent storage is granted heuristically (e.g. when opened as a Home Screen web app).
- EVIDENCE: https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ (2020-03-24, 'A Note On Web Applications Added to the Home Screen'); https://webkit.org/blog/14403/updates-to-storage-policy/ (2023); https://webkit.org/blog/14445/webkit-features-in-safari-17-0/
- IMPLICATION: An offline cache of today's batch and the pending-grade queue is safe in the installed web app; in a plain Safari tab a 7-day lapse can wipe wd.pendingGrades (already mitigated because grades are posted immediately and only failures are queued).

### [ios-tech-options-19] (high) Route B (Capacitor): origin, cookies and network model on iOS

- CLAIM: On iOS the WebView origin is capacitor://localhost; iosScheme 'Can't be set to schemes that the WKWebView already handles, such as http or https' (Android default scheme is https). server.url 'is intended for use with live-reload servers… This is not intended for use in production'; allowNavigation and cleartext carry the same warning. ## Open questions

- Is an App Store listing (discoverability, trust) a goal in itself, or is the requirement really 'installable on the phone + daily reminder'? The latter is already met on iOS 26 by the PWA plus the existing Bark/WeCom/Feishu webhooks.
- Who are the target users — mainland China or overseas Chinese learners? This decides ICP filing exposure on the China App Store, whether Android distribution is even possible without a Chinese entity, and whether FCM-based Web Push is usable.
- Must the iOS app include the admin screens (≈15% of UI code) for 'feature parity', or can admin stay web-only?
- Does the owner have Swift or React Native experience? Effort ranges for routes C/D assume an experienced developer; add 4-8 weeks otherwise.
- Will the API adopt an additive-only/versioned policy (client-version header, min-version gate) before any binary client ships, given today's atomic SPA+API snapshot deploy (DEPLOY.md §2)?
- Should native clients keep the cookie session (works with URLSession) or should the backend issue bearer tokens mapped onto the sessions table (needed for RN reliability, Keychain storage and tokenised /media URLs)?
- Can the production host reach api.push.apple.com (APNs, HTTP/2) and *.push.apple.com (Web Push) from its deployment region, and will the Developer Program be enrolled as an individual (no D-U-N-S) or an organisation?
- Device tests still needed on iOS 26.x/27.x: Web Speech voices and silent-switch behaviour in the installed web app and in WKWebView; the CSV/JSON export behaviour in standalone mode; Add-to-Home-Screen from the WeChat in-app browser (not verified in this slice).
- Is the owner's proxy-dependent network able to download Xcode 27.2 (3.1 GB) plus an iOS simulator runtime (~8 GB) in reasonable time, or is EAS Build (no local Xcode) preferable for a first TestFlight?
- If Capacitor is chosen, start on 8.6 now or wait for Capacitor 9 GA (targeted end of November 2026, Node 24 minimum)?
- Registration policy for public users: WD_REGISTRATION_MODE defaults to 'invite' and registration is throttled 5/h per IP (API.md 142) — how will App Review and carrier-grade-NAT users in China register?
- Apple Developer Program regional price (¥688/yr in China) and Codemagic/Bitrise free tiers were not verified in this slice.
