# Fact slice: delivery-push (25 findings)

## Summary

Today word-Dance has exactly two job-backed notification channels — `send_email` (SMTP digest) and `send_webhook` (five POST formats: generic, wecom, feishu, serverchan, bark) — plus the in-app /today page as source of truth; Bark is not an app integration but a webhook format that POSTs `{"title","body"[,"url"]}` to a user-supplied `https://api.day.app/<device_key>` URL, deduped per batch by the job key `webhook:<batch_id>` and the `webhook_status='sent'` guard, retried on HTTP/transport errors 2 min then 10 min and then marked `failed` (the 60-min step documented in DESIGN §6.5 is unreachable with max_attempts=3), with SSRF rejections final. An APNs channel is a full new channel: no HTTP/2 or crypto library exists in the venv (httpx 0.28.1 without `h2`, no `cryptography`/PyJWT), APNs requires HTTP/2 to api.push.apple.com with an ES256 .p8 JWT refreshed every 20–60 min, a persistent connection (the per-call `safe_post` client is the wrong shape), a `device_tokens` table plus registration endpoints, an `apns_enabled` setting, an `apns_status` column, 410-driven token pruning, and — the costly part — a new `jobs.type` CHECK value, which in SQLite means rebuilding the `jobs` table in migration 0010 and touching registry/queue/schemas/completeness tests; by analogy with webhook.py (407 lines) + its tests (497) the channel is roughly 800–1,100 lines backend+tests before any iOS code. Alternatives that need no new channel: Bark works now for any iOS user (third-party app, device key stored in plaintext, LAN-hosted Bark refused by the SSRF guard), e-mail works when SMTP is configured, and iOS Web Push for a Home-Screen web app (iOS 16.4+, user-gesture permission, service worker + manifest, VAPID keys, a subscriptions table and a web-push sender) is about the same backend size as APNs but needs no Apple account or App Store and also covers Android/desktop. SMTP is needed only for e-mail verification codes (sent synchronously in-request), the test mail and the daily digest; without it registration and login still work, but there is no password-reset flow at all, and the mailer opens one unpooled SMTP connection per message with no rate limiting, bounce handling, List-Unsubscribe or SPF/DKIM guidance, all drained by a single IoWorker thread shared with image fetches and webhooks. Pushes are already per-user timezone (per-user `next_push_at`, 02:30 local consolidation); only maintenance 03:30, the AI budget day/month windows, admin “today” and backup names use the operator `WD_TZ`, which for a global audience resets AI quota at Asia/Shanghai midnight. Every delivery link is `<public_url>/today` from `WD_PUBLIC_URL` → `kv.public_url_guess` (a private-IP http guess that is wrong behind a proxy) → omitted; there are no per-batch or signed links, a logged-out tap lands on `/login?next=/today`, and the SPA catch-all would serve index.html for `/.well-known/apple-app-site-association`, so universal links need an explicit JSON route plus an https `WD_PUBLIC_URL`.

### [delivery-push-1] (high) (a) channel inventory

### [delivery-push-2] (high) (a) Bark wiring: payload

- CLAIM: Bark is a webhook *format*, not an app integration: the user pastes the full Bark URL (device key included) into Webhook 地址 and picks format `bark`; the job POSTs JSON `{"title": "word-Dance 今日词汇 10月14日 · 复习 N · 新词 N[ · 推荐 N]", "body": <summary line + first 10 words with phonetic/meaning/example + link line>}` and adds `"url": "<public_url>/today"` only when a public URL is known; no Bark-specific keys (group, badge, sound, level, icon, isArchive, ciphertext, device_keys) are sent.
- EVIDENCE: backend/wd/delivery/webhook.py:267-303 (build_payload bark branch :288-291, digest_payload), :258-264 (digest_body); backend/wd/delivery/email.py:37 (DIGEST_WORDS=10), :120-157 (title/summary/word_lines), :160-194 (build_digest); backend/tests/integration/test_delivery.py:279-280, :291, :297 (bark bodies with/without url; URL `https://api.day.app/key`); Bark API fields: https://raw.githubusercontent.com/Finb/bark-server/master/docs/API_V2.md and route_push.go (POST /:device_key and POST /push with device_key(s)), retrieved 2026-11-03
- IMPLICATION: iOS users can get push notifications today with zero backend work by installing Bark; richer behaviour (badge, group, time-sensitive level, archive) would be a ~5-line addition to build_payload, but the device key sits in `user_settings.webhook_url` in plaintext and one user can register only one Bark device URL.

### [delivery-push-3] (high) (a) Bark/webhook dedupe and idempotency

- CLAIM: Delivery dedupe is per batch, not per attempt: `enqueue_deliveries` uses dedupe key `webhook:<batch_id>` folded by the partial unique index on live jobs, `publish_batch` fires exactly once via a conditional UPDATE, and the handler short-circuits when `webhook_status == 'sent'`; nothing is sent to the target to make the POST itself idempotent, so a target that accepted the request but timed out is re-POSTed on retry (at-least-once, duplicate notification possible).
- EVIDENCE: backend/wd/services/batches.py:365-373 (publish_batch), :1000-1032 (enqueue_deliveries, priority 20 at :46); backend/wd/jobs/queue.py:75-108 (UPSERT on live key); backend/wd/migrations/0001_init.sql:503 (ux_jobs_dedupe_live); backend/wd/delivery/webhook.py:321-339 (already_sent guard, raise on error); backend/wd/jobs/scheduler.py:145-157
- IMPLICATION: An APNs channel can do better cheaply (apns-collapse-id = `batch:<id>` collapses duplicates device-side); for Bark/webhooks duplicates after timeouts are an accepted property.

### [delivery-push-4] (high) (a) failure handling and retry schedule (docs vs code)

- CLAIM: `safe_post` never raises: a non-2xx answer becomes `http_error`, transport errors are classified (dns_failed/connect_failed/timeout/tls_failed), and the handler maps them to `queue.fail` with backoff 2 min after attempt 1 and 10 min after attempt 2, then `dead` on the third failure (`max_attempts=3`), setting `webhook_status` to `queued` while retrying and `failed` when dead with `delivery_error` truncated to 300 chars; SSRF rejections are final (`failed`, job `done` with `{"error","final":true}`). DESIGN §6.5 says “retries 1 min / 10 min / 60 min” and email.py's docstring says “2 / 10 / 60 min”; with max_attempts=3 the 60-min step is never reached — the test asserts dead after 3 attempts.
- EVIDENCE: backend/wd/delivery/webhook.py:224-254 (safe_post), :356-381 (handler); backend/wd/delivery/email.py:9 (docstring), :317-335 (handler); backend/wd/jobs/queue.py:31 (BACKOFF_MINUTES 2,10,60), :47-50, :83 (max_attempts=3 default), :173-195 (fail); docs/DESIGN.md:424; backend/tests/integration/test_delivery.py:218-234
- IMPLICATION: A Bark 400 for a bad device key is retried twice uselessly before `failed`; an APNs channel should add a 4xx-is-final rule (BadDeviceToken/Unregistered) consistent with the SSRF-final pattern, and the docs should be corrected to the real 2/10-then-dead schedule.

### [delivery-push-5] (high) (a) SSRF guard scope

- CLAIM: Webhook targets must be https, a real DNS name (no IP literal, no localhost/.local/.internal/.lan/… suffixes), resolve only to globally routable addresses, and are pinned to the resolved IP with Host/SNI set, 10 s timeout, no redirects; the save-time check `is_safe_https_url` mirrors this.
- EVIDENCE: backend/wd/delivery/webhook.py:36-51, :83-172 (is_public_ip, validate_url, pin), :175-182 (_client: HTTP/1.1 client per call), :224-254; backend/wd/security.py:489-525; backend/wd/routers/settings.py:94-99; frontend/src/i18n/zh.ts:79-81 (zh reasons)
- IMPLICATION: A self-hosted Bark server on a home LAN or plain http is refused (`host_not_public` / `invalid_url`); only public https Bark servers (api.day.app default) work. Web Push endpoints (web.push.apple.com, FCM) and APNs are public hosts, so the same policy would pass them, but APNs must not reuse the per-call client.

### [delivery-push-6] (high) (a) when deliveries do and do not happen

- CLAIM: Scheduled delivery requires `is_active=1`, `onboarding_state='done'`, `push_enabled=1` and a non-NULL `next_push_at`; deliveries are enqueued only on the first successful publish and are marked `skipped` (never sent) when the publish is more than 6 h late; the channel flags are re-read at send time, so disabling after publish yields `skipped`; `POST /api/today/build` builds without publishing, while admin `POST /api/admin/push/run` publishes immediately with deliveries.
- EVIDENCE: backend/wd/jobs/scheduler.py:49 (STALE_DELIVERY 6h), :102-110 (due_users), :145-157; backend/wd/services/batches.py:1013-1027, :1035-1050 (push_now); backend/wd/routers/admin_ops.py:433-445; backend/wd/delivery/webhook.py:326-329; backend/wd/delivery/email.py:279-282; docs/API.md:211, :234

- EVIDENCE: backend/wd/schemas.py:925-938 (Batch), :1048-1055 (BatchSummary), :1256-1269 (Job); backend/wd/routers/admin_ops.py:80 (_job_dto), :124-125, :207-228; backend/wd/jobs/queue.py:179; backend/wd/services/batches.py:1099; grep of frontend/src for email_status/webhook_status: no matches; delivery_error is written by both channels: email.py:264-269, webhook.py:307-312
- IMPLICATION: For a public service an admin/user-facing delivery status (per batch, per channel, per device) is missing; adding `apns_status` without surfacing it would keep APNs problems invisible except in the jobs ledger.

### [delivery-push-8] (high) (b) APNs transport prerequisites vs repo dependencies

- CLAIM: APNs requires HTTP/2 + TLS 1.2 to `api.push.apple.com:443` (sandbox `api.sandbox.push.apple.com:443`, alt port 2197) with token auth: an ES256 JWT signed by the team's `.p8` key (header alg/kid, claims iss=Team ID, iat), refreshed “no more than once every 20 minutes and no less than once every 60 minutes”, one key valid for all the team's apps. The repo pins `httpx==0.28.*` without the `[http2]` extra; the project venv has httpx 0.28.1/httpcore 1.0.9 but no `h2`, `cryptography`, `PyJWT` or `requests`, and `httpx.Client(http2=True)` raises ImportError there.
- EVIDENCE: backend/requirements.txt (httpx==0.28.*, bcrypt, Pillow, defusedxml, python-dotenv); /Users/sqin/word-dance/.venv pip list and import probes run 2026-11-03; httpx HTTP/2 docs https://www.python-httpx.org/http2/ (retrieved 2026-11-03: not enabled by default, needs `pip install httpx[http2]`); Apple docs retrieved 2026-11-03: sending-notification-requests-to-apns, establishing-a-token-based-connection-to-apns (developer.apple.com/documentation/usernotifications/…)
- IMPLICATION: Minimal new dependencies are `httpx[http2]` (h2/hpack/hyperframe) plus `cryptography` for ES256 (PyJWT would also need it); `aioapns` 4.0 (2025-04-14) is asyncio-only and does not fit the threaded sync IoWorker. Deployment must allow these wheels on the server.

### [delivery-push-9] (high) (b) APNs sender shape: persistent connection and response handling

- CLAIM: Apple asks providers to reuse a connection “for many hours to days”, avoid push bursts over few connections and make an uncached DNS query per connection; the existing `safe_post` opens and closes an HTTP/1.1 client per call with a DNS-pinned URL and Host/SNI override, so it cannot be reused for APNs. Required response handling: 200 ok; 400 BadDeviceToken/DeviceTokenNotForTopic → drop token, no retry; 403 Expired/Invalid/MissingProviderToken → mint a new JWT / config error; 410 Unregistered (+`timestamp` in ms) → stop sending to that token unless the app re-registered it after that timestamp; 429 TooManyRequests → retry with delay; 5xx → retry (Apple suggests after 15 min); payload ≤ 4096 bytes; `apns-collapse-id` ≤ 64 bytes.
- EVIDENCE: backend/wd/delivery/webhook.py:175-182, :236-251; Apple docs retrieved 2026-11-03: sending-notification-requests-to-apns (headers apns-topic/apns-push-type/apns-id/apns-expiration/apns-priority/apns-collapse-id, 4 KB limit, connection reuse), handling-notification-responses-from-apns (status table and reason strings)
- IMPLICATION: An `apns.py` needs a module-level persistent `httpx.Client(http2=True)` owned by the single IoWorker thread, a cached JWT with 20–60 min refresh, a per-token outcome map (sent / dropped / retry), and a tests hook like `CLIENT_FACTORY`/`MockTransport` (webhook.py:53-54, test_delivery.py:254-283).

### [delivery-push-10] (high) (b) APNs data model and endpoints

- CLAIM: Multi-device registration needs a new table (e.g. `device_tokens(id, user_id FK ON DELETE CASCADE, token UNIQUE, environment sandbox|production, platform, app_version, created_at, last_seen_at, invalidated_at)`) with `POST /api/devices` (upsert by token, re-own to the current user) and `DELETE /api/devices/{token}`; the app must authenticate with the cookie session and send `X-WD-Request: 1` on non-GETs (CSRF rule). Device tokens from Xcode debug builds only work against the sandbox host, so the environment must be stored per token or fixed per build.
- EVIDENCE: backend/wd/migrations/0001_init.sql:87-97 (sessions: precedent for N rows per user with CASCADE); backend/wd/deps.py:142-171 (cookie-only auth); docs/API.md:10-11 (session cookie, CSRF header/Origin rule); Apple docs retrieved 2026-11-03 (BadDeviceToken: “token matches the environment”)
- IMPLICATION: The iOS app's first backend touchpoints are session login + device registration; account deletion already cascades per-user rows, so a FK with CASCADE keeps DESIGN §10 privacy deletion intact.

### [delivery-push-15] (medium) (c) alternative: iOS Web Push for a Home-Screen web app

- CLAIM: Web Push works on iOS/iPadOS 16.4+ only for web apps added to the Home Screen (no install prompt API; third-party browsers can add since 16.4), permission may be requested only in response to a user gesture, the Badging API is supported, and the site must behave as a web app via a manifest `display: standalone|fullscreen` or the `apple-mobile-web-app-capable` meta that index.html already carries. The repo has no manifest and no service worker (public/ holds only favicon.svg; no PWA plugin). Server-side needs: VAPID keypair + subject (`WD_VAPID_*`), a `push_subscriptions` table (user_id, endpoint UNIQUE, p256dh, auth, user_agent, created_at, failed_at), `POST/DELETE /api/push/subscriptions`, a `send_webpush` job (same jobs-CHECK rebuild) and a sender — `pywebpush` 2.5.0 (2026-08-29; needs `requests`, `cryptography`, `py-vapid`, `http-ece`; raises WebPushException with 404/410 status for dead subscriptions) or an httpx + `cryptography` RFC 8291/8292 implementation (~150 lines). Frontend: `sw.js` (`push`, `notificationclick` → open `/today`) and `manifest.webmanifest` in `frontend/public`, served by the SPA catch-all with `public, max-age=3600`; `.webmanifest` resolves to `application/manifest+json`. When a site is added to the Home Screen Safari copies cookies into the web app, so the `wd_session` login carries over.
- EVIDENCE: frontend/index.html:5-14; frontend/public (favicon.svg only); backend/wd/main.py:242-260 (catch-all, cache headers); venv mimetypes probe 2026-11-03; docs/DESIGN.md:566 (CSP script-src/connect-src 'self'); WebKit blog https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/ (retrieved 2026-11-03); https://pypi.org/project/pywebpush/ (retrieved 2026-11-03); WWDC23 session 10120 notes https://wwdcnotes.com/notes/wwdc23/10120 (cookies copied to Home Screen web apps; retrieved 2026-11-03)
- IMPLICATION: Web Push reaches iOS without an Apple Developer account, App Store review or HTTP/2 — and covers Android/desktop — at roughly the same backend size as APNs, but depends on users performing the Home-Screen ritual on iOS ≥ 16.4 and on an https `WD_PUBLIC_URL` (secure context).

### [delivery-push-16] (medium) (c) comparison of no-new-channel options vs APNs

- CLAIM: Ordered by backend effort: e-mail (0, exists; needs SMTP and deliverability work) < Bark (0; third-party app, one device, plaintext key) < Web Push (≈ APNs-sized: new table, endpoints, job type, sender, SW/manifest; no Apple account) ≈ APNs (same plus HTTP/2 stack, .p8 key management, native app, App Store). Only APNs gives app badge control, reliable background delivery and a tap that opens the native app directly; Bark and Web Push both open `<public_url>/today` in a browser/web-app context.
- EVIDENCE: Synthesis of the findings above: webhook.py:288-291, email.py:60-70, main.py:242-260, requirements.txt, Apple/WebKit docs retrieved 2026-11-03
- IMPLICATION: If the native app is mandated for other reasons, APNs is the natural channel; if notifications are the main motive for an app, Bark now plus Web Push next is the cheaper path.

### [delivery-push-17] (high) (d) what needs SMTP today

- CLAIM: Three code paths need a configured mailer (`WD_SMTP_HOST` + `WD_SMTP_FROM`, built once at app creation, so a change needs a restart): (1) `POST /api/account/email/request-code` sends the 6-digit code synchronously inside the request (409 `smtp_unconfigured` without mailer, 503 `email_send_failed` on MailerError; 3/h per user, TTL 900 s, 5 attempts, HMAC with `WD_SECRET_KEY`, which is ephemeral per process when unset); (2) `PUT /api/settings {email_enabled:true}` → 409 `email_not_verified` / `smtp_unconfigured`; (3) `POST /api/settings/email/test` → 409 or a queued `send_email {user_id, test:true}` job. The daily `send_email` job marks the batch `skipped` with `delivery_error 'SMTP not configured'` when no mailer exists, and `ServerFlags.email_configured` disables the UI switch with 「服务器未配置邮件发送」.

- IMPLICATION: For strangers registering on a public server, a password-reset flow is the first feature that would make SMTP a hard dependency; today the operator would reset passwords by hand.

### [delivery-push-19] (high) (d) provider and politeness assumptions of the mailer

- CLAIM: `SmtpMailer.send` opens a fresh SMTP connection per message (STARTTLS/SSL/plain, optional LOGIN, 20 s timeout), sets only From/To/Subject/Date/Message-ID (Message-ID domain taken from the From address), no `List-Unsubscribe`, no bounce/complaint handling, no suppression list and no send-rate limit (only the test send 1/10 min and codes 3/h per user); the digest footer merely says 「在应用的设置中可以关闭邮件推送」 with no link; `wd check smtp` only TCP-connects; docs never mention SPF/DKIM/DMARC or provider quotas. All e-mails, webhooks and image fetches are drained serially by the single `io-1` thread, so at a shared push time N recipients × (≤ 20 s SMTP + ≤ 10 s webhook) run back to back and a failing relay delays everyone.
- EVIDENCE: backend/wd/delivery/mailer.py:38-47, :70-100; backend/wd/delivery/templates/daily_email.html:20; backend/wd/security.py:74-75; backend/wd/diag.py:107-120; backend/wd/jobs/worker.py:9, :45, :275-278; backend/wd/main.py:105-111 (THREAD_CLASSES: io once); grep of docs/ for dkim/spf/bounce/unsubscribe: no matches
- IMPLICATION: Public use needs an external transactional provider (and for a mainland-China audience one reachable there), a sending domain with SPF/DKIM/DMARC, provider quota awareness, and probably a second IoWorker or per-type workers; none of this is enforced or documented in the repo.

### [delivery-push-20] (high) (e) per-user timezone handling is already in place

- CLAIM: Pushes are per user: `timezone` + `push_time` produce a UTC `next_push_at` (validated against zoneinfo, defaults Asia/Shanghai 08:00 at registration, auto-detected in onboarding, curated 30-zone list with `?all=1`), the scheduler builds/publishes each due user in that user's zone with a DST-safe `compute_next_push`, re-anchors after downtime, and nightly `consolidate_bank` runs at 02:30 user-local; changing timezone/push_time recomputes `next_push_at`.
- EVIDENCE: backend/wd/clock.py:109-130; backend/wd/security.py:84-85, :617-619, :661-664; backend/wd/routers/settings.py:34-65, :107-119, :127-133; backend/wd/jobs/scheduler.py:102-157, :194-225; backend/wd/delivery/email.py:79-83, :302-304 (test mail in the user's tz); docs/DESIGN.md:330, :368-394
- IMPLICATION: A global audience needs no scheduler redesign for delivery timing; APNs/Web Push jobs would be enqueued at the user's local push time like e-mail.

### [delivery-push-21] (high) (e) what remains tied to the operator timezone WD_TZ

- CLAIM: `WD_TZ` governs the 03:30 maintenance (prefetch, dead-job requeue, log pruning, PRAGMA optimize), the AI daily/monthly budget windows and their 00:05 resume times, the admin overview's “today”, and backup file names; DEPLOY documents this split (“user pushes use each user's own timezone”).
- EVIDENCE: backend/wd/jobs/scheduler.py:52, :352-360; backend/wd/ai/budget.py:74-104, :136-165, :213-234, :293-294; backend/wd/routers/admin_ops.py:110; backend/wd/backup.py:252-263, :480; backend/wd/config.py:76, :273-275; docs/DEPLOY.md:310; deploy/env.example:38-39
- IMPLICATION: For users far from Asia/Shanghai the shared AI quota resets at an odd local hour and the prefetch runs at their daytime; acceptable for a hobby deployment, but budget fairness across timezones is an open design question for public use.

### [delivery-push-22] (high) (e) single-process scheduling burst

- CLAIM: The app enforces exactly one uvicorn worker and one lease holder; one scheduler thread processes every due user serially each 60-s tick (prebuild window `WD_PREBUILD_HOURS=3`), and deliveries fan into the single IoWorker — so all users sharing a popular push time (08:00 Asia/Shanghai default) form a build + delivery burst with no horizontal scaling path.
- EVIDENCE: backend/wd/main.py:504-517 (assert_single_worker), :402-436 (lease); backend/wd/jobs/scheduler.py:160-165, :477-482; backend/wd/config.py:80-82; backend/wd/jobs/worker.py:275-278
- IMPLICATION: Capacity planning for a public server is about users per push minute; Apple additionally asks providers to avoid push bursts over few connections.

### [delivery-push-23] (high) (f) delivery links: one target, one precedence rule, no auth

- CLAIM: Every link in e-mails and webhooks is `<base>/today`, with `base` = `WD_PUBLIC_URL` → `kv.public_url_guess` → none (then the button/`url` is omitted and the text says 「请在浏览器中打开 word-Dance」); the test webhook never includes a URL; there is no per-batch link (`/history/:batchId` and `/study?batch=` exist as SPA routes) and no signed/auto-login link — a logged-out tap goes to `/login?next=/today` and a not-onboarded user to `/welcome`.
- EVIDENCE: backend/wd/delivery/email.py:60-70, :198-236, :239-251, :304; backend/wd/delivery/webhook.py:263, :280, :288-291, :351; frontend/src/routes.tsx:30-98; frontend/src/auth/AuthContext.tsx:175-178, :196-218; docs/DESIGN.md:423
- IMPLICATION: An app would want the same canonical URL as a universal link plus a structured `batch_id`; keep `<public_url>/today` as the single deep-link target so e-mail, Bark, Web Push and APNs all open the same place.

### [delivery-push-24] (high) (f) kv.public_url_guess is wrong for a public server

- CLAIM: When `WD_PUBLIC_URL` is empty the server records `http://<first non-loopback IPv4>:<WD_PORT>` at startup (UDP-connect trick) and uses it in links; behind the documented Caddy/nginx setup the app binds 127.0.0.1 and the guess is a private IP over http that outside users cannot open. `install.sh --with-caddy/--with-nginx` writes `https://<domain>`; the Mac install deliberately leaves it empty. `WD_PUBLIC_URL` must start with http(s) and also drives the CSRF origin and cookie `Secure`.
- EVIDENCE: backend/wd/main.py:280-300, :482-484; backend/wd/config.py:145-161, :277-279; deploy/install.sh:114-125; docs/DEPLOY.md:302-303; memory note macos-local-install.md (WD_PUBLIC_URL left empty on purpose)
- IMPLICATION: A public deployment must set `WD_PUBLIC_URL=https://<domain>`; otherwise every notification link (and any universal link) is useless.

### [delivery-push-25] (high) (f) universal links need an explicit AASA route

- CLAIM: iOS universal links require `https://<domain>/.well-known/apple-app-site-association` served as JSON without redirects; the SPA catch-all returns `index.html` (HTML) for any unknown path and would serve an extension-less static file as `application/octet-stream` with `Cache-Control: public, max-age=3600` (Starlette's FileResponse default), while the Caddy/nginx examples simply reverse-proxy everything to the app.
- EVIDENCE: backend/wd/main.py:242-260; .venv starlette/responses.py:319-320 (guess_type or application/octet-stream) and mimetypes probe run 2026-11-03; deploy/Caddyfile.example:2-6; deploy/nginx.conf.example:7-8
- IMPLICATION: A dedicated FastAPI route (or file + explicit media type) for the AASA, plus `WD_PUBLIC_URL` over https, is a small prerequisite for the app to intercept `<public_url>/today` links from e-mails and Bark; also relevant for a `manifest.webmanifest`/`sw.js` which the catch-all already serves correctly.

## Open questions

- Is a native iOS app required for reasons other than notifications? If notifications are the main driver, Bark today plus iOS Web Push for the Home-Screen web app may satisfy the need without APNs, an Apple Developer Program membership or App Store review.
- Does the owner have (or plan) an Apple Developer Program membership, a Team ID, a bundle id and an APNs .p8 key — and where would the key live on the server (file path vs env var, both need masking in GET /api/admin/config)?
- Will the public server have a domain with https so that WD_PUBLIC_URL is https (required for universal links, Web Push secure context and Secure cookies)? Who operates the reverse proxy?
- Which SMTP/transactional provider and sending domain (SPF/DKIM/DMARC) will be used, and is the audience mainland China (overseas providers and api.day.app reachability) or global?
- Should a self-service password-reset flow be added before opening registration? It would be the first hard SMTP dependency for strangers.
- Should a new job type be introduced via a `jobs` table rebuild (migration 0010, affects the live queue during install.sh's stop-migrate-start) or should APNs/Web Push be multiplexed onto `send_webhook` with a payload discriminator?
- Multi-device semantics: one `apns_enabled` flag per user with N tokens, or per-device toggles? What happens when a token is re-registered by a different account on the same device?
- Is at-least-once duplicate delivery after timeouts acceptable for Bark/webhooks, or should APNs collapse-id and per-target idempotency become a requirement?
- Should delivery outcomes (email_status / webhook_status / future apns_status, delivery_error) be surfaced to users or admins, given that today they are visible only in the jobs ledger and the DB?
- Should the AI budget day/month windows and maintenance stay on WD_TZ for a multi-timezone public audience, or move to per-user or UTC accounting?
- Does the existing single IoWorker thread remain acceptable once deliveries include per-device APNs/Web Push fan-out at a shared 08:00 push time, or is a dedicated delivery worker needed?
- Should the test webhook/test push include a URL so users can verify the deep link before the first real digest?
